# LKAP v2 — Phased Delivery Plan

Status: **decided** (Fable 5.1, 2026-09-19). Owners: **Opus 5** for hard/critical, **Sonnet 5** for the rest. Fable reviews at the end of each wave and owns the final review package.

Naming: v2 packages are **`V2-nn`**. Do not confuse with REVIEW-FINAL's fix packages (WP-A..D, done) or UI_UX_SPEC's UI packages (WP-0..WP-12; WP-0 landed, WP-1..12 resume under §4 below).

Definitions used by every package:
- **Python gate** (run inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test && pnpm build`.
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts` (the export diff test must pass).
- **Live gate**: the named `uv run pytest -m live …` commands from `../RUNBOOK.md` §5 plus the v2 stages in §6 of this document, run against `wss://your-project.livekit.cloud` with exactly one worker per connection and never touching `other-project-agent`.
- **Exclusive ownership**: a package may create/edit only the paths it lists; shared files (`providers.py`, `api_models.py`, `registry.ts`, `main.py` router wiring, alembic versions) are owned by exactly one package per wave. Anyone else needing a change files it as a one-line ask in `docs/v2/_asks.md` for the owner.

## 8. Rulings during implementation

Recorded here so they outlive the chat. IDs `R-V2-n`; they amend the cards above and CONTRACTS where noted.

### R-V2-1 — `status` alias derives from availability + image, never from verification (asks #7)
- Rule: `ProviderSpec.status == "mvp"` iff `availability == "available" and worker_image == "slim"`. `verification` is an informational chip and **never** gates validation, seeding, pickers or construction.
- Consequences: V2-00 sets `verification` honestly (four entries) and gives all 18 v1 MVP entries `worker_image="slim"`; V2-05's flip is a no-op for `status`; V2-05 lands every new entry with `worker_image="full"`, so the v1 `mvp` set is byte-identical until consumers migrate. New test in V2-00/V2-05: the `mvp` id set equals the v1 set.
- Why not migrate consumers in wave 0/1: the correct gate needs `installed_on` (V2-04/V2-07) and workspace enablement (V2-06), neither of which exists before wave 2. Gating on `availability` alone would offer ~70 providers the slim worker cannot construct.
- Alias removal: Phase 2 wave 1, after V2-03 and V2-13 have migrated every consumer.

### R-V2-2 — ownership of the `status` consumers (asks #9)
- `api/src/lkap_api/config_service.py` and `api/src/lkap_api/packs.py` → **V2-03** (wave 1; the migration to `availability` + installed-on + enabled happens there, using the `VALIDATORS` hook list; until worker registration exists, "installed-on" falls back to `worker_image ≤ connection.worker_image`).
- `web/src/components/console/registry/**` and `CAPABILITY_META` → **V2-13** (wave 2).
- V2-00's "owns and updates" wording is withdrawn; V2-00 touches none of these files.

### R-V2-3a — home page footer doc links (WP-11)
