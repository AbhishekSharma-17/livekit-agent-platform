# LKAP v3 — Agent Access Layer: delivery plan

Status: **decided** (Fable 5.1, 2026-09-24). Baseline HEAD `edac441` (Phase 1 complete). Owners: **Opus** for the server core, the chat transport and the api changes; **Sonnet** for docs, console and tests. Fable reviews at the end of each wave and signs off the live run.

Naming: v3 packages are **`V3-nn`**. Rulings are **`R-V3-n`** (§8) and amend the cards and `AGENT-ACCESS.md`.

Definitions (unchanged from PLAN-V2):
- **Python gate** (inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test` (never `pnpm build` in `web/`; HANDOFF rule 6).
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts mcp/src/lkap_mcp/generated mcp/claude-plugin/skills/lkap/recipes` (the third path exists from wave 1, once V3-01's copy step lands; the fourth from wave 2, V3-08's recipe copies, R-V3-36; V3-00 ran the gate with the first two paths).
- **Exclusive ownership**: a package edits only the paths its card lists; anything else is a one-line ask in `docs/v3/_asks.md` for the owner. The coordinator's decisions there are binding.
- **Migration discipline** (HANDOFF rule 4, R-V3-10): only the coordinator runs `alembic` against `api/data/lkap.db`, after `sqlite3 api/data/lkap.db ".backup <scratchpad>"`. Packages rehearse on copies.
- **Live rules** (HANDOFF rule 3): the shared Cloud project also hosts `other-project-agent` (never touch it) and the user's worker `lkap-agent` (never run a second worker under that name). Live checks use a scratch api with its own DB and port, and a worker under a fresh agent name.

## 4. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A client does not surface resources or prompts | Every doc is also a tool (`lkap_guide`, `lkap_explain`, `lkap_describe`); the guide tells the agent to call `lkap_guide` first; the console snippet suggests a `CLAUDE.md` line. |
| Sixty tools crowd the model's context | Scope gating hides what the key cannot do (read-only ≈ 25 tools); descriptions are one line; the catalog snapshot keeps them deliberate. Phase 2 may add `LKAP_MCP_TOOLSET=` to select domains. |
| Secrets pasted inline by a user who ignores the guide | Refused by default; the opt-in is an explicit console checkbox with the transcript warning; `file:` refs reuse the env file the user already keeps. |
| `livekit` rtc native wheel fails on a client machine | It is the same wheel the agent uses on the dev host; the tool degrades to `code="chat_unavailable"` with the console Test chat as the fallback; V3-06 (HTTP mode) runs on the platform side. |
| Merge-patch clobbers a concurrent console edit | `agent_update` re-reads before patching and reports the `config_version` it wrote over; the versions history restores; a `config_version` precondition on `PUT /v1/agents/{id}` is a Phase 2 api ask. |

### R-V3-28 — Per-call rate limits are tool results, not HTTP `429`; HTTP `429` stays only for the 6th `initialize` (V3-06-6)
- **Decision.** On an open session, the two per-call limits of §9.3/§9.5 item 5 — 120 `tools/call` per rolling minute per session and 10 tool calls in flight per session — are answered **in band**, as the tool's result with HTTP 200: `ok=false, code="rate_limited", status=429, details={"retry_after_s": <float>, "limit": <int>, "scope": "calls_per_min" | "in_flight"}, next_steps=["wait retry_after_s seconds, then retry this call"]`. This is the exact shape `client.py` already produces when the **api** answers 429 (`code="rate_limited"`, `details.retry_after_s`, `status=429`), so an agent sees one shape for both sources. Reason: a JSON-RPC-level HTTP 429 on an open session makes the Python SDK client raise out of its task group (`raise_for_status` in a child task), so the whole client session dies instead of one call failing; Claude Code and Codex are unverified and this design already answers every other mid-session refusal in band (`unauthorized`, `call_timeout`, `too_many_chats`, `no_session`). The transport-level HTTP `429` with `Retry-After` stays **only** for the 6th `initialize` of one key (no session exists to answer in band, and a client raising at `initialize` is the right outcome).
- **Where.** The check moves from `HttpSessions.serve` (before `transport.handle_request`) into the per-session tool wrapper (`SessionRegistry.wrapped` / `_limited_call`), fed by a per-session meter (the `calls` window and an `in_flight` counter that live on `HttpSession` today; give the registry a reference at `_start`). Only `tools/call` is metered, which is what §9.5 item 5 says ("in-flight **calls**"); `tools/list`, `resources/read` and `prompts/get` are local and stay unmetered (the 1 MB body cap and Caddy's per-IP limits are the flood guards). A refused call does **not** extend the window (today `window.extend` runs only under the limit; keep that), and `retry_after_s` derives from the oldest counted call, so a hammering client always gets out after one minute.
- **Owner:** **V3-06F** (Opus, a follow-up fix before V3-07; card below). **Acceptance:** (1) a test through the real `mcp` streamable-HTTP `ClientSession`: with `LKAP_MCP_CALLS_PER_MIN=3`, the 4th call returns `ok=false, code="rate_limited"` with `0 < details.retry_after_s <= 60`, the session is still open, and a 5th call on the **same** session after the fake clock slides 61 s succeeds; (2) the in-flight test: with the meter at 10 the 11th call returns the same result in band and at 9 it succeeds; (3) `test_sixth_session_for_one_key_is_429_and_other_keys_are_unaffected` stays as is (HTTP 429, `Retry-After`); (4) the two raw-HTTP tests of the old behaviour are rewritten to assert HTTP 200 plus the in-band result, not merely flipped; (5) no `Retry-After` header on a 200; (6) docs synced in the same change: the `http.py` module docstring, `mcp/README.md` "Limits and answers" (the `429 + retry_after_s` row becomes two rows: HTTP `429` for the 6th session; tool result `rate_limited` for the per-call limits), RUNBOOK §20.4 (the table rows **and** the sentence "A `429` on an open session can end some clients' sessions" is deleted), `AGENT-ACCESS.md` §9.3 and §9.5 item 5 (amended by the architect in this commit; V3-06F re-checks the wording against the code), and the V3-06 card's acceptance phrase "the 121st call in a minute → 429 with `retry_after_s`" (amended here to "→ the in-band `rate_limited` result").
