# Dograh — Research Brief for LiveKit Agent Platform Design

**Purpose:** Verified, source-cited analysis of [Dograh](https://github.com/dograh-hq/dograh), an open-source voice-agent platform built on [Pipecat](https://github.com/pipecat-ai/pipecat), to inform feature-parity decisions for our LiveKit-based voice + video agent platform.

**Research date:** 2026-09-19. **Primary sources:** the official repo cloned at commit `main` HEAD as of this date, `docs.dograh.com` (mirrored in-repo under `docs/`), GitHub Issues/PRs/Releases via the GitHub API, and public LiveKit Agents documentation for the comparison section. Every claim below is cited; anything not directly confirmed in a primary source is marked **UNVERIFIED**.

---

## 2. Architecture

### 2.1 Services and components

Dograh ships as **two application images** — `dograh-api` and `dograh-ui` — plus Postgres, Redis, and MinIO, "orchestrated with Docker Compose" ([docs/deployment/introduction.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/introduction.mdx)). The root [`docker-compose.yaml`](https://github.com/dograh-hq/dograh/blob/main/docker-compose.yaml) defines:

| Service | Image | Role |
|---|---|---|
| `postgres` | `pgvector/pgvector:pg17` | Primary DB; **pgvector** extension is used directly for knowledge-base embedding similarity search |
| `redis` | `redis:7` | Cache, ARQ task queue backend, rate limiting, cross-worker pub/sub |
| `minio` | `quay.io/minio/minio` | S3-compatible object storage for recordings/audio (bucket `voice-audio`); swappable for AWS S3 via `ENABLE_AWS_S3` |
| `dograh-init` | `bash:5.2` | One-shot init container (profiles `remote`, `local-turn`) that renders nginx/coturn config before other services start |
| `nginx` | `nginx:alpine` | HTTPS reverse proxy + `least_conn` load balancer across N uvicorn worker processes (profile `remote`) |
| `coturn` | `coturn/coturn:4.8.0` | TURN server for WebRTC NAT traversal (profiles `remote`, `local-turn`) |
| `api` | `dograhai/dograh-api` | FastAPI backend — runs multiple internal processes, not just uvicorn (see §2.4) |
| `ui` | `dograhai/dograh-ui` | Next.js frontend, port 3010 |
| `cloudflared` | `cloudflare/cloudflared` | Optional Cloudflare Tunnel (profile `tunnel`) for inbound reachability without a public IP |

(all rows: [docker-compose.yaml](https://github.com/dograh-hq/dograh/blob/main/docker-compose.yaml)). A stripped `docker-compose-local.yaml` runs only postgres/redis/minio for contributor dev against a locally-run API ([docker-compose-local.yaml](https://github.com/dograh-hq/dograh/blob/main/docker-compose-local.yaml)). `deploy/hostinger/` provides a Traefik-fronted compose variant for Hostinger VPS deployment ([deploy/hostinger/docker-compose.yaml](https://github.com/dograh-hq/dograh/blob/main/deploy/hostinger/docker-compose.yaml)). `deploy/observability/` bundles a Prometheus scrape config (against the API's `/api/v1/metrics`, guarded by a devops-secret header) and a Grafana dashboard JSON ([deploy/observability/prometheus/prometheus.yml](https://github.com/dograh-hq/dograh/blob/main/deploy/observability/prometheus/prometheus.yml)).

A Helm chart at `deploy/helm/dograh/` (marked "v1, alpha … not yet exercised against a live cluster" by the maintainers) **decomposes** the single-container compose model into separate Deployments: `dograh-web` (HPA-able, 2 replicas default), `dograh-arq-worker` (HPA-able), `dograh-ari-manager` (fixed 1 replica, `Recreate` — telephony singleton), `dograh-campaign-orchestrator` (fixed 1 replica, `Recreate` — campaign singleton), `dograh-ui` (2 replicas), `dograh-coturn` (1 replica, `LoadBalancer` Service). It deliberately keeps Postgres/Redis/MinIO as plain in-chart manifests on official images rather than third-party subcharts. Notable operational details: a 1260s pod termination grace period (covers a full 20-minute call), an active-call-drain `preStop` hook, and explicitly deferred TODOs — no leader-election HA for the two singletons, no NetworkPolicy, no TURN TLS in v1 ([deploy/helm/dograh/README.md](https://github.com/dograh-hq/dograh/blob/main/deploy/helm/dograh/README.md), [Chart.yaml](https://github.com/dograh-hq/dograh/blob/main/deploy/helm/dograh/Chart.yaml)).

### 2.2 Backend tech stack

**Framework:** FastAPI (`fastapi==0.135.3`, `uvicorn==0.35.0`), entrypoint `api.app:app` ([api/requirements.txt](https://github.com/dograh-hq/dograh/blob/main/api/requirements.txt), [api/app.py](https://github.com/dograh-hq/dograh/blob/main/api/app.py)). **Python** `>=3.13,<3.14`, pinned `3.13.7` ([api/pyproject.toml](https://github.com/dograh-hq/dograh/blob/main/api/pyproject.toml)). Dependencies are managed as a plain `requirements.txt` installed with `uv pip install` at Docker build time (uv as installer only, not a project/lockfile manager) ([api/Dockerfile](https://github.com/dograh-hq/dograh/blob/main/api/Dockerfile)).

Key dependencies ([api/requirements.txt](https://github.com/dograh-hq/dograh/blob/main/api/requirements.txt)): `sqlalchemy[asyncio]==2.0.43` + `asyncpg==0.30.0` (async ORM), `alembic==1.16.5` (migrations), `pgvector==0.4.2` (KB embeddings), `redis==5.3.1` + `arq==0.26.3` (queue), `aioboto3`/`minio` (storage), `twilio==9.8.0`, `fastmcp==3.2.4` (Dograh's own MCP server), `langfuse==4.14.3` + `opentelemetry-exporter-prometheus` + `sentry-sdk[fastapi]` (observability), `posthog` (product telemetry), `tuner-pipecat-sdk`, `noveum-trace`.

**Database (`api/db/`):** SQLAlchemy 2.0 async models in `db/models.py`, with per-domain "client" modules (`workflow_client.py`, `campaign_client.py`, `telephony_configuration_client.py`, `knowledge_base_client.py`, etc.) rather than a generic repository pattern. `api/AGENTS.md` mandates that "routes, services, tasks, and MCP code must call DB clients instead of importing SQLAlchemy or opening sessions" ([api/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/AGENTS.md)). Key tables include `organizations`, `users`, `api_keys`, `telephony_configurations`, `telephony_trunks`, `telephony_phone_numbers`, `workflow_definitions`, `workflows`, `workflow_runs`, `campaigns`, `queued_runs`, `embed_tokens`, `agent_triggers`, `external_credentials`, `webhook_deliveries`, `tools`, `knowledge_base_documents`, `knowledge_base_chunks`, `workflow_recordings` — every domain table hangs off `organization_id`, and `AGENTS.md` has a dedicated "Organization Scoping (Security)" section mandating org-id filtering on every read/write, i.e. **row-level multi-tenancy enforced by convention, not DB-level RLS** ([api/db/models.py](https://github.com/dograh-hq/dograh/blob/main/api/db/models.py), [api/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/AGENTS.md)). Migrations run via Alembic (100+ versioned files under [api/alembic/versions/](https://github.com/dograh-hq/dograh/tree/main/api/alembic/versions)).

**Background task/queue: ARQ, not Celery.** Confirmed by the `arq==0.26.3` dependency and the container entrypoint launching `python -m arq api.tasks.arq.WorkerSettings` ([scripts/start_services_docker.sh](https://github.com/dograh-hq/dograh/blob/main/scripts/start_services_docker.sh); root [AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/AGENTS.md): "Cache/Queue: Redis with ARQ for background tasks"). Tasks live in `api/tasks/`: `campaign_tasks.py`, `knowledge_base_processing.py`, `run_integrations.py`, `text_chat_inactivity.py`, `webhook_delivery.py`, `workflow_completion.py` ([api/tasks/](https://github.com/dograh-hq/dograh/tree/main/api/tasks)). ARQ worker count scales independently of FastAPI worker count via `ARQ_WORKERS` ([docs/deployment/scaling.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/scaling.mdx)).

**Routes vs. services convention:** routes stay HTTP-concern-only (`api/routes/`, e.g. `campaign.py`, `workflow.py`, `telephony.py`, `webrtc_signaling.py`, `agent_stream.py`, `public_embed.py`); all multi-step orchestration and business rules live in `api/services/<domain>/` (`auth/`, `call_concurrency/`, `campaign/`, `configuration/`, `gen_ai/`, `integrations/`, `pipecat/`, `telephony/`, `worker_sync/`, `workflow/`); background work in `api/tasks/`. "Do not create pass-through services solely to preserve a route → service → DB call chain" ([api/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/AGENTS.md)).

**Cross-worker state sync:** because multiple uvicorn worker processes run independently (not OS pre-fork), a `WorkerSyncManager` (`api/services/worker_sync/manager.py`) propagates in-memory state changes (e.g. cached credentials) to all workers via Redis pub/sub ([api/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/AGENTS.md)).

### 2.3 How Dograh uses Pipecat

**Pipecat is a git submodule pointing at a Dograh-owned fork (`dograh-hq/pipecat`), not upstream `pipecat-ai/pipecat`** — declared in `.gitmodules` ([`.gitmodules`](https://github.com/dograh-hq/dograh/blob/main/.gitmodules)). It is installed as a pip package from that local source with a large extras set: `pipecat[cartesia,deepgram,openai,elevenlabs,groq,google,azure,sarvam,soundfile,silero,webrtc,speechmatics,openrouter,camb,mcp,inworld,smallest,aws-nova-sonic]` ([api/Dockerfile](https://github.com/dograh-hq/dograh/blob/main/api/Dockerfile)). Code comments in `pipeline_builder.py` reference fork-specific, non-upstream APIs (`PipelineWorker`, `ProcessorUnusablePolicy`) and note "Pipecat 1.8 replaces `ErrorFrame.fatal` with processor usability plus a worker policy" while preserving "the fork's old fatal-error cancellation behavior" — strong evidence of an **actively-diverged, heavily customized fork**, not a thin wrapper ([api/services/pipecat/pipeline_builder.py](https://github.com/dograh-hq/dograh/blob/main/api/services/pipecat/pipeline_builder.py)).

**Pipeline construction per call** (`api/services/pipecat/run_pipeline.py`, `pipeline_builder.py`): entry points `run_pipeline_telephony(...)` (any telephony provider) and `run_pipeline_smallwebrtc(...)` (browser WebRTC) both register the call in `call_concurrency` bookkeeping, parse the pinned workflow run's JSON into a `WorkflowGraph`, resolve per-run STT/LLM/TTS (or a single realtime speech-to-speech provider), and build one of two pipeline shapes:

1. **Cascade (non-realtime) pipeline**: `transport.input() → termination_funnel → stt → [answer_supervisor] → user_context_aggregator → call_duration_processor → generation_stage (slot) → transport.output() → audio_buffer → assistant_context_aggregator → pipeline_metrics_aggregator`. The **generation stage is a "slot," not fixed processors** — the actual `llm → generation_callback_processor → [recording_router] → tts` chain runs inside a **separate `PipelineWorker` per agent "visit"** (one worker per node/agent the call transitions through), letting the engine swap the live agent/LLM+TTS combo on a node transition or handoff without tearing down the call-scoped transport, recording, or conversation context ([api/services/pipecat/pipeline_builder.py](https://github.com/dograh-hq/dograh/blob/main/api/services/pipecat/pipeline_builder.py)).
2. **Realtime (speech-to-speech) pipeline**: no separate STT/TTS stages; a single realtime LLM service (OpenAI Realtime, Gemini Live, Azure Realtime, Grok Realtime, AWS Nova Sonic, Ultravox) consumes audio directly ([api/services/pipecat/pipeline_builder.py](https://github.com/dograh-hq/dograh/blob/main/api/services/pipecat/pipeline_builder.py)).

**Transports:** WebRTC via Pipecat's `SmallWebRTCConnection`, used for the browser test-call experience, with signaling in `api/routes/webrtc_signaling.py` and TURN credentials from `api/routes/turn_credentials.py` + coturn ([api/services/pipecat/run_pipeline.py](https://github.com/dograh-hq/dograh/blob/main/api/services/pipecat/run_pipeline.py)). Telephony uses `FastAPIWebsocketTransport`, built per-provider — each telephony provider is a **self-registering plugin package** under `api/services/telephony/providers/<name>/` (`config.py`, `provider.py`, `transport.py`) registering a `ProviderSpec` into a central registry, so adding a provider is designed to touch only its own folder plus two lines elsewhere ([api/services/telephony/providers/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/services/telephony/providers/AGENTS.md)).

**Workflow → Pipecat runtime mapping:** the `PipecatEngine` class (`api/services/workflow/pipecat_engine.py`) is the bridge — it holds the `WorkflowGraph` (parsed from the React Flow JSON persisted per workflow), the call's `LLMContext`, and an `AgentRuntime` per "visit." Per node, `pipecat_engine_context_composer.py` builds the system prompt and available tool schema; edges are evaluated by the **LLM itself deciding to call a transition tool**, which the engine intercepts to advance the graph and spawn a fresh generation-stage `PipelineWorker` for the new node ([api/services/workflow/pipecat_engine.py](https://github.com/dograh-hq/dograh/blob/main/api/services/workflow/pipecat_engine.py)).

**`docs/core-concepts/how-dograh-works.mdx`** frames a "core loop": dashboard/API triggers a call → Dograh instructs the telephony provider to dial → on answer, a real-time audio pipeline opens → STT transcribes caller audio → transcript + active node's prompt + history go to the LLM → LLM response is synthesized by TTS and streamed back → when an edge condition is met the workflow transitions to the next node → on an end node the call ends → post-call, context is extracted, webhooks fire, and the run record (transcript, recording, extracted data, cost) is saved. Five "key components" are defined: Workflows (Agents), Runs, Telephony, Transcriber (STT), LLM Provider (also evaluates edge conditions), and Voice Synthesizer (TTS) ([docs/core-concepts/how-dograh-works.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/how-dograh-works.mdx)).

### 2.4 How calls are run and scaled

Calls are **not** container-per-call or subprocess-per-call — every call runs as an **async task set inside a long-lived FastAPI/uvicorn worker process**. The `api` container's entrypoint script runs several sibling processes under one supervisor with signal forwarding: (1) `alembic upgrade head` once at boot, (2) a singleton `ari_manager` process (optional, `ENABLE_ARI_MANAGER`), (3) a singleton `campaign_orchestrator` process (optional, `ENABLE_CAMPAIGN_ORCHESTRATOR`), (4) `FASTAPI_WORKERS` independent single-worker `uvicorn` processes each on its own port, and (5) `ARQ_WORKERS` independent ARQ worker processes ([scripts/start_services_docker.sh](https://github.com/dograh-hq/dograh/blob/main/scripts/start_services_docker.sh)). Within one uvicorn process, a call's Pipecat pipeline runs as an asyncio task tree owned by a `PipelineWorker`.

Per [docs/deployment/scaling.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/scaling.mdx): the API/WebSocket surface scales by adding more independent uvicorn **processes** (not `uvicorn --workers N` pre-fork, which would stick long-lived WebSockets to whichever worker first accepted them), load-balanced by nginx `least_conn` — chosen specifically because it distributes by live-connection count, which matters for long-lived voice WebSockets. `ari_manager` and `campaign_orchestrator` are **hard singletons regardless of worker count** (they hold global in-memory state: Asterisk channel registry, campaign dedup/scheduling locks). ARQ workers scale independently via `ARQ_WORKERS`. Guidance given: ~1 FastAPI worker per vCPU (capped at 8 unless profiled), ~300–500MB RAM/worker. Postgres/Redis/MinIO are each single-container in the compose path; production is expected to point at managed services instead.

**Concurrency limiting** (`api/services/call_concurrency/service.py`): `CallConcurrencyService` implements per-organization concurrent-call slots backed by Redis, not OS-level limits — `acquire_org_slot(...)` polls a Redis-backed counter bounded by the org's `CONCURRENT_CALL_LIMIT`, with an optional secondary "scope" counter (e.g. per-campaign) so one source can't starve another. Slot state maps to `workflow_run_id` so any process can release it on cleanup, and a fleet-wide active-call count backs an autoscale metric endpoint ([api/services/call_concurrency/service.py](https://github.com/dograh-hq/dograh/blob/main/api/services/call_concurrency/service.py)). This Redis-backed counter — not any in-process count — is what makes concurrency limits correct across N uvicorn processes and (in Helm) N pods.

### 2.5 Frontend tech stack

**Framework:** Next.js 15.3 with React 19 and TypeScript ([ui/package.json](https://github.com/dograh-hq/dograh/blob/main/ui/package.json); root [AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/AGENTS.md): "Frontend: Next.js 15 with React 19, TypeScript, Tailwind CSS"). **Styling:** Tailwind CSS v4 with shadcn/ui conventions (`shadcn-ui`, full Radix UI primitive set, `class-variance-authority`, `lucide-react`) — primitives live in `ui/src/components/ui/`. **Workflow canvas:** `@xyflow/react` (React Flow) v12 + `@dagrejs/dagre` for auto-layout, under `ui/src/components/flow/` and `workflow/`. **State:** `zustand` + `zundo` (undo/redo middleware, used for the flow editor's undo history). **API client:** fully **OpenAPI-generated** — `@hey-api/openapi-ts` fetches `${backendUrl}/api/v1/openapi.json` and emits a typed SDK (`client.gen.ts`, `sdk.gen.ts`, `types.gen.ts`) into `ui/src/client/`, not just types ([ui/openapi-ts.config.ts](https://github.com/dograh-hq/dograh/blob/main/ui/openapi-ts.config.ts)). **Auth:** dual-mode, built-in local email/password JWT or **Stack Auth** for social login, switched at runtime via `AUTH_PROVIDER` and discovered by the frontend from `/api/v1/health` — no rebuild required either way ([docs/deployment/authentication.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/authentication.mdx)). App Router route segments include `campaigns/`, `overview/`, `reports/`, `recordings/`, `telephony-configurations/`, `tools/`, `model-configurations/`, `billing/`, `automation/`, `files/`, `api-keys/`, `settings/`, `superadmin/` ([ui/src/app/](https://github.com/dograh-hq/dograh/tree/main/ui/src/app)).

### 2.6 Deployment model

Dograh is self-hosted-first, distributed as Docker images, with a managed cloud alternative at `app.dograh.com`. [docs/deployment/introduction.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/introduction.mdx) frames four paths: **Local Docker** (single machine, no public URL/telephony), **Remote server** (public server with free HTTPS via sslip.io + Let's Encrypt, no domain required), **Custom domain** (layered on a remote deployment), and **Heroku** — the last is listed but the docs page itself is a placeholder for a "coming soon" one-click path; no functioning Heroku deployment exists today ([docs/deployment/heroku.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/heroku.mdx)).

Local install: `curl` the root `docker-compose.yaml` + `start_docker.sh`, which auto-generates `.env` secrets and starts postgres/redis/minio/api/ui, served at `localhost:3010`, using direct peer-to-peer WebRTC by default (a `local-turn` profile adds coturn for NAT/VPN cases). Remote install: `setup_remote.sh` (root) provisions Docker, obtains a certificate automatically via sslip.io + Let's Encrypt for public IPs, and supports "prebuilt" (pull official images) vs. "build" (build from a clone/fork) modes. Documented minimum spec: 8GB RAM, 4 vCPUs, open ports TCP 80/443/3478/5349 and UDP 3478/5349/49152–49200 for WebRTC/TURN ([docs/deployment/docker.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/docker.mdx)). Images are published to `ghcr.io/dograh-hq` (default) and Docker Hub `dograhai`, selectable via a `REGISTRY` env var ([docker-compose.yaml](https://github.com/dograh-hq/dograh/blob/main/docker-compose.yaml)).

The **Helm chart** (§2.1) is the more production-grade, horizontally-scalable path — decomposed workloads, HPA, Gateway API/Ingress, external DB/Redis/S3 modes — versus the Compose path's single-container multi-process model, but is explicitly alpha and not yet cluster-validated by the maintainers ([deploy/helm/dograh/README.md](https://github.com/dograh-hq/dograh/blob/main/deploy/helm/dograh/README.md)).

**Architectural takeaway for a LiveKit-based competitor:** Dograh's real-time core is a deep, actively-diverged fork of Pipecat (its own `dograh-hq/pipecat` submodule), not a WebRTC-media-server-based architecture — calls are asyncio tasks inside long-lived FastAPI processes, scaled horizontally by adding more processes behind nginx `least_conn`, with Redis as the cross-process coordination substrate for concurrency slots and cache invalidation. This is a fundamentally different substrate than a LiveKit Agents design, where the SFU/room model and `AgentSession` give per-call isolation and horizontal scaling "for free" at the media layer — a LiveKit-native platform does not need to re-solve WebSocket-affinity load balancing or build a custom cross-worker pub/sub layer for state that LiveKit's room/participant model already scopes per call.

## 3. Complete feature inventory

### 3.1 Agent/workflow building

In the product, an "agent" is presented to the user; in the API, the same object is called a "workflow" — "workflow is the underlying definition, agent is the product name for it" ([docs/core-concepts/workflows-and-agents.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/workflows-and-agents.mdx)). A workflow is a **directed graph** of nodes connected by edges, built visually with **React Flow (`@xyflow/react` v12)** + `@dagrejs/dagre` auto-layout ([ui/package.json](https://github.com/dograh-hq/dograh/blob/main/ui/package.json)).

**Node types** ([docs/core-concepts/workflows-and-agents.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/workflows-and-agents.mdx); confirmed against the `NodeType` enum in `api/services/workflow/dto.py`):

| Node type | Purpose |
|---|---|
| `startCall` | Entry point for telephony calls — the first thing the agent says when a call connects |
| `agentNode` | An LLM-powered conversation step — the core building block, each with its own prompt |
| `globalNode` | Instructions that apply across all agent nodes (tone, language, fallback behavior) |
| `endCall` | Terminates the call |
| `trigger` | Entry point for API-triggered (non-telephony) runs |
| `webhook` | Fires an HTTP request when reached (CRM updates, notifications, etc.) |
| `qa` | Runs automated quality analysis on the completed call |

**Edges/transitions:** each edge carries a natural-language **condition** describing when to move on — the LLM itself evaluates whether the condition is met from the conversation so far (not a deterministic/rule-based condition engine); an optional `transition_speech` field lets the agent speak a line before moving to the next node ([docs/core-concepts/workflows-and-agents.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/workflows-and-agents.mdx)). The underlying schema is a `ReactFlowDTO` with `RFNodeDTO`/`RFEdgeDTO` — edges store free-text `condition` + `label` + `transition_speech`, i.e. conditions are **prompt text, not a structured boolean/variable expression language** (confirmed from `api/services/workflow/dto.py`).

**Prompts per node** and **global instructions** are authored directly in each node's editor panel; at runtime `pipecat_engine_context_composer.py` composes the system prompt and available tool schema per node from these fields (see §2.3).

**Variables and context:** `docs/core-concepts/context-and-variables.mdx` and the engine's `pipecat_engine_variable_extractor.py` handle extracting structured variables from the conversation (e.g. name, order ID) into a shared context object usable in later node prompts, webhooks, and post-call data — mirrored by a `TemplateContextVariablesDialog.tsx` and `MentionTextarea.tsx` (`@mention`-style variable insertion) in the node prompt editor ([ui/src/app/workflow/[workflowId]/components](https://github.com/dograh-hq/dograh/tree/main/ui/src/app/workflow/%5BworkflowId%5D/components)).

**Versioning:** every update to a workflow's `workflow_definition` saves a new version while retaining history; the current version is always what runs, and old versions are kept for audit ([docs/core-concepts/workflows-and-agents.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/workflows-and-agents.mdx)) — surfaced in the UI as `VersionHistoryPanel.tsx` + `WorkflowVersionDiffDialog.tsx` with a `workflowVersionDiff.ts` diffing utility.

**Two ways to create a workflow:** provide the full node/edge graph via the API ("from a definition"), or describe the use case in natural language and let an LLM generate the initial graph ("from a template") — the latter is also the flow shown in the README quickstart ("describe the use case in 5–10 words") ([docs/core-concepts/workflows-and-agents.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/workflows-and-agents.mdx); [README](https://github.com/dograh-hq/dograh/blob/main/README.md)).

### 3.2 Voice pipeline

**STT, LLM, and TTS providers** are abstracted behind a single `ServiceProviders(str, Enum)` in [`api/services/configuration/registry.py`](https://github.com/dograh-hq/dograh/blob/main/api/services/configuration/registry.py), read directly from source (34 active entries, one — `NEUPHONIC` — commented out): `OPENAI`, `ATLASCLOUD`, `DEEPGRAM`, `GROQ`, `OPENROUTER`, `INWORLD`, `CARTESIA`, `ELEVENLABS`, `GOOGLE`, `AZURE`, `AZURE_SPEECH`, `DOGRAH`, `SARVAM`, `SPEECHMATICS`, `CAMB`, `AWS_BEDROCK`, `SPEACHES`, `HUGGINGFACE`, `ASSEMBLYAI`, `GLADIA`, `RIME`, `MINIMAX`, `GOOGLE_VERTEX`, `OPENAI_REALTIME`, `GROK_REALTIME`, `ULTRAVOX_REALTIME`, `GOOGLE_REALTIME`, `GOOGLE_VERTEX_REALTIME`, `AZURE_REALTIME`, `AWS_NOVA_SONIC`, `SMALLEST`, `XAI`, `LMNT`, `SPEECHIFY`. Per-category documentation ([docs/configurations/transcriber.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/transcriber.mdx), [voice.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/voice.mdx), [llm.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/llm.mdx)) states the provider sets exposed in the UI, which is a subset/framing of the same enum:
- **STT ("Transcriber")**: Deepgram, OpenAI, Google, Azure Speech, AssemblyAI, Speechmatics, Cartesia, Gladia, Sarvam, Smallest AI, Hugging Face, ElevenLabs, and Dograh-managed; plus **Speaches** (a self-hosted, OpenAI-API-compatible server) for locally-deployed/self-hosted STT models.
- **TTS ("Voice")**: ElevenLabs, OpenAI, Google, Azure Speech, Deepgram, Cartesia, Smallest AI, MiniMax, Sarvam, Rime, Inworld, Camb.ai, xAI, LMNT, Speechify, and Dograh-managed; plus Speaches for self-hosted TTS.
- **LLM**: OpenAI, Google AI Studio, Google Vertex AI, Azure OpenAI, AWS Bedrock, Groq, OpenRouter, Hugging Face, MiniMax, Sarvam, and Dograh-managed; plus any OpenAI-compatible endpoint (explicitly including self-hosted **Ollama** and **vLLM**) via a configurable Base URL — the same mechanism used for xAI/Grok or proxies per issue #527.
- **Realtime / speech-to-speech models** (bypass separate STT/TTS, per the registry's dedicated `*_REALTIME`/`AWS_NOVA_SONIC` entries and `api/services/pipecat/realtime/` modules): OpenAI Realtime, Google (Gemini) Realtime, Google Vertex Realtime, Azure Realtime, Grok Realtime, AWS Nova Sonic, and Ultravox Realtime.

**VAD and turn detection** is a three-tier, per-provider-selectable design (`run_pipeline.py`'s `_create_realtime_user_turn_config` / `_create_non_realtime_user_turn_*_strategies`, see §2.3), and is also documented end-user-facing at [docs/configurations/interruption.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/interruption.mdx):
1. **Local Silero VAD**, run by default at a pipeline-wide sample rate capped to 8000 Hz or 16000 Hz (no other value accepted) — this is what makes barge-in possible: the moment it detects the caller talking, the bot's speech is cut and the pipeline processes the new input ([docs/configurations/interruption.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/interruption.mdx)).
2. **`LocalSmartTurnAnalyzerV3`** — a semantic turn-completion classifier (Pipecat's "smart turn" concept), used to reduce false interruptions on mid-thought pauses (**UNVERIFIED** whether it is itself LLM-based vs. a smaller dedicated classifier model — not confirmed from primary source in this pass).
3. **STT-native external turn signals** — for STT providers that emit their own end-of-turn events (e.g. Deepgram Flux's `eot_threshold`/`eager_eot_threshold`/`eot_timeout_ms`, currently hardcoded per open issue #688) — v1.47.0 shipped "let external-turn STT decide the turn start, retire provisional_vad" ([v1.47.0 release notes](https://github.com/dograh-hq/dograh/releases/tag/dograh-v1.47.0)), i.e. Dograh is actively moving turn-taking authority toward STT-native signals where available.
4. For **realtime/speech-to-speech providers**, VAD/turn detection is delegated to the provider itself — the docs explicitly name OpenAI Realtime, Azure Realtime, and "Grok Voice Agent" as supplying their own VAD signals, so local Silero VAD is skipped for those calls ([docs/configurations/interruption.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/interruption.mdx)). This isn't always well-tuned: open issue #687 asks to expose `GeminiVADParams` for `google_vertex_realtime` because "short utterances go unanswered for 10-20s."

**Interruption ("Allow Interruption") is configured per node, not globally** — each node in the workflow has its own toggle; disabled (the default) means the bot finishes its entire response and the user's mic is muted while it speaks, useful for legal disclaimers or confirmation read-backs; enabled lets the caller barge in naturally, useful for Q&A/objection-handling nodes ([docs/configurations/interruption.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/interruption.mdx)). Known rough edges include closed issue #296 ("Doesn't let me interrupt") and open issue #750 ("Realtime LLMs — user-idle disconnect hangs up before the farewell is spoken").

**Latency features:** an "answer supervisor" that begins listening/processing before or during the initial greeting (v1.47.0: "enhance answer supervisor to listen even when playing initial greeting," the most recent commit on `main` at research time — [commit 17abfb5e](https://github.com/dograh-hq/dograh/commit/17abfb5e)); a "generation stage" pipeline-worker-per-visit design that lets the engine pre-build/swap the next agent's LLM+TTS chain without tearing down the call-scoped transport (see §2.3); and the marketing site's claimed (**UNVERIFIED in source**) "2x conversion" feature that blends pre-recorded human voice clips with synthesized speech to cut latency/cost.

### 3.3 Telephony

Telephony is unified behind a single configuration model: "the same configuration powers both outbound calls (initiated from Dograh) and inbound calls (received on a phone number you own)" and "Dograh does not sell phone numbers or minutes... the phone service is always yours" ([docs/integrations/telephony/overview.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/overview.mdx)).

**Supported providers**, each a self-registering plugin under `api/services/telephony/providers/<name>/` implementing `config.py`/`provider.py`/`transport.py` against a central `ProviderSpec` registry ([api/services/telephony/providers/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/services/telephony/providers/AGENTS.md)). The provider directory as shipped on `main` at research time contains exactly eight packages ([api/services/telephony/providers/](https://github.com/dograh-hq/dograh/tree/main/api/services/telephony/providers)):
- **Carrier-API providers**: Twilio (TwiML, HMAC webhook signing), Vonage (JWT auth, 16kHz PCM, NCCO), Plivo, Telnyx (call-control REST — several 2026-09 open bugs around its webhook/status-callback handling, e.g. #778–#781), Vobiz, Exotel (India-focused, "Connect Voice AI" streaming).
- **Bring-your-own-SIP / PBX**: Cloudonix (every organization is auto-provisioned a "Dograh Cloudonix SIP" connection giving a SIP domain and inbound endpoint already wired to the voice pipeline — the customer still supplies their own carrier trunk or PBX and phone numbers; Dograh "does not sell or resell phone numbers" — [docs/integrations/telephony/dograh-sip.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/dograh-sip.mdx)) and **Asterisk ARI** for self-hosted PBX/SIP — a WebSocket/Stasis-application integration run by a standalone singleton `ari_manager` process, requiring specific Asterisk modules (`chan_websocket`, `res_websocket_client`) and a 3-step cross-system setup ([docs/integrations/telephony/asterisk-ari.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/asterisk-ari.mdx)).
- A documented path to **build a custom provider integration**, built on Pipecat's `FastAPIWebsocketTransport` and requiring only 2 edits outside the new provider's own folder ([docs/integrations/telephony/custom.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/custom.mdx)). Several community members have opened PRs against this extension point for additional carriers — VoxPro, TryVox, PAPI, Tata Smartflo — but **all four were closed unmerged** as of this research (confirmed via the GitHub API: `merged: false` on PRs #595, #594, #670, #731); none of these providers ship on `main`. The extension point is real and documented, but "community-contributed providers shipping in the product" would currently be an overstatement.

**Configuration UI:** a single `/telephony-configurations` screen — add a configuration, select provider, enter credentials, add phone number(s), optionally assign an **Inbound workflow** to a number. One org can hold multiple configurations (e.g. separate Twilio sub-accounts) and mark one as **default outbound** for test calls/campaigns ([docs/integrations/telephony/overview.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/overview.mdx)).

**Inbound calling** uses a single org-wide webhook URL (`/api/v1/telephony/inbound/run`); Dograh resolves the organization from the webhook's account credentials and picks the agent from the called number's Inbound-workflow assignment — all 8 providers support inbound this way, sharing the same telephony configuration as outbound ([docs/integrations/telephony/overview.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/overview.mdx); [docs/integrations/telephony/inbound.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/inbound.mdx)).

**Campaigns / outbound dialer:** a first-class feature — a campaign runs "a workflow against many contacts automatically," uploading a contacts CSV (must have a `phone_number` column; any extra columns become per-call `initial_context`/template variables), then dialing "respecting scheduling windows, concurrency limits, and retry rules," with live progress (processed/completed/failed/pending) and pause/resume ([docs/core-concepts/campaigns.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/campaigns.mdx)). In the UI: `campaigns/` list, create, edit with CSV contact upload (`CsvUploadSelector.tsx`) and advanced pacing/retry settings (`CampaignAdvancedSettings.tsx`), backed by `api/routes/campaign.py` and a `CampaignModel` ([ui/src/app/campaigns](https://github.com/dograh-hq/dograh/tree/main/ui/src/app/campaigns)). Campaign execution runs through a singleton `campaign_orchestrator` process plus ARQ tasks (`api/tasks/campaign_tasks.py`), gated by the same per-organization `CallConcurrencyService` Redis slots used for all calls (see §2.4) — v1.47.0 shipped "refactor campaign dispatcher to handle higher concurrency," and an open issue (#745) reports the dispatcher "leaks concurrent-call slots when the arq batch job is cancelled (job_timeout), stalling campaigns," i.e. this subsystem is still maturing.

**Call transfer — two distinct tools, not one, with different scope:**
- **Call Transfer** (`TransferCallToolConfig`) — transfers to an external phone number or SIP endpoint, resolved via a static/templated destination, ordered context-value-to-destination mapping rules, or a dynamic HTTP resolver called at transfer time. It is a **blind transfer only** — "Dograh does not currently pass conversation context to the receiving human" — and is available **only on telephony calls using Twilio, Telnyx, or Asterisk ARI** ("Web calls do not support call transfer") ([docs/voice-agent/tools/call-transfer.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/tools/call-transfer.mdx)) — notably **not** Vonage, Plivo, Cloudonix, Vobiz, or Exotel.
- **Transfer to Agent** (`TransferAgentToolConfig`, shipped in v1.47.0) — hands the caller to a *different Dograh agent* (by `workflow_id`) without dropping the call: a **warm** transfer that compacts the conversation so far into a handover note plus verbatim recent turns, so "the caller never repeats themselves." It works on "any cascade call, including web calls," but is explicitly **not available on speech-to-speech (realtime) agents** — the tool registers but refuses and tells the model to keep helping the caller itself rather than failing silently ([docs/voice-agent/tools/transfer-agent.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/tools/transfer-agent.mdx)).

**Voicemail detection is a real, fairly sophisticated shipped feature, not just an aspiration.** A design doc in source (`api/voicemail_handling.md`) describes classifying, while the initial greeting is still playing, whether the far end is a **voicemail system**, a **human call-screener** (e.g. an assistant/screening service that itself plays a message before connecting), or a **live conversation** — with different agent behavior per case (leave a pre-configured voicemail message and drop; say a short screening line and wait for the phone to actually ring; or proceed normally) — and explicitly handles the edge case of a human picking up mid-voicemail-or-screener-message ([api/voicemail_handling.md](https://github.com/dograh-hq/dograh/blob/main/api/voicemail_handling.md)). This is implemented as part of the "answer supervisor" (the same subsystem enhanced in the most recent commit on `main`, [17abfb5e](https://github.com/dograh-hq/dograh/commit/17abfb5e)) and has dedicated tests (`test_answer_classification.py`, `test_answer_supervisor*.py`). It is real, tested code — but still has open production reliability issues (open issue #777, "Voicemail Detection and Audio Interferences in real Phone Calls").

**DTMF is only partially implemented.** Asterisk ARI receives and logs inbound DTMF digit events from the PBX channel (`api/services/telephony/ari_manager.py`), but a general-purpose **DTMF-input tool exposed to workflow builders does not exist yet** — the tool-type enum in `api/enums.py` lists `NATIVE = "native"  # Built-in integrations (future: dtmf_input)`, i.e. DTMF-as-a-workflow-tool is explicitly marked as a future item, not a shipped capability, as of this research.

### 3.4 Web/WebRTC calling and embeddable widget

The browser-based **Test Audio** experience runs over WebRTC via Pipecat's `SmallWebRTCConnection`, with Dograh's own signaling (`api/routes/webrtc_signaling.py`) and TURN credentialing (`api/routes/turn_credentials.py`) backed by a bundled coturn server (see §2.1, §2.3). The **embeddable widget** is configured from the agent's own settings (gear icon → Add to Website → Configure Widget) and offers two independent choices ([docs/voice-agent/add-to-website.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/add-to-website.mdx)):
- **Widget type** — **Voice** (a live WebRTC audio call, microphone required, HTTPS/localhost only) or **Chat** (text messages, no microphone; a chat session lasts up to 1 hour, offers a "Start new chat" button on expiry, and does not persist history across page reloads — each conversation still lands in the agent's call history with a full transcript, and counts once against the embed token's usage limit, same as a voice call).
- **Embed mode** — **Floating Widget** (a corner CTA button/panel), **Inline Component** (renders into a page-supplied `<div id="dograh-inline-container">`), or **Headless** (no UI at all — just the audio/chat pipeline plus a `window.DograhWidget` JavaScript API for a fully custom UI). All three modes support both widget types.

Embedding is domain-restricted via an **Allowed Domains** allowlist (empty = allow all) and requires HTTPS (or `localhost`) for voice widgets, since browsers refuse microphone access on plain HTTP/`file://` origins. The backend has dedicated routes (`public_embed.py`, `public_embed_chat.py`, `workflow_embed.py`) and a UI `EmbedDialog.tsx` for generating the deployment `<script>` snippet; widget assets are served from `ui/public/embed/` as `dograh-widget.js`, loaded asynchronously.

### 3.5 Tools and integrations

**Function/tool calling** is native to the workflow engine — `pipecat_engine_custom_tools.py` and `services/workflow/tools/` implement a calculator, custom HTTP tool, knowledge-base RAG tool, MCP tool, timezone tool, and a transfer resolver, each composed into the per-node function schema the LLM can call (see §2.3). In the UI, tools are managed at `/tools` with per-type config components: `BuiltinToolConfig`, `HttpApiToolConfig` (+ an `HttpToolTestDialog` for live-testing a webhook before saving), `TransferCallToolConfig`, `TransferAgentToolConfig`, `EndCallToolConfig` ([ui/src/app/tools](https://github.com/dograh-hq/dograh/tree/main/ui/src/app/tools); [docs/voice-agent/tools/introduction.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/tools/introduction.mdx), [docs/voice-agent/tools/http-api.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/tools/http-api.mdx)). HTTP tool authentication supports `NONE`, `API_KEY`, `BEARER_TOKEN`, `BASIC_AUTH`, `CUSTOM_HEADER` credential types ([api/routes/credentials.py](https://github.com/dograh-hq/dograh/blob/main/api/routes/credentials.py)) — though open issue #633 notes "Webhook node has no way to sign/authenticate outbound requests without a plaintext secret in workflow source," and issue #612 (merged) added OAuth2 Client Credentials support.

**MCP — both directions:**
- **As a tool source (client)**: an "MCP Tool" (a *tool* type attachable to a node, not a distinct `NodeType` — the `NodeType` enum itself is only `startCall`/`endCall`/`agentNode`/`globalNode`/`trigger`/`webhook`/`qa`, confirmed directly from `api/services/workflow/dto.py`) lets a running agent call out to an external MCP server's tools mid-conversation over authenticated **Streamable HTTP**. Configuration is name/description/URL/credential plus an optional per-server tool filter. At runtime: Dograh opens one live MCP session per attached server per call, exposes only the tools allowed by the server- and node-level filters as ordinary namespaced LLM function definitions (so they coexist safely with HTTP tools, transfer, end-call, etc.), and the LLM "sees only the tool name, description, and argument schema" — never the credential secret ([docs/voice-agent/tools/mcp-tool.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/tools/mcp-tool.mdx)).
- **As a server (Dograh exposing itself)**: `api/mcp_server/` runs a `fastmcp`-based MCP server (`fastmcp==3.2.4` dependency) authenticated via API key/Bearer token, exposing workflow-editing tools so external coding agents (Claude Code, Codex, Cursor) can "inspect existing agents, search Dograh docs, fetch node schemas, create new workflows, and save draft edits from natural language" ([README](https://github.com/dograh-hq/dograh/blob/main/README.md); [docs/integrations/mcp.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/mcp.mdx); [api/mcp_server/server.py](https://github.com/dograh-hq/dograh/blob/main/api/mcp_server/server.py)). This is reinforced by an installable `dograh-hq/dograh-plugins` Claude Code/Codex plugin that runs Dograh's own setup scripts end-to-end.

**Knowledge base / RAG:** documents (PDF, DOCX/DOC, TXT, or JSON; 5 MB max) are uploaded at "Knowledge Base Files" (`DocumentUpload.tsx`, `DocumentList.tsx`) and processed under one of **two retrieval modes chosen per document**: **Full Document** (the entire text is handed to the agent on every query — no chunking/embedding, no embedding API key required; best for menus, price lists, FAQs, short reference sheets) or **Chunked Search** (the document is split and indexed with vector embeddings, and only the most relevant chunks are returned per query; best for large policies/manuals/contracts) ([docs/voice-agent/knowledge-base.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/knowledge-base.mdx)). Chunked Search documents are stored as `KnowledgeBaseDocumentModel`/`KnowledgeBaseChunkModel` rows, embedded via `api/services/gen_ai/embedding/` (OpenAI, Azure OpenAI, or a Dograh-managed embedding service), and queried with **pgvector** on Postgres (`pgvector/pgvector:pg17` image; `pgvector==0.4.2` dependency) using an **ivfflat** index. Documents are then attached to one or more workflow nodes. This is a real production rough edge, not a theoretical one: open issue #635 reports "KB vector search recall silently collapses on small corpora — ivfflat index built on empty table + default probes=1" (affecting Chunked Search specifically), and issue #634 reports the plain-text ingestion path "mangles Japanese text (dakuten stripped, kanji dropped)" while `.docx` ingestion of the same content is intact.

**Other integrations** are implemented as first-class "packs" under `api/services/integrations/` — dedicated `noveum/`, `tuner/`, and `paygent/` subpackages, each contributing its own dynamically-mounted router (`all_routers()` in `api/routes/main.py`) and its own node type in the flow canvas (mirrored in `sdk/typescript/src/typed/noveum.ts`, `tuner.ts`, `paygent.ts`) ([api/services/integrations](https://github.com/dograh-hq/dograh/tree/main/api/services/integrations)). **Paygent** is a third-party usage-based billing platform built specifically for AI voice agents: Dograh passively calculates per-call multimodal token usage and audio duration and exports it to Paygent after every call, where the operator's own rate cards convert that into an invoice line for their end customer — aimed at teams reselling voice agents as a service who don't want to build margin-tracking infrastructure themselves ([docs/integrations/paygent.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/paygent.mdx)). Noveum and Tuner are LLM-observability/tracing-adjacent third-party integrations (per their `docs/images/` screenshot names — `noveum-trace-detail.png`, `tuner-agent-settings.png`), each with its own dashboard panel akin to the Langfuse integration in §3.7; not read in full detail in this pass, flagged **UNVERIFIED beyond this characterization**. No dedicated first-party CRM connectors (Salesforce/HubSpot) were found — CRM sync is done generically via the HTTP/webhook tool.

**Webhooks:** a generic outbound-webhook mechanism (the `webhook` node type, plus post-call `webhook_delivery.py` ARQ task) lets any node or run-completion event push data to an external URL, with the same credential types as HTTP tools ([docs/developer/webhooks.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/developer/webhooks.mdx), [docs/getting-started/send-call-data-with-webhooks.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/getting-started/send-call-data-with-webhooks.mdx)).

### 3.6 Testing and evaluation

The primary testing surface is a **Test Agent** panel with two modes, per the README quickstart: **Test Audio** (browser voice call over WebRTC) and **Test Chat** (text-only, faster iteration) — "In Test Chat, you can edit or replay user turns and Dograh will regenerate the agent's replies and node transitions from that point" ([README](https://github.com/dograh-hq/dograh/blob/main/README.md)). In the UI this is `WorkflowTesterPanel.tsx`, with `EmbeddedVoiceTester.tsx` for audio and `ManualTextChatPanel.tsx` + `ChatComposer.tsx` + `useTextChatSession.ts` for text, backed by a `workflow_text_chat.py` route and `WorkflowRunTextSessionModel` — meaning a workflow can be exercised as text chat, not only as a phone call. Notably, the UI also contains an `AiSimulatorPlaceholder.tsx` component — an **AI-driven caller simulator that appears to be planned/upcoming rather than shipped** (a placeholder, not a working feature) as of this research date.

`evals/` at the repo root contains an **STT evaluation harness** (`evals/stt/`, with `providers/`, `audio/`, `results/` subfolders) and a separate `evals/visualizer/` (a small web app, `public/`+`src/`) for viewing STT eval results — this is an internal benchmarking tool for comparing STT provider accuracy/latency, not a customer-facing simulated-call or LLM-as-judge test suite.

The **`qa` node** is the closest thing to an automated evaluation feature exposed to end users, and is more developed than a single grading pass: it runs an **LLM quality review on the call transcript strictly post-call** — "it is not part of the live call flow," has no edges, and cannot connect to any other node (builders typically place it off to the side on the canvas as a standalone evaluator that runs automatically for every eligible call once published) ([docs/voice-agent/qa.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/voice-agent/qa.mdx)). Its configuration is a single freeform **System Prompt** to the reviewer LLM; the default prompt already covers: a **tag set** (`DEAD_AIR`, `USER_FRUSTRATED`, `ASSISTANT_IN_LOOP`, `ASSISTANT_REPLY_IMPROPER`, `USER_NOT_UNDERSTANDING`, `HEARING_ISSUES`, `UNCLEAR_CONVERSATION`, `USER_REQUESTING_FEATURE`, `ASSISTANT_LACKS_EMPATHY`, `USER_DETECTS_AI`), a **1–10 call quality score**, **sentiment** (positive/neutral/negative), and a short **summary** — and can be fully replaced with a domain-specific rubric (the docs give a debt-collection compliance-review example returning custom structured JSON fields). Results are surfaced in webhook payloads as an `annotations` object ([docs/developer/webhooks.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/developer/webhooks.mdx)). This is a real, reasonably well-designed LLM-as-judge primitive — but open issue #636 reports "QA grader returns empty results — grade JSON truncated on Google/Gemini models," indicating some fragility in the implementation. There is no dedicated **multi-scenario regression-testing or simulated-adversarial-caller product surface** comparable to a Hamming/Cekura-style eval platform — pre-call testing is limited to a human manually driving Test Audio/Test Chat, not automated scenario coverage. This is a **notable gap** relative to what a production voice-agent team typically wants (see §5, §7).

### 3.7 Analytics and observability

**Call logs, recordings, transcripts:** every call produces a "Run" record holding transcript, recording, extracted data, and cost ([docs/core-concepts/how-dograh-works.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/how-dograh-works.mdx); [docs/core-concepts/calls-and-runs.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/core-concepts/calls-and-runs.mdx)). Recordings are stored in MinIO/S3 (bucket `voice-audio`); a post-call **conversation timeline** UI renders the transcript with tool calls and node transitions inline (`ConversationTimeline.tsx`, `MessageBubble.tsx`, `ToolCallCard.tsx`, `NodeTransitionMarker.tsx`, `RealtimeFeedback.tsx` — [ui/src/components/workflow/conversation](https://github.com/dograh-hq/dograh/tree/main/ui/src/components/workflow/conversation)), and a live-call monitoring view exists at `workflow/[workflowId]/run/[runId]/` with connection status, audio controls, and live context-variable display.

**Dashboards:** a `/reports` screen with `DurationChart.tsx`, `DispositionChart.tsx`, and `MetricsCards.tsx` provides call-volume, duration, and disposition-breakdown analytics ([ui/src/app/reports](https://github.com/dograh-hq/dograh/tree/main/ui/src/app/reports)); a `superadmin/runs/` screen gives operators a cross-org runs view.

**Cost tracking:** run records include cost; `/billing` and `/usage` pages surface organization-level credit/usage data via generated SDK calls (e.g. `getBillingCreditsApiV1OrganizationsBillingCreditsGet`).

**Tracing:** Dograh has its **own built-in trace viewer**, not just a Langfuse pass-through — after a call, a "Traces" tab on the call summary screen shows STT entries (transcribed user speech), LLM entries (the full combined global+node prompt, conversation history, available tools for that node, and the model's response), and tool-call request/response pairs; available tools are further broken into System Tools (a default calculator, get-current-time, convert-time), Pathway Tools (the node's configured transitions), and Custom Tools ([docs/configurations/tracing.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/tracing.mdx)). **Langfuse** is offered as an optional, additive integration on top of this — "tracing is automatically active when credentials are available" (no separate enable flag needed once host/keys are set, either per-organization in Settings or via environment variables for a self-hosted default), and works on both managed and self-hosted deployments. A `LANGFUSE_TRACES_PUBLIC`/per-org "Make traces publicly viewable" toggle controls whether trace URLs are viewable without a Langfuse login (default private) ([docs/configurations/tracing.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/tracing.mdx)) — though open issue #658 argues traces "should be private or behind an environment variable," suggesting some confusion among users about the default. Also **Prometheus + Grafana**: the API exposes `/api/v1/metrics` (guarded by a devops-secret header), scraped by a bundled Prometheus and visualized in a bundled Grafana dashboard JSON ([deploy/observability/](https://github.com/dograh-hq/dograh/tree/main/deploy/observability)). **OpenTelemetry**: the most recent merged PR in the repo at research time is "feat: expose OTEL endpoint for telemetry" ([commit 9933b880](https://github.com/dograh-hq/dograh/commit/9933b880), 2026-09-17) — i.e. general-purpose OTEL export (distinct from the Langfuse-specific path) is a brand-new, still-landing capability, not a mature feature. Error reporting uses **Sentry** (`sentry-sdk[fastapi]`, `@sentry/nextjs`). Product analytics/telemetry uses **PostHog**, enabled by default (`ENABLE_TELEMETRY=true`) and opt-out via an env var — this is anonymous usage telemetry sent to Dograh, not customer-facing observability.

### 3.8 Multi-tenancy, auth, RBAC, API keys

**Multi-tenancy** is real and organization-scoped: an `OrganizationModel` plus a many-to-many `organization_users_association` table (just `user_id`/`organization_id`, no role column), and nearly every resource table (`WorkflowModel`, `CampaignModel`, `TelephonyConfigurationModel`, `ExternalCredentialModel`, `ToolModel`, `KnowledgeBaseDocumentModel`, `APIKeyModel`, etc.) carries `organization_id` with per-org unique constraints. `api/AGENTS.md` mandates org-id filtering on every read/write as a named security invariant ("Organization Scoping (Security)") (all: [api/db/models.py](https://github.com/dograh-hq/dograh/blob/main/api/db/models.py), [api/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/AGENTS.md)).

**Auth** is pluggable via a backend `AUTH_PROVIDER` env var, switchable at runtime with no rebuild:
1. **Local** (default) — built-in email/password with a signed JWT, no external dependency; gated to prevent hosted/cloud deployments from accidentally accepting local-style signups.
2. **Stack Auth** (`AUTH_PROVIDER=stack`) — delegates social login (Google, GitHub, etc.) to the third-party Stack Auth service; only the server key is a genuine secret, and the frontend discovers the public Stack project config at runtime from `/api/v1/health`. In Stack mode, "organization" maps 1:1 to a Stack "team," and only Stack-mode deployments get a visible org-switcher UI (`SidebarTeamSwitcher.tsx` renders `null` otherwise) — **local-auth users have no visible multi-org switching affordance even though the schema supports multi-org membership** (all: [docs/deployment/authentication.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/deployment/authentication.mdx), [api/services/auth/depends.py](https://github.com/dograh-hq/dograh/blob/main/api/services/auth/depends.py), [ui/src/components/layout/SidebarTeamSwitcher.tsx](https://github.com/dograh-hq/dograh/blob/main/ui/src/components/layout/SidebarTeamSwitcher.tsx)).

**API keys** are a third auth path for programmatic access (`X-API-Key` header, checked before JWT/Stack). Keys are generated as `secrets.token_urlsafe(32)` with a `dgr_` prefix and stored as a SHA-256 hash plus an 8-character display prefix — the raw key is never persisted ([api/utils/api_key.py](https://github.com/dograh-hq/dograh/blob/main/api/utils/api_key.py), [api/db/models.py](https://github.com/dograh-hq/dograh/blob/main/api/db/models.py)). Lifecycle: list/create, archive (immediate revocation), reactivate ([docs/api-reference/api-keys.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/api-reference/api-keys.mdx)) — closed issue #303 ("Can't change/delete Dograh Service Keys") suggests this UX had rough edges historically.

**RBAC: absent beyond a single global superuser flag.** No role model (owner/admin/member/viewer) or fine-grained permission system was found in `api/db/` or `api/services/auth/` — every member of an organization has equal access to that org's resources. The only privilege distinction is `UserModel.is_superuser`, a platform-wide (not per-org) flag gating a superuser API surface (`api/routes/superuser.py`) that includes a cross-org runs viewer and a real **impersonation endpoint** (`POST /superuser/impersonate`, minting live access/refresh tokens for another user by ID or email) — a support/debug tool with meaningful security weight and no per-org RBAC to fall back on.

**Public REST API:** versioned at `/api/v1`, JSON in/out, consistent error shape, `X-API-Key` auth ([docs/api-reference/overview.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/api-reference/overview.mdx)). Resource surface (from `api/routes/main.py`'s router mounts): `telephony`, `workflow`, `workflow_text_chat`, `campaign`, `credentials`, `tool`, `organization`, `service_keys`, `organization_usage`, `reports`, `webrtc_signaling`, `turn_credentials`, `public_embed`(+chat), `public_agent`, `public_download`, `workflow_embed`, `knowledge_base`, `workflow_recording`, `folder`, `auth`, `node_types`, `agent_stream`, `superuser`, plus dynamically-mounted integration routers (Tuner, Noveum, Paygent). Documented CRUD coverage spans Agents (list/get/count/create-from-template/create-from-definition/update/archive/validate + nested runs), Campaigns (list/create/get/update/upload-contacts/start/pause/resume/progress/runs), Runs (trigger/trigger-workflow/get/list/download/inbound), Telephony Configs (+ nested phone-numbers), and API Keys.

**A distinctive SDK-exposure pattern:** not every FastAPI route is public SDK surface. Routes opt in via an `sdk_expose()` helper that stamps `openapi_extra={"x-sdk-method": ...}` on the route; `sdk/codegen/client_codegen.py` walks a filtered OpenAPI dump (only `x-sdk-method`-tagged operations) to emit typed method stubs for **both** SDKs, with request/response models generated separately via `datamodel-codegen` (Python) and `openapi-typescript` (TypeScript) — giving Dograh a deliberately small, auditable public SDK surface distinct from its full internal API ([api/sdk_expose.py](https://github.com/dograh-hq/dograh/blob/main/api/sdk_expose.py), [sdk/codegen/client_codegen.py](https://github.com/dograh-hq/dograh/blob/main/sdk/codegen/client_codegen.py)).

**SDKs:** official `dograh-sdk` (PyPI, v0.1.8 at research time, 9 releases) and `@dograh/sdk` (npm, v0.1.7, 7 releases) — both generated from the same backend OpenAPI spec ([PyPI](https://pypi.org/project/dograh-sdk/), [npm](https://www.npmjs.com/package/@dograh/sdk); [docs/sdks/introduction.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/sdks/introduction.mdx)). They let you construct a `Workflow` object, `.add()` typed nodes, `.edge()` them with label/condition, and `save_workflow`/`load_workflow` drafts without disrupting live traffic, with node types/specs discoverable at runtime via `list_node_types()` ([docs/sdks/build-an-agent.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/sdks/build-an-agent.mdx)); outbound calls are triggered via `client.test_phone_call(...)`, the same endpoint behind the UI's "Test Call" button, with bulk calling steered toward Campaigns rather than looping single calls ([docs/sdks/outbound-calls.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/sdks/outbound-calls.mdx)).

### 3.9 Credential/provider management in the UI

Provider/model credentials live at **`/model-configurations`** ("Models" in the sidebar) — not under `/settings`. Three modes, each organization-scoped with per-agent override toggles (LLM/Voice/Transcriber independently) ([docs/configurations/inference-providers.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/inference-providers.mdx)):
1. **Speech to Speech** — pick a realtime model; a separate non-realtime LLM is still required for variable extraction/QA.
2. **Dograh** — a single Dograh-issued **Service Key** unlocks Dograh-managed LLM/Voice/Transcriber providers (no separate BYOK credentials needed).
3. **BYOK** — separate LLM / Voice / Transcriber / Embedding tabs, each with provider, model, optional Base URL (for OpenAI-compatible endpoints), and API key; provider-specific fields appear conditionally (e.g. an ElevenLabs voice ID field). The docs carry an explicit warning that BYOK forwards prompts/transcripts/audio/tool data to the chosen third-party provider under that provider's own data policy.

Two separate key concepts exist at `/api-keys` (Developers screen): **API Keys** (trigger agents from external systems) and **Service Keys** (authenticate against Dograh-managed inference providers specifically, portable between self-hosted and cloud but billed to the owning cloud account) ([docs/configurations/api-keys.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/configurations/api-keys.mdx)).

**Encryption-at-rest — a significant, verifiable gap.** `ExternalCredentialModel.credential_data` is documented in a code comment as "Encrypted credential data (JSON)" but is declared as a plain `Column(JSON, nullable=False, default=dict)` with no encryption library anywhere in the codebase (`grep`-verified absence of `encrypt|fernet|cipher|aesgcm|cryptography|pgcrypto|nacl` usage on credential paths) ([api/db/models.py](https://github.com/dograh-hq/dograh/blob/main/api/db/models.py)). BYOK provider keys follow the same plain-JSON pattern via `OrganizationConfigurationClient.upsert_configuration`. The only protection is **response-time masking** — `api/services/configuration/masking.py` truncates secrets to their last 4 characters when returning config to the client, and rejects "updates" that just resubmit the masked placeholder ([api/services/configuration/masking.py](https://github.com/dograh-hq/dograh/blob/main/api/services/configuration/masking.py)). In short: **provider and webhook credentials appear to be stored in plaintext in Postgres**, with masking applied only on the way out — this is a concrete, verifiable area where our platform's encrypted-credential design is already ahead. By contrast, Dograh's own platform API keys *are* handled correctly (SHA-256 hash + short prefix only, never the raw key).

### 3.10 Anything else distinctive

- **Dograh setup skill/plugin for coding agents** — an installable `dograh-hq/dograh-plugins` Claude Code/Codex plugin that auto-detects OS, picks a deploy path, runs Dograh's own setup scripts, and verifies the result end-to-end from a natural-language "set up Dograh" request ([README](https://github.com/dograh-hq/dograh/blob/main/README.md)).
- **A built-in "voice prompting guide."** `api/services/voice_prompting_guide/` is a structured, topic-based prompt-engineering knowledge base shipped inside the product itself (`turn_taking.py`, `instruction_collision.py`, `success_criteria.py`, `guardrails.py`, `call_flow_design.py`, `tool_calls.py`, `end_call_logic.py`) — i.e. productized prompt-engineering guidance for building better voice-agent nodes ([api/services/voice_prompting_guide/](https://github.com/dograh-hq/dograh/tree/main/api/services/voice_prompting_guide)).
- **Gender detection service** (`api/services/gender/`, with a bundled trained model) — plausibly used for TTS voice matching/personalization.
- **Pluggable storage abstraction** (`api/services/filesystem/`: `local.py`, `s3.py`, `minio.py`, `null.py` backends) — lets self-hosters swap storage backend without code changes.
- **Native RNNoise integration** — compiled `librnnoise.so` shared libraries in `api/native/rnnoise/` for real-time neural noise suppression on call audio.
- **Lease-guarded organization bootstrap** — `organization_bootstrap.py` uses a DB "lease" to prevent double-provisioning of non-idempotent upstream calls (minting a managed service key, provisioning managed SIP connectivity) when a new organization is first created — a solid idempotent-tenant-setup pattern.
- **Text-chat parity with voice** — any workflow can be run/tested as a text chat (`workflow_text_chat.py`, `WorkflowRunTextSessionModel`), not only as a phone/voice call.
- **`automation/` is a shipped-but-empty stub** — the nav entry exists and renders a literal "Coming Soon" card, confirming a roadmapped-but-unbuilt feature area ([ui/src/app/automation/page.tsx](https://github.com/dograh-hq/dograh/blob/main/ui/src/app/automation/page.tsx)).
- **No avatar/vision support found anywhere in the codebase or docs.** Dograh is voice/text-only — no camera input, screen-share, or talking-head avatar rendering (Tavus/Beyond Presence/HeyGen-style) surfaced in any route, component, or provider registry inspected. This is a clean differentiation opportunity for a platform (like ours) that already has camera/screen-share vision and avatars wired.

## 4. UI/UX

The UI is a Next.js 15 (App Router) + React 19 single-page-app-like experience, styled with Tailwind v4 + shadcn/ui, state managed with Zustand (+ `zundo` for undo/redo in the flow editor) ([ui/package.json](https://github.com/dograh-hq/dograh/blob/main/ui/package.json)). The primary navigation (`AppSidebar.tsx`) groups screens into three sections ([ui/src/components/layout/AppSidebar.tsx](https://github.com/dograh-hq/dograh/blob/main/ui/src/components/layout/AppSidebar.tsx)):
- **Top-level:** Overview (dashboard landing).
- **BUILD:** Voice Agents (workflow list/builder), Campaigns, Models (provider/credential config), Telephony, Tools, Files (knowledge base), Recordings, Developers (API keys).
- **MANAGE:** Agent Runs, Billing, Reports.

**Agent/workflow builder.** The centerpiece screen (`ui/src/app/workflow/[workflowId]/`) is a React Flow canvas (`ui/src/components/flow/`: `BaseNode.tsx`, `GenericNode.tsx`, `CustomEdge.tsx`, `AddNodePanel.tsx`) with a side panel that renders per-node-type property forms (`NodeEditForm.tsx`, `PropertyInput.tsx`, driven by node specs fetched from a backend catalog via `useNodeSpecs.ts`), a `ToolSelector.tsx` and `DocumentSelector.tsx` for attaching tools/knowledge base per node, and `MentionTextarea.tsx` for `@`-style variable insertion into prompts. Surrounding the canvas: `VersionHistoryPanel.tsx` + `WorkflowVersionDiffDialog.tsx` (version history/diff), `EmbedDialog.tsx` (widget deployment code), `PhoneCallDialog.tsx` (trigger a real test call to a phone number), a `DictionaryDialog.tsx`/`TemplateContextVariablesDialog.tsx` for variables, and `ConfigurationsDialog.tsx` for per-agent model overrides.

**Testing screen.** A dedicated `workflow-tester/` panel (`WorkflowTesterPanel.tsx`) offers **Test Audio** (`EmbeddedVoiceTester.tsx`, a WebRTC mic/speaker test) and **Test Chat** (`ManualTextChatPanel.tsx` + `ChatComposer.tsx`, with per-turn actions via `TurnMessageActions.tsx` — letting a builder edit/replay a user turn and regenerate the agent's reply and node transition from that point, per the README). An `AiSimulatorPlaceholder.tsx` component exists but appears to be a planned, not-yet-shipped AI-caller-simulator feature.

**Call/run review.** A live-call screen at `.../run/[runId]/` shows connection status, audio controls, and live context-variable display during an in-progress test call. Post-call, `ui/src/components/workflow/conversation/` renders a timeline view (`ConversationTimeline.tsx`, `MessageBubble.tsx`, `ToolCallCard.tsx`, `NodeTransitionMarker.tsx`) interleaving transcript, tool calls, and node transitions in one scrollable view — a notably richer session-review artifact than a flat transcript.

**Provider configuration screen.** `/model-configurations` presents three top-level tabs (Speech-to-Speech / Dograh-managed / BYOK) as described in §3.9, each rendering conditional per-provider fields — this is a config-driven form pattern (provider selection changes which fields render) conceptually similar to our own provider-registry-generates-UI-forms approach, though Dograh's version has no field-level encryption underneath.

**Campaigns/dialer screens.** List, create, and edit pages with a CSV contact-upload selector and an advanced-settings panel for pacing/retry configuration — the closest thing in the UI to a "batch operations" surface.

**Reports/analytics screen.** `/reports` combines `DurationChart.tsx`, `DispositionChart.tsx`, and `MetricsCards.tsx` into a single dashboard.

**Settings screen is minimal** — only three cards: Preferences (org defaults like test phone number/timezone), MCP Server (access setup), and Telemetry (Langfuse config); it is explicitly not where provider credentials live (that's `/model-configurations`), which is a slightly unusual information architecture choice worth noting when designing our own settings IA.

**Screenshots corroborating additional surfaces** (filenames only, from `docs/images/`, not fetched as images in this research pass): embed widget variants, BYOK vs. Dograh vs. speech-to-speech model-configuration screens, telephony inbound-config screens per provider, tool-attachment screens, and tracing-integration panels for Noveum/Tuner ([docs/images/](https://github.com/dograh-hq/dograh/tree/main/docs/images)).

## 5. Strengths and weaknesses

### 5.1 Strengths

- **Breadth of telephony coverage**, including a genuine bring-your-own-SIP/PBX path (Cloudonix, Asterisk ARI) alongside six carrier APIs (Twilio, Vonage, Plivo, Telnyx, Vobiz, Exotel), plus a well-documented provider extension point (self-registering package + `ProviderSpec`, only 2 edits needed outside the new provider's own folder) that has already attracted community PRs for additional carriers (VoxPro, TryVox, PAPI, Tata Smartflo) — though none of those four have been merged as of this research, so the extension point's real-world track record is "documented and attempted," not yet "proven by accepted outside contributions" ([docs/integrations/telephony/custom.mdx](https://github.com/dograh-hq/dograh/blob/main/docs/integrations/telephony/custom.mdx)).
- **Fast release cadence and visible momentum** — weekly releases, commits landing the day before this research, 5,693 stars/1,423 forks in ~1 year, #1 Product of the Day/Week/Month on Product Hunt ([README](https://github.com/dograh-hq/dograh/blob/main/README.md); [Releases](https://github.com/dograh-hq/dograh/releases)).
- **Deliberately small, auditable, code-generated SDK surface** (`x-sdk-method` opt-in + shared OpenAPI-driven codegen for Python/TypeScript) is a clean pattern — it avoids accidentally exposing internal-only endpoints as "public API" ([api/sdk_expose.py](https://github.com/dograh-hq/dograh/blob/main/api/sdk_expose.py)).
- **MCP-native in both directions** — agents can call out to external MCP tools, and Dograh exposes its own workflow-editing surface as an MCP server for coding assistants, with a polished setup story (installable Claude Code/Codex plugin) ([README](https://github.com/dograh-hq/dograh/blob/main/README.md)).
- **Thoughtful internal engineering conventions**, evidenced by unusually rigorous `AGENTS.md` files codifying layering rules, organization-scoping-as-a-named-security-invariant, and a plugin-registry pattern for telephony providers — this is a codebase that has clearly been optimized for safe extension by many contributors ([api/AGENTS.md](https://github.com/dograh-hq/dograh/blob/main/api/AGENTS.md)).
- **Zero-downtime agent handoff design** at the pipeline level (generation-stage-as-a-slot, one `PipelineWorker` per node "visit") is a genuinely clever solution to a hard problem — swapping the live LLM/TTS combo mid-call without disrupting the call-scoped transport/recording ([api/services/pipecat/pipeline_builder.py](https://github.com/dograh-hq/dograh/blob/main/api/services/pipecat/pipeline_builder.py)).
- **Both voice and text-chat testing built into the same workflow**, with turn-level edit/replay in Test Chat for fast prompt iteration — a genuinely useful iteration loop called out explicitly in the README ([README](https://github.com/dograh-hq/dograh/blob/main/README.md)).

### 5.2 Weaknesses and gaps (source: issues, code inspection, third-party review)

- **Credentials are stored in plaintext, contradicting an in-code comment claiming encryption.** `ExternalCredentialModel.credential_data` is commented "Encrypted credential data (JSON)" but is a plain, unencrypted JSON column; no encryption library appears anywhere on the credential read/write path; the only protection is response-time last-4-characters masking ([api/db/models.py](https://github.com/dograh-hq/dograh/blob/main/api/db/models.py), [api/services/configuration/masking.py](https://github.com/dograh-hq/dograh/blob/main/api/services/configuration/masking.py)). This is a serious, concrete gap for any regulated-industry (insurance, healthcare, fintech) buyer.
- **No RBAC within an organization** — every org member has equal access to every org resource; the only privilege tier is a global `is_superuser` flag with a real user-impersonation endpoint. Teams needing per-seat roles (e.g. "QA reviewer can see transcripts but not credentials") have no support today (§3.8).
- **The Helm/Kubernetes path is explicitly alpha and admittedly untested** by the maintainers ("validated with `helm lint`/`helm template`. Not yet exercised against a live cluster") — the production-grade horizontal-scaling story is not yet proven, and the default Docker Compose path relies on a single multi-process container with hard-singleton processes (`ari_manager`, `campaign_orchestrator`) that have no leader-election HA ([deploy/helm/dograh/README.md](https://github.com/dograh-hq/dograh/blob/main/deploy/helm/dograh/README.md)).
- **No avatar or vision capability at all** — voice/text only; no camera input, screen-share, or talking-head rendering.
- **No dedicated evaluation/simulated-call product surface.** The `qa` node is a single LLM-as-judge grading step (itself reported broken on Gemini models in issue #636); the only "eval" tooling in the repo is an internal STT-provider benchmarking harness (`evals/`), not a customer-facing scenario/regression test suite; a UI placeholder (`AiSimulatorPlaceholder.tsx`) suggests an AI-caller simulator is planned but not shipped.
- **Real, currently-open production bugs in core paths**, per GitHub Issues (fetched 2026-09-19): campaign concurrency-slot leaks on job cancellation ([#745](https://github.com/dograh-hq/dograh/issues/745)); knowledge-base vector search "silently collapses" on small corpora due to an ivfflat index/probes misconfiguration ([#635](https://github.com/dograh-hq/dograh/issues/635)); a transcriber client that "crashes on null text field and doesn't recover from a stale pooled connection" ([#766](https://github.com/dograh-hq/dograh/issues/766)); realtime-LLM idle-disconnect hanging up before the farewell line is spoken ([#750](https://github.com/dograh-hq/dograh/issues/750)); an unanswered Asterisk outbound call that "never releases its concurrency slot" for 20 minutes ([#737](https://github.com/dograh-hq/dograh/issues/737)); and a cluster of freshly-filed Telnyx webhook bugs — 404 before signature verification enabling run-ID enumeration ([#780](https://github.com/dograh-hq/dograh/issues/780)), auto-created Call Control Applications missing an Outbound Voice Profile so "every outbound call fails" ([#778](https://github.com/dograh-hq/dograh/issues/778)), and a 500 when an org has no default telephony configuration ([#779](https://github.com/dograh-hq/dograh/issues/779)).
- **Security-relevant issues beyond credential storage**, per issue history: outbound Twilio webhooks historically lacked signature validation (closed as fixed, [#340](https://github.com/dograh-hq/dograh/issues/340)); "public download tokens are permanent bearer secrets with no expiry or rotation" ([#329](https://github.com/dograh-hq/dograh/issues/329)); webhook tools have "no way to sign/authenticate outbound requests without a plaintext secret in workflow source" ([#633](https://github.com/dograh-hq/dograh/issues/633)); Swagger UI silently drops the Authorization header ([#710](https://github.com/dograh-hq/dograh/issues/710)).
- **Internationalization/locale gaps.** A third-party review notes Dograh is explicitly English-centric and that other languages "require custom work" ([dev.co review](https://dev.co/devops/open-source/dograh)); source-level evidence agrees — knowledge-base `.txt` ingestion "mangles Japanese text" while `.docx` of the same content is fine ([#634](https://github.com/dograh-hq/dograh/issues/634)), and runtime STT language switching mid-call is an open feature request, not a shipped capability ([#739](https://github.com/dograh-hq/dograh/issues/739)).
- **No enterprise support/SLA story for self-hosters** — no stated uptime SLA, commercial support tier, or compliance certification (SOC2/HIPAA) disclosed for the open-source path; the operational burden (Docker/K8s expertise, monitoring, upgrades) falls entirely on the self-hosting team ([dev.co review](https://dev.co/devops/open-source/dograh)).
- **Cloud/OSS feature parity is not guaranteed** — at least one shipped feature is explicitly "cloud only" (a Cartesia event-announcement banner in v1.47.0), meaning the self-hosted product is not a strict superset mirror of what `app.dograh.com` runs ([v1.47.0 release notes](https://github.com/dograh-hq/dograh/releases/tag/dograh-v1.47.0)).
- **Contribution/maintenance concentration risk** — two maintainers (`a6kme`, `chewwbaka`) account for the overwhelming majority of commits (511 and 207 respectively, versus a long tail of single-digit-commit contributors), which is typical for a young project but a real bus-factor consideration for anyone betting production infrastructure on the project's continuity ([Contributors](https://github.com/dograh-hq/dograh/graphs/contributors)).

## 6. Pipecat vs. LiveKit Agents — what maps and what doesn't

Dograh's entire real-time core is built on a **deep fork of Pipecat** (§2.3), not LiveKit — so this section maps Dograh's *features* (regardless of the framework detail) onto what LiveKit Agents 1.8 can and cannot do natively, to identify what our LiveKit-based platform gets "for free" vs. must build.

**Framework-level differences relevant here** (general knowledge, cross-checked against public comparisons — [Dograh's own Pipecat-vs-LiveKit blog post](https://www.dograh.com/feeds/blog/pipecat-livekit-agents), [inworld.ai comparison](https://inworld.ai/resources/vapi-vs-pipecat-vs-livekit)): Pipecat is a composable, transport-agnostic pipeline of processors you assemble yourself (Daily, WebSocket, Twilio, LiveKit-as-just-another-transport); LiveKit Agents instead joins a room as a participant over LiveKit's own Go-based WebRTC SFU, with native NAT traversal/jitter buffering and multi-participant rooms built in. Dograh's own comparison content (marketing, but technically specific) credits LiveKit with **native SIP trunking** (inbound and outbound, no Twilio bridge needed) and **built-in multi-agent handoffs**, versus Pipecat's requirement to bolt on external transports and hand-roll multi-agent orchestration — which matches what Dograh's own codebase shows it had to build itself (the `PipecatEngine` + generation-stage-as-a-slot machinery in §2.3 is exactly the kind of custom multi-agent/handoff orchestration LiveKit ships natively).

### 6.1 Maps cleanly onto LiveKit Agents 1.8

| Dograh feature | LiveKit Agents 1.8 equivalent |
|---|---|
| Per-node "agent" with its own prompt/tools, transitions to the next node | **Agent** class + **AgentSession** — `Agent.update_options(...)` or a tool returning a new `Agent` triggers a handoff; an `AgentHandoff` chat-context item records `old_agent_id`/`new_agent_id` ([LiveKit docs](https://docs.livekit.io/agents/build/agents-handoffs/)) |
| Global instructions applying to all nodes | `AgentSession`-level default instructions/plugins, overridable per `Agent`/`AgentTask` |
| Cross-node context/variable carry-over | `chat_ctx` passing (`chat_ctx=self.chat_ctx` or `.copy(exclude_instructions=True)`) + `session.userdata` object ([LiveKit docs](https://docs.livekit.io/agents/build/agents-handoffs/)) |
| Call transfer to a different agent (`TransferAgentToolConfig`) | Native tool-based handoff (`llm.handoff({agent: newAgent, ...})`) — arguably a **cleaner** primitive than Dograh's bespoke transfer-resolver + pipeline-worker-swap machinery |
| STT/LLM/TTS provider swapping per agent/node | `Agent`/`AgentTask` constructor plugin overrides (`stt=`, `llm=`, `tts=`, `vad=`) and `Agent.update_options(...)` mid-conversation |
| DTMF handling (a Dograh gap per §3.3 — explicitly marked "future" internally) | LiveKit's native SIP layer ships DTMF and SIP REFER support out of the box ([LiveKit SIP docs](https://docs.livekit.io/sip/sip-trunk/)) — **an area where LiveKit is already ahead of Dograh's own shipped state**, not just at parity |
| Realtime/speech-to-speech models (OpenAI Realtime, Gemini Live, etc.) | **LiveKit Inference** unifies STT/LLM/TTS/realtime model access behind one interface (`inference.STT`/`inference.LLM`/`inference.TTS`, e.g. `deepgram/nova-3`, `google/gemma-4-31b-it`, `fishaudio/s2.1-pro`), billed per-model, introduced as a first-class primitive in **LiveKit Agents 1.7.0** (2026-08-20) alongside **Expressive Mode** (`AgentSession(..., expressive=True)`, natural prosody/emotion tags derived from conversation context) — a TTS-quality feature Dograh has no equivalent of. **1.8.1** (2026-09-10) added a `DuplexModel` class for full-duplex speak-while-listening models, OpenAI's "GPT-Live" model as the first implementation ([LiveKit Agents 1.7.0 release](https://github.com/livekit/agents/releases/tag/livekit-agents%401.7.0), [1.8.1 release](https://github.com/livekit/agents/releases/tag/livekit-agents%401.8.1) — dates confirmed via the GitHub Releases API) |
| VAD + turn detection | `AgentSession`'s configurable `turn_handling`, including **preemptive generation** (speculatively starts the LLM request before end-of-turn is confirmed) — arguably ahead of Dograh's three-tier VAD/smart-turn/STT-native design on latency, though Pipecat's dedicated smart-turn classifier is a close/older analog ([LiveKit docs](https://docs.livekit.io/agents/build/sessions/)) |
| SIP telephony (inbound/outbound, per-provider carriers) | **Native SIP trunk support** — inbound/outbound trunks, DTMF, SIP REFER, works with Twilio/Telnyx/Plivo/etc. as SIP carriers rather than bespoke per-provider REST integrations; "the same agent code" handles inbound and outbound ([LiveKit SIP docs](https://docs.livekit.io/sip/sip-trunk/), [docs.livekit.io/sip/quickstart](https://docs.livekit.io/sip/quickstart/)) — this is a **structural advantage**: one SIP integration point instead of Dograh's 8 per-carrier plugin packages |
| Call recording | **Egress** — RoomComposite (stops automatically when all participants leave), Track Composite, and standalone Web Egress, with audio-only mode ([LiveKit Egress docs](https://docs.livekit.io/home/egress/overview/)) — a managed, first-party equivalent to Dograh's MinIO/S3-recording-router pattern |
| MCP tool calling (agent → external MCP server) | **Native `mcp_servers` parameter on `AgentSession`** (`MCPServerStdio` etc.), with auth headers and tool filtering — LiveKit's MCP-as-client support is at least as capable as Dograh's MCP tool |
| Tracing/observability (Langfuse, PII handling) | LiveKit Agents **1.7.0** (2026-08-20) introduced PII redaction for Agent Observability (semantic redaction of chat history/audio recordings, filtered logs/traces); **1.8.0** (2026-09-05) followed with a full **OpenTelemetry GenAI semantic-convention overhaul** (a breaking change to span/event shapes), enabling native Langfuse/Datadog Agent Observability integration with PII filtering moved fully in-process (stripped before any exporter, including LiveKit Cloud's own collector); **1.8.2** (2026-09-15) added run-loop-blocking detection and full agent-lifecycle tracing (dispatch → startup → shutdown) ([release notes via GitHub Releases API](https://github.com/livekit/agents/releases)) — collectively more mature and standardized than Dograh's dual-track own-viewer + optional-Langfuse setup (§3.7), and notably LiveKit's PII-redaction feature has **no Dograh equivalent** at all |
| Avatar rendering (a feature Dograh **lacks**, see §5.2) | LiveKit has a mature **avatar plugin ecosystem** (14+ providers: Tavus, Beyond Presence, Anam, Simli, Hedra, D-ID, Synthesia — the last added as a first-party plugin in 1.8.2 — etc.) already wired as first-party plugins — exactly the two providers (Beyond Presence, Tavus) our platform already has integrated |

### 6.2 Requires meaningful custom work on LiveKit (no first-class equivalent)

| Dograh feature | Gap on LiveKit / what we'd need to build |
|---|---|
| **Visual, declarative node/edge workflow builder** (React Flow canvas, JSON-persisted graph, LLM-evaluated free-text edge conditions) | LiveKit Agents is **code-first/imperative** — workflows are expressed as Python/TS code with tools returning handoffs, not a JSON graph a non-engineer edits visually. There is no LiveKit-native visual builder; this is pure product surface we'd build ourselves (our provider registry → UI-form pattern is a good foundation, but the flow-canvas + node-type system is a separate, substantial build) |
| **Natural-language-condition edges evaluated by the LLM** (no structured expression language) | No direct equivalent — LiveKit handoffs are triggered by explicit tool-call logic in code. We could choose either model; a hybrid (structured conditions with an LLM-evaluated fallback) is a reasonable design LiveKit doesn't dictate either way |
| **Campaigns/outbound dialer with CSV upload, pacing, and per-org concurrency slots** | Not a LiveKit Agents concept at all — LiveKit gives you the SIP/room primitives to place a call, but batch-dialing orchestration, contact-list management, pacing/retry logic, and concurrency-slot accounting are entirely platform-level work, same as Dograh had to build (`CallConcurrencyService`, `campaign_orchestrator`) |
| **Voicemail detection** | Not part of LiveKit Agents or SIP docs surfaced in this research; would need a dedicated AMD (answering-machine detection) integration or model, same gap Dograh itself has open issues against (#777) |
| **Workflow versioning/diffing UI** (git-like history of the agent definition) | Pure product-layer feature; no framework equivalent on either side — build cost is the same regardless of runtime |
| **Text-chat-mode parity with the same "workflow"** (test/run an agent as pure text, not just voice) | Not a LiveKit concept (LiveKit is fundamentally room/media-centric); would need a parallel text-mode execution path in our own agent runtime, decoupled from `AgentSession`'s audio assumptions |
| **In-house prompt-engineering guidance product surface** ("voice prompting guide") | Pure content/product feature, unrelated to either framework |
| **A "generation-stage-as-a-slot" zero-downtime handoff at the pipeline level** | LiveKit's handoff model already solves the *problem* this was built for (swapping agent/model without dropping the call) via its own `AgentSession`/`Agent` abstraction — we don't need to replicate Dograh's specific mechanism, but we do need to verify LiveKit handoffs preserve call-scoped resources (recording, transport) the way we need, which is a design/testing task, not a framework gap |
| **MCP server exposing the platform itself to coding agents** (Dograh's `fastmcp`-based self-editing surface) | Not a LiveKit concern at all — this is Dograh's own product choice (workflow-as-code editable by Claude Code/Codex) and would be entirely new work for us if we wanted parity, independent of runtime |
| **Gender-detection service, native RNNoise integration** | Niche, independent of framework — LiveKit doesn't ship these either; would be bespoke additions on either stack |
| **Encrypted-credential storage done correctly** | Not a framework feature at all (Dograh's gap is a product/security defect, not a Pipecat limitation) — we already have this covered per our existing platform |

**Bottom line:** most of Dograh's *runtime* voice-agent capabilities (multi-agent handoff, realtime models, SIP, recording, tracing, MCP tool-calling) map onto LiveKit Agents 1.8 primitives as well or better, often with less custom plumbing than Dograh had to write for itself on top of a Pipecat fork. The capabilities that do **not** map are almost entirely **product-layer** (visual workflow builder, campaigns/dialer, versioning UI, text-chat parity) rather than runtime/transport gaps — which means our build effort should go into the product layer, not into re-solving problems LiveKit Agents already solves at the framework level.

## 7. Recommendation — prioritized feature list

Given our platform already has: config-driven agents/packs with a provider-registry-generated UI, encrypted credentials, HTTP/MCP tools, a knowledge base (LanceDB + fastembed), live UI panels with camera/screen-share vision and avatars (Beyond Presence, Tavus), session history, and a console with test-call — the gaps below are scoped relative to that baseline, not from zero.

### MVP (must-have to reach parity on what buyers will actually compare us against)

1. **Visual workflow/flow builder (node/edge canvas)** — this is Dograh's headline feature and the single biggest thing a Vapi/Retell/Dograh-comparison buyer will look for first; without it we're a code-first tool competing against a no-code one. *Rationale: table stakes for the product category Dograh defines.*
2. **SIP trunk + carrier telephony (inbound/outbound) using LiveKit's native SIP support**, covering at minimum Twilio and Telnyx as SIP carriers plus DTMF handling. *Rationale: telephony is the primary distribution channel for voice agents; LiveKit's native SIP is structurally simpler to ship well than Dograh's N-provider plugin architecture — an area we can actually beat Dograh on with less code.*
3. **Call recording via LiveKit Egress, stored to our existing storage layer, surfaced in session history.** *Rationale: Dograh treats recordings as core to every "Run"; our session history needs the audio artifact, not just the transcript, to be comparable.*
4. **Per-node/per-agent prompt + tool configuration UI, backed by our existing provider registry pattern** (extend it to also drive per-node STT/LLM/TTS/realtime-model overrides, the way Dograh's Model Overrides work). *Rationale: leverages an asset we already have; closes the "provider flexibility per agent step" gap directly.*
5. **Outbound campaigns/dialer (CSV upload, pacing, concurrency limits) reusing LiveKit SIP for dispatch.** *Rationale: this is the #1 commercial use case in Dograh's own issue tracker (multiple carrier PRs exist purely to support campaign-style outbound) and a Dograh strength we cannot skip.*
6. **Test Chat (text-mode) alongside the existing test-call console**, with turn-level edit/replay. *Rationale: cheap to build relative to value — dramatically speeds up prompt iteration without needing a live call, and is explicitly called out as a favorite Dograh workflow in its own README.*
7. **Fix-forward: keep our encrypted-credential design and RBAC as an explicit competitive claim** — no new build needed, but this should be a called-out differentiator in positioning since Dograh's plaintext-credential gap and absent RBAC are verifiable, concrete weaknesses (§5.2, §3.8, §3.9).

### v1.1

8. **LLM-as-judge QA step per call (a `qa`-node equivalent) with a fix for the fragility Dograh reports on Gemini models** — i.e. build it more robustly than Dograh's version rather than just matching it. *Rationale: real customer-requested feature category (call grading/QA), moderate build cost, differentiable by being more reliable.*
9. **Workflow versioning + diff UI.** *Rationale: valuable for team workflows once multiple people edit the same agent, but not blocking for MVP adoption.*
10. **Embeddable web widget (floating/inline/headless) for the workflow builder's agents**, building on our existing live UI panels. *Rationale: Dograh feature with clear customer value (deploy an agent to a website) but secondary to telephony/campaigns for our insurance-vertical use case.*
11. **Voicemail/answering-machine detection for outbound campaigns.** *Rationale: needed for production-grade dialers but can follow campaigns MVP by one release; Dograh itself still has open reliability issues here, so there's no rush to match a broken bar.*
12. **Webhook node/tool with signed outbound requests (HMAC or similar) from day one** — explicitly better than Dograh's current gap (issue #633, plaintext-secret-only signing). *Rationale: low cost, clear "we do this better" claim if we ship signing where Dograh doesn't.*
13. **OTel-based tracing integration (Langfuse/Datadog) via LiveKit Agents 1.8's native GenAI semantic-convention export.** *Rationale: LiveKit gives us this closer to free than Dograh got it (Dograh's OTEL endpoint just landed 2026-09-17); low-cost, high-signal observability story.*

### Later

14. **AI-driven call simulator / scenario regression testing** (the thing Dograh has only as an unshipped UI placeholder). *Rationale: genuinely valuable but nobody in this market has shipped it well yet — an opportunity to lead rather than catch up, but not urgent since Dograh itself hasn't shipped it.*
15. **Kubernetes/Helm production deployment path.** *Rationale: Dograh's own Helm chart is alpha/unproven; we can defer serious k8s investment until self-hosted enterprise demand is concrete, since LiveKit's own infrastructure model is inherently more horizontally-scalable than Dograh's compose-first design, reducing our urgency here.*
16. **Bring-your-own-SIP/PBX (Asterisk ARI-equivalent) for self-hosted, telco-savvy customers.** *Rationale: niche but real (Dograh built it); LiveKit's SIP layer likely covers most of this need already via standard SIP trunking, so this may be largely subsumed by item 2 rather than a separate build.*
17. **In-product "voice prompting guide" content and MCP-server self-editing surface** (Dograh's coding-agent-facing MCP server for its own workflows). *Rationale: nice differentiation/DX polish, not a purchase driver; revisit once core parity is reached.*
18. **Gender-detection / voice-personalization service, native noise-suppression (RNNoise-equivalent).** *Rationale: marginal quality-of-life features; low priority relative to core reliability and feature-parity work.*
