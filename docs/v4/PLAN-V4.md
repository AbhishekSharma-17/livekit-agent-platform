# LKAP v4 — delivery plan

Status: **started** (Fable 5.1, 2026-09-24) with the starter-template packages; V4-03/04 (OpenRouter) added 2026-09-25; V4-05 (LiveKit-hosted numbers) and V4-06 (populate-and-validate) added 2026-09-25 with rulings R-V4-10 … R-V4-20; V4-07 … V4-10 (custom model ids, live catalogs, "Test model", catalog drift) added 2026-09-25 with rulings R-V4-21 … R-V4-28. Later v4 packages append to §1 and §2. Owners: **Opus** for contracts, api and MCP; **Sonnet** for the console. Fable reviews each package against its acceptance and records rulings in §5.

Naming: v4 packages are **`V4-nn`**. Rulings are **`R-V4-n`** (§5) and amend the cards, `TEMPLATES.md`, `OPENROUTER.md` and `PHONE-NUMBERS.md`. Design: [`TEMPLATES.md`](TEMPLATES.md) (decisions D-V4-1…8, contracts, seeding algorithm, the catalogue, the dialog, tests); [`OPENROUTER.md`](OPENROUTER.md) (findings per modality with sources, decisions D-V4-9…13, the live check); [`PHONE-NUMBERS.md`](PHONE-NUMBERS.md) (LiveKit-hosted numbers: facts from the upstream proto and the `lk` CLI, decisions D-V4-14…22, the shim, the live check); [`CUSTOM-MODELS.md`](CUSTOM-MODELS.md) (custom model ids, live catalogs per vendor with sources, the "Test model" probes, the drift job, decisions D-V4-23…28, the live check). V4-06 (populate-and-validate) has no design doc; its card is the whole spec.

Definitions (unchanged from `../v3/PLAN-V3.md`):
- **Python gate** (inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test` (never `pnpm build` in `web/`; HANDOFF rule 6).
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts mcp/src/lkap_mcp/generated mcp/claude-plugin/skills/lkap/recipes`.
- **Exclusive ownership**: a package edits only the paths its card lists; anything else is a one-line ask in `docs/v4/_asks.md` (V4-01 creates it with the v3 format: **owner package** — file — the exact edit — who asked — status). The coordinator's decisions there are binding.
- **Migration discipline** (HANDOFF rule 4): none in V4-01…V4-04 (D-V4-3: no new column). V4-05 carries **one**, `v4_001_livekit_numbers`, pre-authorised by R-V4-11: rehearsed on a copy and on the Postgres CI job, applied to `api/data/lkap.db` by the coordinator after a `.backup`. V4-07 carries the **second and last**, `v4_002_provider_models`, pre-authorised by R-V4-24 under the same rehearsal discipline. Any other package that finds it needs one stops and files an ask.
- **Live rules** (HANDOFF rule 3): a scratch api on its own port and DB, a worker under a fresh agent name, never `lkap-agent`, never `other-project-agent`.
- **Path rules**: never create, read or name a path whose segment starts with `credentials` (HANDOFF rule 1) — say "provider keys", `provider_keys.py`, `/console/keys`; never read or write `.env*` (rule 2). The catalogue's prose names only fictional companies and `example.com` (R-V3-8).

## 4. Risks

- **`seed_config_from_manifest` assumptions.** It reads `manifest.default_panel` only through `effective_layout` (the config's `panel` stays default). Templates that compose blocks must store them (§4 step 2) or block tools will not register. Mitigated by the flow-reference test, which fails if `request_form`/`table_append` are not allowed for `receptionist`.
- **Placeholder tool URLs** on `receptionist`: an unedited starter reports "couldn't reach the booking system" at runtime. Accepted (R-V4-4); the next step and the dry run make the fix one edit.
- **Long JSON flows** are easy to break by hand. The test validates every one; the MCP `agent_flow_validate` recipe covers edits after creation.
- **Console before api**: a console upgraded before its api sees a 404 on `templates`; the fallback to `packs` keeps the dialog working with derived tiles.
- **Two "Acme"s** in seeds (dental practice, meter product) are fictional by design; the doc lint keeps real hostnames out.
- **LiveKit's rule-conflict refusal** (V4-05): the shared project hosts `other-project-agent`'s rules, which LKAP cannot see. Mitigated by the pre-check warning and the 422 relay that names LiveKit's message; the live check records the outcome.
- **Unverified LiveKit semantics** (V4-05 §1: the grant, detach, delete-while-attached, region): the design plans for both outcomes of each; the live check settles them; none changes the schema.
- **The demo run writes to the user's database** (V4-06): bounded by the Builder key, the `Demo — ` prefix, the manifest check after every run, one permitted delete, and the before/after diffs. A foreign write stops the run.
- **A probe proves the vendor, not the plugin** (V4-08): a model id the vendor accepts can still be rejected by the LiveKit plugin (a `Literal` kwarg, a plugin-side rename). Mitigated by the result panel's one-line caveat and the unchanged first-session `ProviderBuildError` path; a worker-side build check is a later decision (R-V4-25).
- **Vendor list shapes drift** (V4-07): three adapters already disagree with today's vendor pages (Cartesia headers, Hume `provider`, ElevenLabs v1/v2). `parse_items` stays lenient, page one is always tried, and the live check settles each; none may fail the providers page (V2-06 rule).
- **Secret-looking ids** (V4-07): the prefix list is a heuristic; a key with an unknown prefix passes the id rule and is sent to the vendor as a model id — the vendor 4xx names it, and the scrub step removes the stored secret values from every message, so the exposure is one log-free vendor request. The list grows by test, never by guess.
- **Test-model cost** (V4-08): capped by count (10/min/workspace, 2 in flight, ≤ 4 tokens, 1 s of audio, no images), not by dollars, because most custom models are unpriced (`pricing.lookup` → `None`). Free-tier keys can still hit vendor rate limits; the 429 is relayed as `ok=false`, never retried.
- **Deprecation false positives** (V4-10): "missing from the live list" is compared only against the previous fetch of the same filtered list; explicit vendor signals are trusted as-is. A wrong warning is still a warning (never an error).

### R-V4-21 — A model id is free text under one rule; unknown stays a warning; a secret-looking value is refused without echo (`CUSTOM-MODELS.md` D-V4-23, 2026-09-25)
- The registry's `models` list is a suggestion list, never an allowlist (CONTRACTS.md, D-W2-10) — this ruling keeps it so. `validate_model_id` refuses only two things, as **errors**: a value that looks like an API key (`SECRET_PREFIXES`, or a bare ≥ 40-character token) and a value that breaks the syntax rule (1–200 printable ASCII characters, no whitespace, no `://`/`?`/`#`/`&`/`=`/quotes, not starting with `http`; `/ . _ : @ + -` admitted because real ids use them). The secret check runs first and no message, audit payload, log line or console string ever contains the value; the "not in the suggestion list" warning is reworded to omit the value, and `_validate_fields`' enum error (`got '<value>'`, the one built-in echo) drops the value too. The bare-token rule is ≥ 32 characters of one class with no separator (32-hex keys included); `SECRET_PREFIXES` includes `sk_`. The same rule applies to every `type="model"`/`type="catalog"` field and to `ID_LIKE_FIELD_NAMES` (voice, voice_id, avatar_id, face_id, pal_id, persona_id, voice_name, emotion_id). Rejected: an allowlist (LiveKit Inference lists churn weekly); errors for unknown ids (inverts the documented rule); a secret *value* comparison against the vault (validation never decrypts).

### R-V4-25 — "Test model" runs in the api process over the guarded client, as a second adapter tree, capped by count, never for images (D-V4-26)
- The worker has no inbound surface (registration and heartbeat are outbound; sessions arrive by LiveKit dispatch), and the api already calls vendors for the QA judge and the embedder, so probes run in the api through `net_guard`; LiveKit Inference is reachable because the gateway is OpenAI-shaped and the api's own `livekit-api` can mint the `InferenceGrants(perform=True)` JWT from the connection named by `ModelTestRequest.connection_id` (default: the workspace's default connection). `ProviderSpec.probe` names a probe adapter — a POST with a payload and a budget, deliberately **not** folded into `test` (the `test == catalog.adapter` invariant is a GET that lists). Budgets: `max_tokens ≤ 4`, TTS input `"Hello."`, a bundled 1 s STT clip, embeddings `"ping"`, realtime = websocket handshake without audio, avatars = a session-less GET; **no image generation** (every image costs money; catalog membership only). Caps are by count — 10 per workspace per minute, 2 in flight — because most custom models are unpriced (`pricing.lookup` → `None`; `cost_estimate_usd` is `None` with a note unless a price or OpenRouter `meta.pricing` exists). Every message is scrubbed against the decrypted secret values before it is stored, returned or logged; `sample` and vendor messages are untrusted data (mono box in the console, `untrusted()` in the MCP; TTS returns byte count and content type, never bytes). Stated limitation: a passing probe proves the vendor accepts the id with that key, not that the LiveKit plugin constructs it — the first-session `ProviderBuildError` path keeps that job; a worker-side build check is a later decision, not this one. Rejected: a worker-side probe via a LiveKit room (a full session lifecycle per click); dollar caps (unknowable for custom ids).
- **Owner:** V4-08. **Acceptance:** the request-body, scrub, cache, rate-limit and no-`/images` tests of the card.

### R-V4-26 — Gating and the validation link: builders may test with `agents:write`; an untested custom model is a warning; strict mode is deferred
- `POST /v1/providers/{provider_id}/test-model` gets its own `_Rule` (the longest route-template prefix wins in `policy_for`): `builder` + `agents:write` to run, `builder` + `providers:read` to read records — a builder testing the model they are configuring spends vendor money exactly as test chat does under `sessions:write`. Declaring capabilities (`PUT …/models/{id}`) stays `admin` + `providers:write`. In validation an untested custom model, a failed last test, a catalog disappearance or an explicit vendor deprecation is a **warning** at the slot's path; `agent_publish` inherits them as warnings. A workspace setting that turns "untested" into a publish error (strict mode) is **deferred** and recorded here so it is not built ad hoc.
- **Owner:** V4-08 (rule and route), V4-07 (validators). **Acceptance:** the `roles` longest-prefix test; the warning cases in `test_config_service.py`.

### R-V4-27 — Registry defaults are promoted on evidence; drift is reported weekly by a job that reuses the adapter tree and never fails the build (D-V4-27)
- A model enters the registry `models` list only with a recorded passing `test-model` run on the dev stack; `default_model` changes only with a second recorded text-chat session; `supports_video` flips only on a passing `vision` probe or a recorded vision session, never from vendor metadata; no `:free`, `auto` or preview id becomes a default. `scripts/catalog_drift.py` imports `lkap_api.catalogs.adapters` (one adapter tree, D-V2-9), runs keyless for public lists (OpenRouter, Deepgram, Rime) and with repository secrets where present, applies each entry's `CatalogFilter`, and reports `registry_not_upstream`, `upstream_new`, `deprecation_notices` and `skipped` into one open `Catalog drift` issue; `permissions: issues: write` only on that job (V2-21); exit 0 always. `VERIFIED_IDS` is a provider-level live-call fact and is not touched by model promotion.
- **Owner:** V4-10. **Acceptance:** the card's fixture cases; the `CONTRIBUTING.md` section.

### R-V4-28 — Live catalogs are filtered by registry data, searched over the cache, and "missing upstream" is compared only against the same filtered list (D-V4-25, D-V4-27)
- `CatalogSpec.filter` (`CatalogFilter`: id include/exclude regexes, one meta path/contains) and `CatalogSpec.page` (`PageSpec`) are registry data applied by `service.get_catalog`; a contracts test proves every `models[].id` and `default_model` passes its own entry's filter. Search (`q`, `limit`, `offset`, `model` for voices) runs over the cached list; a vendor-side search happens only on an explicit `search_vendor=true` and only for OpenRouter (the one vendor with a `q` parameter) — typing never burns vendor rate limit. A public list (Deepgram `/v1/models`, Rime's JSON, OpenRouter `/models`) may be a `catalog` adapter but never `test` (R-V4-9) — which requires `service.get_catalog` to resolve the adapter from `spec.catalog.adapter` (today it uses `spec.test` and skips the fetch with an empty secret bag) and adapters to declare `public` so a keyless fetch runs; credential tests keep `spec.test`. Azure's voice list needs the slot's `speech_region`, which the provider-level catalog route cannot carry: no adapter in v4 (ask). A model is marked missing upstream only when it was in the previous cached fetch of the **same entry and filter** and is absent from the new one, or when the vendor says so explicitly (OpenAI `shutdown_date`, Mistral `archived`, Bedrock `modelLifecycle`); a differently filtered list never counts. Three adapter discrepancies found this pass (Cartesia headers/version, Hume's required `provider`, ElevenLabs v1 vs v2) are asks settled by the live check, not guesses. Bedrock (SigV4), Fireworks (account-scoped) and LiveKit Inference (no documented list; the gateway answered `{}` unauthenticated) get no adapter in v4.
