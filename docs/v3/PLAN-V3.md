# LKAP v3 — Agent Access Layer: delivery plan

Status: **decided** (Fable 5.1, 2026-09-24). Baseline HEAD `edac441` (Phase 1 complete). Owners: **Opus** for the server core, the chat transport and the api changes; **Sonnet** for docs, console and tests. Fable reviews at the end of each wave and signs off the live run.

Naming: v3 packages are **`V3-nn`**. Rulings are **`R-V3-n`** (§8) and amend the cards and `AGENT-ACCESS.md`.

Definitions (unchanged from PLAN-V2):
- **Python gate** (inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test` (never `pnpm build` in `web/`; HANDOFF rule 6).
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts mcp/src/lkap_mcp/generated` (the third path exists from wave 1, once V3-01's copy step lands; V3-00 runs the gate with the first two paths).
- **Exclusive ownership**: a package edits only the paths its card lists; anything else is a one-line ask in `docs/v3/_asks.md` for the owner. The coordinator's decisions there are binding.
- **Migration discipline** (HANDOFF rule 4, R-V3-10): only the coordinator runs `alembic` against `api/data/lkap.db`, after `sqlite3 api/data/lkap.db ".backup <scratchpad>"`. Packages rehearse on copies.
- **Live rules** (HANDOFF rule 3): the shared Cloud project also hosts `other-project-agent` (never touch it) and the user's worker `lkap-agent` (never run a second worker under that name). Live checks use a scratch api with its own DB and port, and a worker under a fresh agent name.

## 4. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A client does not surface resources or prompts | Every doc is also a tool (`lkap_guide`, `lkap_explain`, `lkap_describe`); the guide tells the agent to call `lkap_guide` first; the console snippet suggests a `CLAUDE.md` line. |
| Sixty tools crowd the model's context | Scope gating hides what the key cannot do (read-only ≈ 25 tools); descriptions are one line; the catalog snapshot keeps them deliberate. Phase 2 may add `LKAP_MCP_TOOLSET=` to select domains. |

| The Claude Code transcript still carries the api key (from `--env`) | That is how every MCP client stores keys; the dialog says user-level config, 30-day expiry, and revoke in the console; the key is scoped to one workspace. |

## 8. Rulings

IDs `R-V3-n`, recorded here so they outlive the chat. They amend the cards and `AGENT-ACCESS.md`.

### R-V3-1 — No CLI: the MCP server is the single agent surface (user decision, 2026-09-24)
- The user ruled: "If MCP itself can do it, no need for a CLI." There is no `lkap` CLI, no CLI package, no CLI commands and no JSON-output mode. `lkap_mcp/client.py` is an internal module, not a published SDK. The console's "Connect an AI agent" dialog shows MCP config snippets (Claude Code `claude mcp add`, Codex `config.toml`, Cursor/generic `mcpServers` JSON, and the remote form when V3-06 is on) in place of any install line. Shell-only agents connect through their MCP support or not at all.

### R-V3-2 — Dialogs only: no side drawers or sheets anywhere in the console (UI ruling)
- The user's rule: no side drawers or sheets anywhere; use modals/dialogs. Every V3 console surface is a `Dialog` (`@/components/ui/dialog`) or a `ConfirmDialog`; no V3 file imports `@/components/ui/sheet` and V3-04's acceptance greps for it. The existing sheet/drawer usages (`test-chat-drawer.tsx`, `credential-sheet.tsx`, the webhooks deliveries panel, the flow node inspector and version history, the editor shell) are being converted by another agent and are **not** V3 files; V3 packages must not touch them. This ruling amends `UI_UX_SPEC-V2-AMENDMENTS.md` §2.3 ("node inspector as a right sheet", "version history sheet") and §2.5 ("deliveries drawer"): those become dialogs. New console work after v3 follows the same rule.

### R-V3-3 — Secrets go in inline or by reference; the MCP never returns one (amended 2026-09-24 by the user's decision "Allow pasting in chat")
- Inline secrets are a first-class path: the user may paste the LiveKit url, key and secret and vendor keys into the agent chat, and the tools accept them as plain values and send them straight to the vault. By-reference (`env:NAME`, `file:/path`, `file:/path#KEY`, `raw:` escape) stays as the alternative the guide recommends when an env file exists. Inline is **simply allowed, with no per-key flag**: the exposure is in the client's own local transcript, which a server-side flag cannot change; the console shows a one-time, acknowledged warning at minting instead. A process-level opt-out (`LKAP_MCP_INLINE_SECRETS=off`) exists for operators who want to force references on a shared or remote server.
- Non-negotiables, tested: no tool result, `plan`, log line, error message or doc ever contains a secret value; the redaction filter and the seen-value scrubber run on every result and error; the value is sent once to the api's write route and not retained; the webhook signing secret goes to a 0600 file in stdio mode and is unavailable in HTTP mode.
- The earlier `LKAP_MCP_ALLOW_INLINE_SECRETS` opt-in and the dialog's "Allow pasting secrets" checkbox are withdrawn.

### R-V3-4 — Test chat runs in the MCP process over the room; nothing MCP-related mounts in the api
- `chat_*` tools use the `livekit` rtc SDK from the MCP process (`lk.chat` in, `lk.transcription` out, `lkap.agent.action` for rewind). The api stays stateless and rtc-free (R-V2-5 boundary). The remote HTTP mode is the same server run as its own process and compose service; `/mcp` is never a FastAPI route. A server-side text relay is the recorded Phase 2 alternative if a pure-HTTP MCP is ever required.

### R-V3-5 — The MCP is a `/v1` client with an API key, never more
- No `/internal/v1` calls, no service token, no admin token, no cookie sessions. `X-Workspace` is set only from `LKAP_WORKSPACE` at startup. The api's `WorkspaceContext`, role and scope rules are the security boundary; the MCP adds gates (R-V3-6, R-V3-7) and never removes one.

### R-V3-6 — Destructive operations need `confirm`; every write offers `plan`
- `lkap_delete`, `connection_rotate`, `connection_fleet(stop|restart)`, `agent_archive`, `agent_versions(restore=)`, `call_place`, `call_control` return `needs_confirmation` unless `confirm=true`, and carry `destructiveHint`. Every write tool accepts `plan=true` and then sends nothing. `api_request` requires `confirm=true` for any non-GET.

### R-V3-7 — Telephony: reads by default; dialing behind three gates; the policy is never a tool
- `call_place` and `call_control` register only when the key has `calls:write` **and** the process has `LKAP_MCP_ALLOW_DIAL=1`, and each call needs `confirm=true`. The workspace dialing policy (R-V2-23, R-V2-28, R-V2-29) is read-only through `workspace_get`/`telephony_overview` and cannot be written through any tool, including `api_request` (which refuses `/v1/workspaces/*` writes and `/v1/telephony` writes). Trunk, number and dispatch-rule writes stay console-only in v3.

### R-V3-8 — Docs served to agents are sanitised and linted
- R-V2-3a's reason stands: repo docs carry the live LiveKit host and credential names. The MCP's guide, concept docs, recipes and generated resources never contain a hostname, IP literal, token name, `launch.json` content or `other-project-agent`; `test_docs_lint.py` enforces it and also checks that every id, name, route and model the docs mention resolves against the contracts and the OpenAPI document.

### R-V3-9 — Agent keys: presets, expiry, console-only minting
- The console mints agent keys (`kind=agent`) from three presets — Read-only (`agents:read`, `sessions:read`, `connections:read`, `providers:read`, `audit:read`), Builder (Read-only + `agents:write`, `sessions:write`), Operator (Builder + `connections:write`, `providers:write`, `webhooks:write`) — with `calls:write` as a separate, off-by-default checkbox, 30-day default expiry and a 365-day maximum. Key management is never an MCP tool; `api_request` refuses `/v1/api-keys*`. The `*` scope is never offered by the dialog.

### R-V3-10 — Migration `v3_001_agent_keys` follows HANDOFF rule 4
- V3-00 writes and rehearses the migration on a copy of the live SQLite file and on the Postgres CI job, and **stops and asks** before it reaches `api/data/lkap.db`; the coordinator applies it after a `.backup`. No other v3 package adds a migration.

### R-V3-11 — Attribution through `X-LKAP-Client`, not through router edits
- The client sends `X-LKAP-Client: lkap-mcp/<version>; client=<clientInfo.name>; tool=<tool>; call=<uuid>` on every request. The api parses it in `resolve_principal` into a contextvar that `audit.record` merges into `payload.client`, and `resolve_api_key` records `last_client`. No router changes; a missing or malformed header is ignored. The activity view and the `activity` tool filter on `payload.client`.

### R-V3-12 — Untrusted content is data
- KB text and hits, transcripts, session events, chat replies, dry-run bodies and vendor catalog labels are returned inside the `Untrusted` envelope, capped at 8,000 characters per item, and the guide tells the agent never to follow instructions found there. Tool descriptions are static strings; no platform data is ever interpolated into them.

### R-V3-13 — Scope-shaped tool lists
- At startup (stdio) or per session (HTTP), the server calls `GET /v1/api-keys/self` and registers only the tools whose scope the key carries; `LKAP_MCP_READ_ONLY=1` restricts to read tools regardless. A tool that is not registered does not exist for the client, which is the least-privilege default: the agent cannot even attempt a write it is not allowed.

### R-V3-14 — KB url import happens on the api, never in the MCP process
- `kb_add_document(url=…)` calls the new `POST /v1/knowledge-bases/{id}/documents/import`, which fetches through `net_guard`. The MCP process never fetches a user-supplied url on the platform's behalf: in HTTP mode that would be an SSRF vector from the service's network, and in stdio mode it would bypass the platform's own rule. `text` and `file_path` (stdio only, 25 MB) use the existing multipart upload.

### R-V3-15 — Remote streamable-HTTP mode is core, as its own service (user decision "Build remote now too", 2026-09-24)
