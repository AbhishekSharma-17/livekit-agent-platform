# LKAP v4 — delivery plan

Status: **started** (Fable 5.1, 2026-09-24) with the starter-template packages; later v4 packages append to §1 and §2. Owners: **Opus** for contracts, api and MCP; **Sonnet** for the console. Fable reviews each package against its acceptance and records rulings in §5.

Naming: v4 packages are **`V4-nn`**. Rulings are **`R-V4-n`** (§5) and amend the cards, `TEMPLATES.md` and `OPENROUTER.md`. Design: [`TEMPLATES.md`](TEMPLATES.md) (decisions D-V4-1…8, contracts, seeding algorithm, the catalogue, the dialog, tests); [`OPENROUTER.md`](OPENROUTER.md) (findings per modality with sources, decisions D-V4-9…13, the live check).

Definitions (unchanged from `../v3/PLAN-V3.md`):
- **Python gate** (inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test` (never `pnpm build` in `web/`; HANDOFF rule 6).
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts mcp/src/lkap_mcp/generated mcp/claude-plugin/skills/lkap/recipes`.
- **Exclusive ownership**: a package edits only the paths its card lists; anything else is a one-line ask in `docs/v4/_asks.md` (V4-01 creates it with the v3 format: **owner package** — file — the exact edit — who asked — status). The coordinator's decisions there are binding.
- **Migration discipline** (HANDOFF rule 4): none needed in these two packages (D-V4-3: no new column). A package that finds it needs one stops and files an ask.
- **Live rules** (HANDOFF rule 3): a scratch api on its own port and DB, a worker under a fresh agent name, never `lkap-agent`, never `other-project-agent`.
- **Path rules**: never create, read or name a path whose segment starts with `credentials` (HANDOFF rule 1) — say "provider keys", `provider_keys.py`, `/console/keys`; never read or write `.env*` (rule 2). The catalogue's prose names only fictional companies and `example.com` (R-V3-8).

## 4. Risks

- **`seed_config_from_manifest` assumptions.** It reads `manifest.default_panel` only through `effective_layout` (the config's `panel` stays default). Templates that compose blocks must store them (§4 step 2) or block tools will not register. Mitigated by the flow-reference test, which fails if `request_form`/`table_append` are not allowed for `receptionist`.
- **Placeholder tool URLs** on `receptionist`: an unedited starter reports "couldn't reach the booking system" at runtime. Accepted (R-V4-4); the next step and the dry run make the fix one edit.
- **Long JSON flows** are easy to break by hand. The test validates every one; the MCP `agent_flow_validate` recipe covers edits after creation.
- **Console before api**: a console upgraded before its api sees a 404 on `templates`; the fallback to `packs` keeps the dialog working with derived tiles.
- **Two "Acme"s** in seeds (dental practice, meter product) are fictional by design; the doc lint keeps real hostnames out.

## 5. Rulings

IDs `R-V4-n`, recorded here so they outlive the chat. They amend the cards and `TEMPLATES.md`.

### R-V4-1 — Starters are configuration on a pack; packs stay code (user decision, 2026-09-24)
- The user's rule: insurance was one use case, not the starter pack. The gallery lists **starter templates**, data-only presets on the `generic` pack (`TEMPLATES.md` D-V4-1), and code packs appear only through a template (`insurance_claim`, category "example", last). No new code pack is created for a starter; a starter that needs code is a pack plus a template that names it.

### R-V4-2 — The New agent flow is a dialog; `UI_UX_SPEC.md` §4.2 is amended
- §4.2's "a page, not a modal" is withdrawn. The flow is a `Dialog` (`size="xl"`) opened from every "New agent" trigger; `/console/agents/new` stays as a deep link that opens the dialog over the agents list (`?template=` preselects). R-V3-2 (no drawers or sheets) applies unchanged. V4-02 replaces §4.2's text with a pointer to `TEMPLATES.md` §6.

### R-V4-3 — No template column, no migration; `pack_id` alone is the pack's derived starter
- `AgentCreate.template_id` is resolved at create time and remembered only in the version note and the log. When `template_id` is present, `pack_id` is ignored (it defaults to `generic` and the MCP tool always sends it; a "differs → 422" rule would reject every MCP create from a code-pack starter). `POST /v1/agents` with `pack_id` and no `template_id` keeps working and is defined as creating from the derived `pack:<id>` starter, so both paths run one seeding function. A column is Phase 2.

### R-V4-4 — Seeding gates, never fails, and ships no transfer targets
- A starter must create on any workspace: `capabilities.dtmf` is set only when the connection reports SIP, `recording.enabled` only when Egress and a storage config exist, and the catalogue ships **no** `telephony.transfer_targets` (the dialing policy is workspace state, R-V2-23). Placeholder HTTP tool URLs on `example.com` are allowed in the catalogue; they fail as ordinary tool errors until edited. The console explains what was gated in the create toast by comparing the starter with the created config; the api response shape does not change.

### R-V4-5 — The catalogue is tested, not trusted
- `api/tests/test_templates.py` pins the id list and derives every claim the gallery makes (required keys, vision model, tool references, block configs, seed files) from the contracts and the registry. A malformed catalogue entry is a startup error, not a skipped entry. The MCP doc lint resolves template ids in recipes against the live catalogue.

### R-V4-6 — Templates live in the api package; the MCP reads them live
- Models in `lkap_contracts`, data under `lkap_api/templates/catalog/`, served by `GET /v1/templates`; the MCP's `lkap://templates` is a live read like `lkap://packs`. No export-script copy of the catalogue; recipes reach the plugin through the existing copy step (G4).

### R-V4-7 — One vendor key may serve several registry entries: `credential_provider` (2026-09-25)
- A `ProviderSpec` may name another entry as its **credential home**; a credential row is stored under the home and every lookup (validation, seeding, catalog fetch, default-credential setting, key listing, template key requirements, the console picker) compares against `credential_home(spec)`. The home must exist, have no home of its own and declare the same secret field names. V4-03 sets it only on the four non-LLM OpenRouter entries (home `openrouter-llm`). Existing multi-entry vendors (OpenAI, Google, Deepgram, ElevenLabs, Cartesia) are not migrated in v4 — merging their existing rows needs a data migration and is an ask, not a side effect. Rejected: per-vendor key rows the user pastes N times (what the user asked to avoid), and a kind-less "vendor key" entry (invisible to the per-kind pickers).

### R-V4-8 — What OpenRouter may fill, and the honest defaults (`OPENROUTER.md` §1)
- OpenRouter fills `llm`, `workflow_llm`, `qa_llm` (worker and api-process judge), flow node LLM overrides, `stt`, `tts`, the KB embedder and `image_gen`. It never fills `realtime` (no speech-to-speech or websocket endpoint exists), and no registry entry may say otherwise. `openrouter-stt` and `openrouter-tts` ship as `available` on the slim image with a `notes` caveat rendered in the slot editor (V4-04): STT is batch (no interim results, per-turn upload after end-of-speech), TTS is non-streaming like `openai-tts`. The recommended "one key" voice stack is OpenRouter for the LLM family plus LiveKit Inference STT/TTS. Defaults are chosen from the live catalogue, not the plugin: `openai/gpt-4.1-mini` (not `openrouter/auto`, which is not tool-capable), `openai/gpt-4o-mini-transcribe`, `google/gemini-3.8-flash-tts`/`Kore` (the plugin's `gpt-4o-mini-tts`/`ash` do not exist on OpenRouter), `openai/text-embedding-3-small` only (1536 dims), `openai/gpt-image-1`. `provider.require_parameters` defaults to true in the factory so tool-bearing requests never route to an endpoint without tools; an admin may turn it off per agent.

### R-V4-9 — The credential test must fail on a bad key; `/models` alone is not a test
- OpenRouter's `GET /api/v1/models` is public (a bogus key gets 200), so the OpenRouter adapter probes `GET /api/v1/key` before listing; a non-2xx probe is a failed test and no catalog call is made. General rule for any future adapter: the endpoint used as `ProviderSpec.test` must reject a wrong key (OpenAI's `/v1/models` does; verify with a bogus key before wiring a vendor). The KB embedder stays platform-level (`LKAP_EMBEDDER`, D-V4-13), now in the `<provider_id>:<credential_id>` form for any OpenAI-shaped embedding entry; a per-workspace embedder is out of scope.
