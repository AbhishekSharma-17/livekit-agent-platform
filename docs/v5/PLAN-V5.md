# LKAP v5 — master plan: the research backlog as work packages

Status: **planned** (Fable 5.1, 2026-09-25). This plan turns the three v4 research documents (`docs/research-v4/{tools-and-integrations,knowledge-and-memory,panels-and-capabilities}.md`) into sequenced packages the coordinator runs autonomously: Fable decides, Opus and Sonnet implement, about 3–4 agents at a time, one commit and push per package. Every open question the research left for the user is answered here with a **default** (§1); the user can override any of them later by a ruling, and the affected card says what changes.

Naming: packages are **`V5-nn`**, decisions are **`D-V5-n`** (§1), rulings made while the plan runs are **`R-V5-n`** (§7, appended by Fable). Cards are in §3, the security checkpoint in §4, what the user must provide in §5, the status table in §6.

## 0. Ground rules, prerequisites and ownership

### 0.1 Definitions (verbatim from `docs/v4/PLAN-V4.md`, so this document is self-contained)

- **Python gate** (inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test` (never `pnpm build` in `web/`; HANDOFF rule 6).
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts mcp/src/lkap_mcp/generated mcp/claude-plugin/skills/lkap/recipes`.
- **Exclusive ownership**: a package edits only the paths its card lists; anything else is a one-line ask in `docs/v5/_asks.md` (V5-01 creates it with the v3/v4 format: **owner package** — file — the exact edit — who asked — status). The coordinator's decisions there are binding; design questions go to Fable.
- **Live rules** (HANDOFF rule 3): a scratch api on its own port and DB, a worker under a fresh agent name, never `lkap-agent`, never `other-project-agent`; a Builder key minted for the run and revoked at the end (R-V4-17); `Demo — ` objects only, cleaned up.
- **Path rules**: never create, read or name a path whose segment starts with `credentials` (HANDOFF rule 1) — say "provider keys", `provider_keys.py`, `/console/keys`; never read or write `.env*` (rule 2). Prose names only fictional companies and `example.com` (R-V3-8). The repository is public: no user names, no machine paths, no real hostnames, no key values in any file, log line or brief.
- **UI rules**: dialogs only, never a drawer or sheet (R-V3-2: no `@/components/ui/sheet` import in any touched file); **no internal jargon in UI copy** (no "RRF", "tsvector", "FTS5", "CIMD", "DCR", "PKCE", "HMAC", "pgvector", "RFC" in a string the user sees — say "Hybrid search", "Connect", "Re-connect", "Pseudonymous id"); mobile at 375 px with no horizontal page scroll; axe green on every new dialog.
- **Compatibility rule**: a new config field must not change what an existing published agent does. Defaults are chosen so every fixture in `api/tests/fixtures` and the eight V4-06 `Demo — ` agents validate and behave unchanged; each package that adds a field pins that with a test ("an agent saved before this field exists resolves to the same `ResolvedAgentConfig` behaviour").
- **Contracts rules**: every contracts package may additively edit `contracts/src/lkap_contracts/{__init__,export}.py` (re-exports and model registration) without listing them; generated files (`contracts/generated/**`, `web/src/contracts/lkap-contracts.d.ts`, `mcp/src/lkap_mcp/generated/**`) are never hand-merged — after any rebase the package re-runs the contracts gate and commits the regeneration, and two packages never regenerate in the same commit window (the coordinator serialises contracts commits within a wave in the listed start order).
- **New block types**: a contracts package that adds a `BlockType` member also adds the **minimal `web/src/panels/blocks/catalog.ts` entry** (label, `configFields` equal to the schema's keys, no renderer — the generic panel shows "not rendered yet"), so `pnpm typecheck` (the catalog is keyed by `BlockType`) and `web/tests/block-config-parity.test.ts` stay green from the contracts commit; the console package adds the renderer, previews and fixtures.
- **MCP docs rule**: `mcp/src/lkap_mcp/docs/**` is linted for hostnames and tokens (`mcp/tests/test_docs_lint.py`): concept docs and recipes name vendors, never URLs (V4-03's rule); every card that adds a doc there inherits it.
- **Commit rule**: one commit per package once its gates are green, pushed to the remote (`origin`, named generically in docs), with the attribution line the session reminder gives. A package whose live check is deferred still commits; the status table (§6) records "live: deferred (needs …)".

## 1. Decisions (answers to every open question in the three research docs)

Each decision: **default** → one-line rationale. "Override" says what a later ruling would change. Numbering groups: T = `tools-and-integrations.md` §6, K = `knowledge-and-memory.md` §8, P = `panels-and-capabilities.md` §7, X = cross-cutting choices this plan had to make.

### Tools and integrations (T)

- **D-V5-1 (T1) Composio first, Arcade later; pricing verified at sign-up, not assumed.** Default: build the "tool provider" connection with a provider-agnostic adapter interface and one adapter, `composio`; `arcade` is a stub adapter that raises "not available yet" and is not shown in the console. Rationale: the largest catalogue, a REST execute endpoint that fits the HTTP-tool execution model, an MIT SDK; the free-tier figure (100k vs 20k calls) is checked in the live check and recorded, since no key exists today. The full Composio design (connect from the console, actions as tools, the app MCP server, Tool Router with its meta tools, guards) is `docs/v5/COMPOSIO.md` (D-V5-C1 … C12), and it is the **first** integrations work in the plan. Override: an Arcade key plus a ruling adds the second adapter (V5-18's interface already allows it).
- **D-V5-2 (T2) Tenants bring their own vendor OAuth apps (the `preregistered` path); LKAP-owned vendor apps are a hosted-plan feature, not v5.** Rationale: there is no hosted deployment and no production yet; owning Slack/Google/HubSpot apps makes LKAP the data processor and needs vendor app review. The console shows the redirect URI to paste into the vendor's app settings. Override: a hosted plan adds a per-vendor "LKAP-managed app" option with `client_id`/`client_secret` from platform settings.
- **D-V5-3 (T3) Public origin: `LKAP_PUBLIC_BASE_URL` stays the one public origin; in local dev the OAuth callback is `http://localhost:<port>/v1/oauth/mcp/callback` (the spec allows loopback redirects) and CIMD is unavailable (it needs a public HTTPS document), so registration falls through to DCR or pre-registered.** Rationale: local only for now. The api mounts `/v1/oauth/mcp/*` on its own sub-router so a later Caddy rule can expose exactly that path when the console is private. Override: a public HTTPS origin turns CIMD on with no code change.
- **D-V5-4 (T4) MCP host allowlist: a separate `LKAP_MCP_ALLOWED_HOSTS`; empty means "any public HTTPS host that passes `net_guard`"; non-empty is a ceiling exactly like the HTTP-tool list.** Rationale: reusing `LKAP_HTTP_TOOL_ALLOWED_HOSTS` fails closed for every preset whenever it is unset (two empty lists allow nothing). Non-HTTPS MCP URLs are refused outside `LKAP_ENV=dev` loopback. Override: one setting (`LKAP_MCP_ALLOWED_HOSTS=@http`) makes it alias the HTTP list.
- **D-V5-5 (T5) Per-end-user connections are out of scope; `subject ∈ {workspace, agent}` is the whole v5 scope.** Rationale: telephony callers are unauthenticated; the systems being read belong to the business. The `subject` column exists so `user:<id>` can be added without a migration.
- **D-V5-6 (T6) Payments by phone: link-only. No card capture, no `collect_card_by_dtmf`, no recording pause.** Rationale: PCI scope and no verified "pause Egress" primitive. The `link` block (V5-43/44) carries Stripe Checkout / Payment Links and e-sign; on voice-only channels the link goes by SMS when `send_sms` is configured.
- **D-V5-7 (T7) Web search: a `web_search` provider kind with two registry entries, `tavily-search` (default suggestion) and `brave-search`; one built-in tool `web_search` bound through `ToolsConfig.web_search: ProviderRef | None`.** Rationale: Tavily's free tier needs no card; Brave is the low-latency alternative; a provider slot reuses the existing key vault, catalogue and test-call machinery instead of two tools. Override: adding Exa is one registry entry plus an adapter.
- **D-V5-8 (T8) Weather: skipped.** Rationale: Open-Meteo's free tier is non-commercial and the demos are company material (R-V4-18 already excluded it); no key for a commercial vendor. Override: a paid key plus a ruling adds `get_weather` as an HTTP tool template.
- **D-V5-9 (T9) Google Workspace MCP: shipped as a preset marked "needs your own OAuth client and Developer Preview membership", never live-checked in v5; Calendar/Gmail reach the agent through Composio (V5-18) or a Cal.com template (V5-24) instead.** Rationale: no membership, no key.
- **D-V5-10 (T10) Zendesk and Salesforce: not shipped as presets.** They stay in `mcp_presets.json` under `candidates` with `status: "unverified"` and are hidden by the console until a ruling promotes them. Rationale: both endpoints are third-party reports only.
- **D-V5-11 (T11) Upgrade cadence: track, do not fork.** The `GuardedMCPServerHTTP` subclass keeps its `_create_http_client` override; a tripwire test asserts `MCPServerHTTP.__init__` has no `auth` parameter and `livekit-agents` still pins `mcp<2`, so the release that changes either fails a test and a package shrinks the subclass. The api's OAuth helpers are written against the stateless `mcp.client.auth.utils` functions so the api can move to `mcp` 2.x independently of the worker.

### Knowledge and memory (K)

- **D-V5-12 (K1) Prod topology: single host for now; P0 ships on LanceDB; pgvector lands in V5-13 as the default whenever `LKAP_DATABASE_URL` is Postgres, and that package also closes the two-writer risk.** Rationale: there is no production deployment; the research measured quality, not latency, as the problem. Until V5-13 lands, the prod compose keeps `jobs` as the only LanceDB writer by moving KB/document deletes onto the job queue (V5-04 does this: deletes enqueue `KB_DELETE`, `inline` in dev).
- **D-V5-13 (K2) The default stays vendor-key-free in every mode: `fastembed` `bge-small-en-v1.5` + LanceDB (SQLite) or pgvector (Postgres).** A hosted embedder is a per-KB choice (`knowledge_bases.embedder_model`, credential from the vault; `openrouter-embedding` works with the key the user has). Re-embedding is a job (`kb_reindex`) shipped in V5-13 because the pgvector migration needs it anyway.
- **D-V5-14 (K3) Corpus assumption: policy PDFs with tables plus Markdown/FAQ text, hundreds of pages per KB.** P0 parsing = MarkItDown for DOCX/PPTX/XLSX/HTML and pypdf for PDF; Docling is deferred (heavy dependency set) to an optional extra `lkap-api[docling]` in a later plan. OCR: not in v5.
- **D-V5-15 (K4) Languages: English and Hindi.** The default embedder stays English; a KB flagged `language != "en"` must pick a multilingual embedder (`openrouter-embedding` with a multilingual model, or `snowflake-arctic-embed-m` when fastembed adds a multilingual model); the console warns. Hybrid lexical search covers Hindi transliterations poorly and the eval harness (V5-05) is where that is measured, not assumed.
- **D-V5-16 (K5) Bring-your-own store order: Qdrant, Pinecone, Weaviate (Turbopuffer deferred).** Rationale: the research's order; no prospect data says otherwise. All three ship with fakes and unit tests; each live check "needs <key>".
- **D-V5-17 (K6) Memory: Mem0 OSS, opt-in per agent (`memory.enabled=false` by default), scope per agent, retention 90 days by default, keyed by an HMAC of the caller identity with a per-workspace key in the vault, read once before the greeting, written once at session end by the summary job, an erasure route, no per-turn calls.** Backend by database: pgvector on Postgres; on SQLite dev the Mem0 vector store is **Qdrant in local (file) mode** under `LKAP_DATA_DIR/memory` — the implementer confirms the embedded-path configuration against the `mem0ai` docs before pinning the dependency and files an ask if it is not supported. Extraction LLM = the agent's configured LLM through an OpenAI-compatible base URL (OpenRouter works with the stored key). Zep Cloud is a later `MemoryStore` backend, not v5. Regulatory posture: consent line optional per agent, erasure and purge routes mandatory.
- **D-V5-18 (K7) Preemptive generation stays enabled by default (the SDK default).** The existing rule (auto-inject with KBs turns it off unless the config sets it) stands; V5-06's pre-fetch spike tries to land the injection before the SDK snapshot; if the spike fails, the rule stands and the card says so.
- **D-V5-19 (K8) Hosted rerank: local only by default; Cohere and Voyage adapters behind the `Reranker` Protocol as knowledge-connection kinds, tool path only, no spend cap beyond the cost lines.** Rationale: the local cross-encoder is ~55 ms for 10 passages and free; hosted rerank is a tenant's choice with its own key. Each hosted rerank call is costed through a `pricing.PRICES` row when V4-15's `PriceQuote` exists (else "no price").
- **D-V5-20 (K9) Graph RAG: deferred.** The `ExternalRetriever` Protocol (V5-13) is the hook; LightRAG/Neo4j adapters are not in v5.

### Panels and capabilities (P)

- **D-V5-21 (P1) Warm transfer is available only on LiveKit Cloud connections; self-hosted connections fall back to cold transfer automatically, with a console warning on the agent and the transfer summary recorded on the call row (not whispered).** Rationale: `MoveParticipant` is Cloud-only. Override: none needed.
- **D-V5-22 (P2) Jurisdiction defaults: AI disclosure always on; recording consent required by default when recording is enabled; three text presets (`eu`, `in`, `us`) selectable per workspace under Settings → Compliance, default `in`; the US two-party-consent list and TRAI specifics are marked "confirm with counsel" in the UI and never encoded as a state list.** Rationale: the EU AI Act Art. 50 applies; India is the user's market; the safest default is to ask.
- **D-V5-23 (P3) Languages: Hindi/English code-switching is the target (Deepgram `multi`); Marathi/Tamil/Telugu are out of v5 (the design leaves `languages[]` open for Gladia/Google later).** Live check: through LiveKit Inference `deepgram/nova-3` with `language=multi` **if the gateway accepts it (unverified)**, else "needs Deepgram key".
- **D-V5-24 (P4) Human agents are not a new role.** Supervisors are console users with `builder` or above holding a new scope `sessions:listen` (granted to `builder`+ by default); listen-in tokens are per session, hidden, `canPublish=false`, 15-minute TTL; audio takeover is deferred. Rationale: the role matrix stays at four roles; a scope is a smaller change than a principal.
- **D-V5-25 (P5) Voice cloning: catalog-only (list vendor-cloned voices through the existing dynamic voice catalogs); console cloning is not in v5.**
- **D-V5-26 (P6) Payments and identity verification: link-only (same as D-V5-6); IDV vendors (Stripe Identity, Persona) are `link` kinds, never embedded.**
- **D-V5-27 (P7) MCP Apps embeds: parked; no `embed` block in v5.**
- **D-V5-28 (P8) Map: deferred (no tile-provider key, no insurance pull).**
- **D-V5-29 (P9) Simulation runner: LKAP's own persona runner in the api over the v3 text-session transport; judging in the api through `qa/llm_client.py` with judge prompts modelled on the SDK's built-in judges (task completion, tool use, safety, relevancy, accuracy).** Rationale: the api has no `livekit-agents` dependency (verified in `api/pyproject.toml`) and should not gain one; the worker is untouched, which keeps the runner working on any connection. `lk agent simulate` and external vendors are not v5.
- **D-V5-30 (P10) Noise-cancellation spend: opt-in per agent; the `telephony` conversation preset turns the telephony-tuned variant on and shows the per-minute price.**
- **D-V5-31 (P11) Avatar recording stays audio-only; a `recording.video: bool` flag is deferred.**
- **D-V5-32 (P12) Release upgrade: V4-14 lands 1.8.3 before any V5 agent package; V5 pins nothing newer.**

### Cross-cutting choices this plan makes (X)

- **D-V5-33 `flow_progress` becomes `steps` by renderer aliasing, not by a config migration.** A `custom` block with `kind == "flow_progress"` is rendered by the `steps` renderer with `source="flow"`; new agents get a real `steps` block; `lkap_contracts.migrate` is untouched (no rewrite of every published agent).
- **D-V5-34 Every blocking request tool (`request_choice`, `request_consent`, `request_upload`, `request_slot`, `request_signature`) is on `NEVER_BACKGROUND_TOOLS` (V4-12's list) and cancels on barge-in (`cancelled` status, `None` result).** Barge-in cancels only generic `request`-method requests; the legacy `form` path keeps today's behaviour (R-V5-1).
- **D-V5-35 Caller bytes are a first-class session asset.** The api gains `session_assets` (`v5_002`) and `POST /internal/v1/sessions/{id}/assets` (multipart, service token, size and mime checked again server-side); files live in the configured storage backend under `sessions/<id>/`; the console serves them through the existing signed-URL path. Uploads, signatures and pinned frames all use it (pinned frames migrate from the in-envelope `AssetRef` bytes-only path to "bytes stored, ref in the envelope" in V5-19).
- **D-V5-36 Cal.com booking ships as an HTTP-tool template set (six definitions with `{{ secret.CAL_API_KEY }}` and the event-type id as an argument default), not a pack.** Rationale: zero worker code, the same editor, a live check that needs only a Cal.com key. The research's "first-class pack" is the later step if templates prove too thin.
- **D-V5-37 Text is not stored in vector stores that cannot return it; the SQL row stays the source of truth for chunk text in every backend**, so BYO connectors carry only `id, vector, kb_id, document_id` plus a small payload and the join happens in the api (the `stores_text` capability is used only to skip the join).
- **D-V5-38 The security checkpoint (V5-26) is a gate**: no E/F/G package (V5-29 onward) starts before Fable's sign-off, and its fix package (V5-27) merges first.

## 2. Packages and waves (one line each)

Themes: **A** conversation quality · **B** knowledge · **C** tools and integrations · **D** panels · **E** capabilities · **F** memory · **G** the rest of the roadmaps · **S** security · **X** closing. Owner: **Opus** for contracts, api, agent and MCP; **Sonnet** for the console. "Worktree" marks api/agent-heavy packages the coordinator runs in an isolated worktree. A wave is a dependency group, not a concurrency promise: **at most four packages run at once**; within a wave the coordinator starts them in the listed order and starts the next as one finishes. Console packages start from their contracts package's **contracts commit** (the regenerated `.d.ts`), as in v4, and never hand-edit generated files.

## 4. Security review checkpoint (V5-26 / V5-27; the gate of D-V5-38)

Modelled on `docs/v2/REVIEW-V2.md` (V2-21): a findings table (`ID · Sev · Finding · Evidence · Status · Test`), a dependency audit, then Fable's sign-off with conditions. It runs after the integrations wave has merged and **before** any E/F/G package starts. The reviewer works through this checklist; each row becomes a table row that says "pass" with the evidence or names a finding.

**Composio (V5-18, V5-22, V5-47, V5-48)**
1. The API key exists only in the vault; `key/test` never persists or logs the pasted value; rotate keeps the row; the worker sees the key only through the `{{ secret }}` substitution over `/internal/v1`.
2. The connect callback: nonce checked in constant time, single use, 10-minute expiry; `connected_account_id` must equal the one recorded at link time; the account's `user_id` and `ACTIVE` status verified against Composio before any row is written; nothing from the query string is trusted alone; the redirect carries no identifiers beyond `connect=ok|error`.
3. Vendor secrets typed in the Connect dialog (client secret, API key) are forwarded once and never stored, logged or echoed (DB, audit, structlog, MCP results).
4. Every Composio URL passes `net_guard`; origin-tagged MCP definitions are pinned to `backend.composio.dev` and `https` at save and at connect; `LKAP_MCP_ALLOWED_HOSTS` semantics hold once V5-09 lands.
5. Execution policy: `COMPOSIO_MULTI_EXECUTE_TOOL`, `COMPOSIO_MANAGE_CONNECTIONS`, `COMPOSIO_WAIT_FOR_CONNECTIONS` never background; `MANAGE`/`WAIT` and the remote bash/workbench/skill meta tools excluded from `allowed_tools` by default; destructive actions need the explicit flag and are always blocking; no connect link is ever spoken (the error mapping strips URLs).
6. Subject scoping: a workspace can never execute with another workspace's `user_id`; `agent:<id>` connections are usable only by that agent; deleting a connection pauses its tools.

**MCP OAuth (V5-09, V5-14, V5-16, V5-21)**
7. Callback: constant-time `state`, single use, expiry; the RFC 9207 table; PKCE S256 refused when unsupported; no token, code or `state` in logs (processor test); the redirect carries no token material.
8. Discovery: every server-supplied URL (`resource_metadata`, `authorization_servers[]`, metadata endpoints, `registration_endpoint`, `token_endpoint`, `revocation_endpoint`, `registration_client_uri`) passes `net_guard.validate_url`; AS endpoints are `https` outside dev loopback; 3xx is an error.
9. Refresh tokens and client secrets never leave the api; the worker bearer is minutes-lived; refresh under a lock; `needs_reauth` on `invalid_grant`; revoke on delete.
10. `_check_payload`: exactly the intended bindings (`mcp-oauth` and `http-tool-secret` on MCP definitions, the two Composio bindings), nothing wider; the `admin` + `providers:write` gate unchanged.
11. `LKAP_MCP_ALLOWED_HOSTS`: empty = any public HTTPS host under `net_guard` (documented), non-empty = a ceiling, enforced on the api and the worker; `http` refused outside dev.

**Request blocks and caller bytes (V5-02, V5-03, V5-08, V5-15, V5-19, V5-23)**
12. `request_block`: timeout, single pending request per block, cancel on barge-in, `None` on every failure path; realtime mode delivers as a background result.
13. Uploads: size, mime and count enforced worker-side before any api call and again server-side; sha256 recorded; bytes in the storage backend under the session; signed, workspace-scoped downloads; retention with the session; no path traversal from `name`.
14. `describe_asset` output is treated as untrusted model input (no instruction following from OCR text — the tool description says so and the schema constrains the answer).
15. Consent: the `text_hash` matches the exact wording; Egress never starts before acceptance when required; a declined required consent leaves no recording.

**Curated tools (V5-25, V5-28)**
16. `calculate` has no `eval`, names or attribute access; `fetch_url` allowlist plus the private-range guard; `send_sms` destination policy (caller or labelled targets only); `notify_team` never posts the transcript by default; vendor keys only via the vault.

**Cross-cutting**
17. Dependency audit of every new package (`markitdown`, `mcp` on the api, `pgvector`, the optional extras): pinned, licences compatible with a public template (no AGPL/SSPL/BSL in the default install), advisories checked.
18. No user name, machine path, real hostname or key value in any doc, brief, fixture or test; the public-repo grep from V4 re-run.
