## 2. Speech: registry truth and the recommended stacks

**The problem.** OpenRouter's speech endpoints are request/response: a transcription takes a whole file and a speech request answers one POST per input. LKAP wrapped them in the SDK's `StreamAdapter` (one WAV per utterance, one request per sentence), which measured 2–4 s from end of speech to first audio against about 0.7 s on LiveKit Inference (`docs/research-v6/openrouter-audio.md`). They cannot be live-call speech; OpenRouter stays the LLM family (the LLM slot, `workflow_llm`, the QA judge, embeddings, image generation) — D-V6-1.

**Streaming is a registry capability (V6-02).** `ProviderCapabilities` gained `streaming` (read from each plugin's `STTCapabilities`/`TTSCapabilities` at 1.8.3; `null` = not recorded), `streaming_field` (the boolean that turns it on: `openai-stt.use_realtime`, `rime-tts.use_websocket`), `streaming_note` (a condition in plain words, such as Google TTS with Chirp 3 HD voices) and `end_of_turn` (STT only). A parity test requires every available speech entry to record `streaming` or a note. The non-streaming list at 1.8.3 is longer than D-V6-2 guessed (ask #15: AWS Polly, LMNT, CAMB.AI, Simplismart, Clova, Mistral and ElevenLabs STT on their default models were added). The api emits a **tip**, never an error, for a cascaded voice pipeline on a non-streaming transcriber or voice (`stt_not_streaming`, `tts_not_streaming`, naming the fix).

**Defaults without changing stored agents (D-V6-4, U-V6-2).** Vendor-deprecated plugin defaults moved (`inworld-tts-1.5-max` → `inworld-tts-2`, `speech-02-turbo` → `speech-2.8-turbo`), the old ids kept with `ModelSpec.deprecated` so stored references resolve with a warning. Newer defaults changed only `default_model` (`cartesia-tts` Sonic 3.6, `elevenlabs-tts` Flash v2.5). The behaviour switches are new fields with **no default**: `FieldSpec.recommended` is what the console pre-selects for a new agent or a newly picked provider, so a stored agent resolves to the same keyword arguments (pinned by a compatibility test). The ElevenLabs field is `encoding`, not the card's `output_format` (ask #14: the 1.8.3 plugin's name).

**Registry changes.** `deepgram-flux-stt` is its own entry on `STTv2` with `end_of_turn`; the worker then runs `turn_detection="stt"` in place of the platform's default detector, and an explicitly configured turn-detection slot still wins (ask #17). `flux-general-en` under `deepgram-stt` is a validator error naming the Flux entry (the pointer lives in `DEEPGRAM_FLUX_MOVED_MESSAGE`, not a registry note, ask #18). `fireworksai-stt` is `removed` (the vendor stopped the service on 2026-06-10); since S6-23 a stored reference fails the session with the vendor's reason, not an import error. `minimax-tts` ships from `livekit-plugins-minimax-ai` on the full image (ask #13). The three `livekit-inference-*` model lists were refreshed against LiveKit's docs table on the day (D-V6-8), except `inworld/inworld-tts-2-flash`, left out until it has a price row (ask #12). The OpenRouter PCM `rate`/`channels` clamp (#331) is in `providers/openrouter.py`.

**The console (V6-03).** Pickers show "Streams" or "Waits for the whole sentence"; OpenRouter speech rows say "not for live calls"; a "Recommended" badge marks LiveKit Inference on Cloud connections and the Deepgram + Cartesia pair on self-hosted ones (D-V6-3). The stacks and the Inference credits line are **dated console constants** (`RECOMMENDED_STACK`, `INFERENCE_CREDITS_LINE` in `provider-meta.ts`, as of 2026-09-28), not registry fields (asks #16, #42). "Pre-selected in Create agent" reads as: Create agent posts no pipeline (the starter seeds it, and every starter already seeds LiveKit Inference), and a freshly picked provider takes `recommended` over `default` (ask #43, confirmed by R-V6-5).

**Recommended streaming stacks (as shipped).**

| Connection | Transcriber | LLM | Voice |
|---|---|---|---|
| LiveKit Cloud | LiveKit Inference `deepgram/nova-3` | LiveKit Inference (`google/gemma-4-31b-it` by default; `google/gemini-3.5-flash` when the camera is on) | LiveKit Inference `inworld/inworld-tts-2` |
| Self-hosted (own keys) | Deepgram Nova-3 (Flux for built-in end-of-turn) | any (OpenRouter is fine here) | Cartesia Sonic (ElevenLabs Flash or Deepgram Aura-2 as alternatives) |

No multi-model gateway is recommended for audio: none has a streaming LiveKit plugin (`docs/research-v6/gateways-audio.md`); Together AI's streaming speech needs a custom plugin, an unscheduled spike (D-V6-7).

## 3. LiveKit Inference from a self-hosted server

**What the research established (D-V6-10; SDK source, not tested live).** Inference is a feature of a LiveKit **Cloud project**: the SDK mints its own JWT from `LIVEKIT_INFERENCE_API_KEY/SECRET` (else `LIVEKIT_API_KEY/SECRET`) and sends it to LiveKit's Inference gateway whatever `LIVEKIT_URL` says; no room is needed (LKAP's model "Test" button already calls it with none); billing is pay-as-you-go on top of monthly credits (Build $2.50 as a hard cap). LiveKit's self-hosting comparison says "N/A" for built-in inference. In LKAP a self-hosted connection is still hard-wired to `inference_available=False`, and the validators refuse Inference slots on it.

**Not built in v6.** D-V6-11's per-connection "LiveKit Cloud Inference credentials" (migration `v6_001_inference_credentials`, the worker env pair, the console switch with its plain-words notice) is gated on the V6-04 spike's verdict (R-V6-1), and the user deferred the spike (U-V6-1: it needs a free LiveKit Build project and Docker). V6-05 and V6-09 are therefore `deferred`, no migration `v6_001` exists, and the D-V6-13 workaround (`LKAP_SUPERVISOR_PASSTHROUGH_ENV` carrying the Inference pair) is **not** a supported path: it would be shared by every pool on the host and the validators still refuse the slots (RUNBOOK §9.9). When the spike runs, the V6-05 card and migration ledger in `PLAN-V6.md` apply as written; `v6_001` then chains after `v6_002_datasets` (ask #102).

## 4. OpenRouter prices (V6-01)

Two defects made every OpenRouter model show "no price". **A:** the live price sheet selected only unkeyed catalogue rows, and every OpenRouter row is keyed by the credential that fetched it; `load_live_sheets` now adds the workspace's default (else only) OpenRouter credential when a reference carries none, resolved the way the cost code resolves the key and scoped to the workspace (S5-27), so the picker, estimates and actuals all price. **B:** speech was priced from `pricing.prompt` for every model, but OpenRouter's unit varies per model. `pricing.openrouter_unit(meta, kind)` classifies each catalogue item (per second, per token, per character, unknown); token-billed transcription is priced at 40 audio tokens a second (`OPENROUTER_AUDIO_TOKENS_PER_S` in `api/src/lkap_api/costs/assumptions.py`, derived from OpenAI's per-minute estimates, ask #3); Gemini TTS audio-out comes from `audio_output`, else `completion`. A speech price above $1 per audio minute or $1 per 1,000 characters is "no price (unit unknown)", never a figure; since V6-21 (S6-24) any live catalogue price above $1 a unit is refused too, and a reconciled `total_cost` above $10,000 fails. Reconciliation (`jobs/reconcile.py`) sums STT/TTS generation ids when the worker reports them; today it reports none for OpenRouter speech (asks #1, #4, open), so that path is dormant. `docs/v4/COSTS.md` carries the unit table.

## 5. Generic panel primitives and caller edits (V6-06, V6-10)

The insurance pack kept four panel moves to itself; they are now built-ins any agent gets from its panel (D-V6-19):

- `set_checklist(items, keep_done?)` and `check_item(item_id, done, hint?)` over the envelope checklist; registered with a checklist block.
- `generate_image(prompt, caption?, block_id?)` on the `image_gen` slot. It registers only when a picture model resolves **and** the panel has a `gallery` block (ask #22: the slot-only rule would have given every insurance agent a second, always-refusing drawing tool); the picture is streamed on `lkap.ui.asset`, stored as a session asset of kind `frame` with `meta.source="generated"`, and dropped (nothing streamed) above the upload size cap (S6-25). The api warns when a picture model sits on a composite panel with blocks but no gallery. Style goes in the prompt (ask #21).
- `push_note(block_id?)` and `NoteItem.block_id`: a note shown in one block's margin.
- On `realtime` and `half_cascade` pipelines these tools answer nothing, so the model does not stop to talk about them (ask #23).

**Structured arguments (V6-30).** Every panel tool whose parameter is a list of objects (`set_details`, `notebook_write`, `cart_set`, `show_chart`, `draw_on_canvas`, `set_checklist`, `set_steps`, `show_cards`, `request_form`, `request_choice`, `request_slot`, `describe_asset`) also reads that list, or an item, sent as JSON text (`agent/src/lkap_agent/tools/json_args.py`): strict `json.loads`, at most 32,000 characters, a `null` inside meaning the default, then the same validation as before; other text is refused with the expected shape. The five most used carry a one-line example call in their description. The root cause was upstream: `openrouter-llm` tool schemas now go out with every `$ref` written in place (`providers/openrouter_llm.py`), because OpenRouter's translation for Gemini showed the model an array of strings for an array of `$ref` objects. A batch of `silent_reply` tools in which a call failed keeps its reply. `search_knowledge` is registered only when `knowledge.kb_ids` names a knowledge base.

**Caller edits reach the model.** A `details` or `checklist` block with `caller_can_edit` (and, since V6-08, a `notebook` with `caller_can_write`; the flags are `CALLER_EDIT_FLAGS`) lets the caller change a value or tick an item on screen. The page sends `block_action {name: "edit"}`; the worker checks the caller's identity (S5-23), validates a strict payload (500 characters; since S6-7 ids and keys have the `NOTEBOOK_ID_PATTERN` shape), applies it as one patch through the state model, records the event without the value, tells the model in one line fenced as `caller_edit`, then still calls `Pack.on_block_action`. An unchanged edit tells nobody. One per-session bucket shared with card taps allows ten a minute; past it the caller sees "Please wait a moment…" and the model hears nothing (S6-5). Since V6-29 (S6-26) a browser answer to a requestable block nobody is waiting for (a late or unsolicited submit or cancel) spends the same bucket and reaches the model as a user message with the values fenced as `caller_answer` (at most 700 characters), never inside the reply's instructions; the `block_submitted` event names the answer's keys only. `EDITABLE_BLOCK_TYPES` is `details`, `checklist`, `notebook`; requestable, link, consent, upload, captions and handoff blocks are never editable. A `details` row whose key the model wrote outside the id pattern (for example `"Claim type"`) is not caller-editable (ask #163, open).

**Safe Markdown (V6-10, #333).** `web/src/lib/safe-markdown.tsx` is the one Markdown renderer for caller-facing text: `https` links only, platform-hosted images only, no raw HTML. Since V6-24 the transcript and the `markdown` block use it too (S6-8), and caller-authored notebook notes render without links (S6-9).

## 6. The notebook, the layout block and the Notebook preset (V6-08, V6-10)

The insurance panel was a React component over an insurance-only `UiState.custom`; the notebook is a **block** any agent can configure, the api validates and the model can read (D-V6-15).

**`notebook`.** Sections of four kinds — `text` (a list of notes, ≤ 100, each `{id, text, author: agent|caller, key, tone, edited_by}`; a `key` updates one note in place), `checklist`, `details` and `ink` (hosts a `canvas` block by id, §7) — on `plain|ruled|grid|legal` paper with a `print` or `handwritten` font. The shape shipped is the coordinator brief's, not D-V6-15's literal text (ask #51): one block-level `caller_can_write` instead of a per-section flag, `font` instead of `handwriting: bool`, notes instead of `{text, author_edits[]}`. The agent writes with `notebook_write(section_id, …, mode)` and `notebook_check`; `update_block` refuses a notebook; `describe_panel` renders the sections bounded and fenced, with "changed by the caller" markers. The caller may remove or rewrite any note, the agent's included, and the model is told (S6-6, accepted as designed).

**`layout`.** A flat container (D-V6-18): `kind: tabs|columns` and a list of child block ids. Children stay top-level entries of the panel, so the state map, patches and `describe_panel` are unchanged; the composite panel renders a claimed child inside its container. The api refuses a child claimed twice, a missing child, a layout claiming itself or another layout. Known gap: `show_block` into an inactive tab does nothing (ask #83).

**The Notebook preset.** `NOTEBOOK_PRESET` (contracts) is a `wide` composite panel: a status block, a notebook with Notes, Still needed, Summary and a Sketch section, a drawing board `sketch_board` claimed by the Sketch section with `caller_can_draw` on (ask #94), and a gallery. `caller_can_write` is on (ask #52). It is listed by `GET /v1/panels/presets` and applied with `agent_update(panel_preset="notebook")` or the "Starting panel" choice in Create agent, which today sends a second `PUT` after the create (ask #82). On the Cloud default LLM (`gemma-4-31b-it`, text-only) the preset carries the vision warning at the board, by design.

## 7. The drawing board and the ink stream (V6-12, V6-14)

**`canvas`.** `CanvasBlockConfig {caller_can_draw, tools, background: none|asset|live_camera}`; `CanvasBlockState {width, height, background, strokes, shapes, snapshot_asset_id, limit_reached}` with coordinates normalised 0..1. `CanvasBlockConfig.signature_mode` is superseded by the `signature` block and kept only so older boards validate (R-V6-3 #212, V6-28).

**The ink stream.** `lkap.ui.ink` is the first browser → agent **text** stream (D-V6-16): one JSON `InkMessage` per message (`add|erase|clear`, a stroke id, normalised points, colour, width — never text). The worker takes it only from the caller participant (checked before reading), at most 2 KiB, 20 messages a second (a token bucket), only for a board whose own flag or notebook allows drawing; it enforces points per stroke and per board, 2,000 strokes per board and a cumulative 50,000-point session budget (clearing does not refund it). Drops are counted and recorded by reason, never with content. Strokes enter state through the normal patch path, so the console mirror and listen-in see them. The page sends uncompressed text streams, batches about every 100 ms and mirrors the rate limit; box and arrow are two-point messages. Known gaps: the session budget has no signal the board can show (ask #122), and the generated TS type for `InkMessage.points` is wrong (ask #121; the page uses its own type).

**Agent shapes and reading handwriting.** `draw_on_canvas(block_id?, shapes)` (box, arrow, circle, text, path; upsert by id) and `clear_canvas`. `read_canvas(block_id?)` sends `lkap.ui.request {method: "snapshot"}`; the page answers, then streams a PNG (≤ 5 MiB) on `lkap.ui.upload` with the board's id. The worker accepts it only while a snapshot is awaited (20 s) for a board the caller may draw on (stricter than D-V6-16: an unsolicited picture is refused, so the caller cannot fill the 50-file cap), stores it as kind `frame` with `meta.source="ink"` (no new asset kind, no migration), and runs `describe_asset` with a handwriting prompt on the agent's vision model; the reading is fenced as `canvas:<id>` and bounded. The api re-checks the board and the type. An agent with a drawing board and no vision-capable LLM gets a validator warning. `pin_frame(canvas_block_id=…)` puts a camera frame behind a board ("circle the dent"). The "locate" half of V6-12 (a vision call returning boxes for `draw_on_canvas`) was **not built**: verifying it needed a paid vision call (ask #95).

**The console.** The board is an SVG with `perfect-freehand` outlines (MIT, 1.2.3), imported lazily so the session page's first load is unchanged; pen, highlighter, eraser, box, arrow; pointer and touch with pressure; undo sends an `erase`; the background is a pinned frame or the caller's camera. A notebook ink section renders its claimed board inside the section and the composite panel leaves it out of the flow.

## 8. The next blocks: signature, chart, timer, code, cart (V6-23, V6-24)

Five strict block types (D-V6-20), each with a tool the model uses and a console renderer:

| Block | Tool | Notes |
|---|---|---|
| `signature` | `request_signature(disclosure_text?, block_id?)` | A blocking request (180 s; cancels on barge-in like the other generic requests, R-V5-1). On a phone call or in text chat nothing can be signed and the tool answers at once. The strokes stay on the page; Sign answers `signed: true`, then the worker asks for the picture through the snapshot path and stores a PNG (≤ 1 MiB) as kind `signature`; only then are `signed`, the asset and the hash of the worker's own wording written and one `signature` event recorded. A late answer is dropped. Since V6-29: Sign is enabled only once the pad holds a stroke (S6-30); a decline on a block whose `allow_decline` is off is a bad answer, not a recorded decline (S6-29); the api stores a `signature` asset only as a PNG of at most 1 MiB for a `signature` block of the session's panel (S6-32). |
| `chart` | `show_chart(points, kind?, …)` | `number|bar|line|pie|gauge`, at most 200 points and 8 series, rendered as inline SVG the console owns with an accessible table; no chart library. |
| `timer` | `start_timer(seconds, label?, mode?, block_id?)` | Countdown or elapsed; the worker schedules the end, records `timer_ended` (never the label) and tells the model in one line; the page counts on its own clock. |
| `code` | `show_code(code, language?, title?, block_id?)` | Never run; rendered as the text of a code block (no Markdown fence built around it). |
| `cart` | `cart_set(lines, adjustments?, currency?, block_id?)` | The worker computes every total to the cent; the page shows them as given. |

`chart`, `code` and `cart` are on `UPDATABLE_BLOCK_TYPES` (their state models bound what `update_block` writes) but not on `STATE_DELTA_BLOCK_TYPES`: a page never rewrites what the agent showed the caller (ask #213, confirmed by R-V6-3). On phone channels the display tools write nothing and say so. Still parked from v5: map (D-V5-28), MCP Apps `embed` (D-V5-27), translation, campaigns, browser use, A/B tests, console voice cloning.

## 9. Tool context: placeholders, bindings, `requires_vars`, `confirm_readback` (V6-07, V6-11)

**Placeholders (D-V6-22).** An HTTP tool's URL path and query, its body template, and the pinned arguments of app actions and MCP tools may use `{{ ctx.session_id }}`, `{{ ctx.agent_id }}`, `{{ ctx.caller_phone }}`, `{{ ctx.caller_identity }}`, `{{ ctx.language }}`, `{{ ctx.timezone }}` (the caller's zone of R-V5-10; closes V5 ask #150), `{{ ctx.channel }}` (`web|phone|text`) and `{{ var.<name> }}` (flow and extraction variables, one namespace). The worker substitutes them at call time from a per-session `ToolCallContext` in one pass after the arguments, percent-encoding URL values. A placeholder is refused at save (and again at build) in a URL's scheme, host or port and in any header; `ctx.caller_phone` and `ctx.caller_identity` never reach a log or event. A missing value makes the tool answer "I need <label> first" without calling out; `requires_vars` makes the refusal explicit.

**`confirm_readback`.** Names arguments the model must read back first: the tool gains a reserved `confirmed` parameter and refuses until it is true. Since S6-10 the worker also requires a caller message newer than the refusal before it accepts `confirmed` (on realtime pipelines the caller's transcript can land late: at most one extra refusal, ask #165).

**Bindings (D-V6-23).** `bindings: [{path, to}]` (a JSON pointer into the result after `result_path`) write a successful result to `details:<block>.<key>`, `table:<block>`, `checklist:<item>`, `status`, `note` or `var:<name>` before the model's turn, bounded (20 bindings, 500 characters a value, 100 table rows), never to a requestable, link, consent, upload, captions or handoff block; a `tool_bindings_applied` activity line records them. **As fixed by S6-2 (the V6-20 gate):** a body *holds* its bound values and the handler applies them only after `run_with_policy` returns and the `tool_output` guardrail handed the result through, so a withheld result binds nothing; MCP tools go through the same guard since S6-3. Bound variables reach a flow's instructions only fenced (`tool_binding`, ask #31). HTTP, app, MCP and dataset tools share one helper.

**The console (V6-11).** The HTTP, MCP and app-action editors gained an "Insert value" picker (never offered for the URL host), a bindings table whose targets come from the agent's panel, and "Needs these values first" / "Read back before calling" fields. The dry run still renders only `{{ arg }}` placeholders (ask #33, open), so a tool that uses session values is tested in a session.

## 10. Live extraction and declarative rules (V6-13, V6-15, V6-28)

**Extraction (D-V6-24).** `AgentConfig.extraction {enabled, fields, triggers, min_turn_chars, still_needed}` runs in the background on `workflow_llm` (else the LLM): one JSON call within the worker's `LKAP_EXTRACTION_TIMEOUT_S` (default 10 s; V6-30 raised it from a fixed 2 s that a hosted model never met), cached by a transcript hash, never delaying the reply; when the model answers after the reply went out, the values, the panel writes and the rules still land then (an `instruct` note waits for the next caller turn), and a timeout is a logged warning. At most one call is in flight per session, with one more queued. Triggers are one per kind — every *n* caller turns (the default is every turn), after named tools, on leaving named flow nodes, or `manual` (the `extract_now` tool) — the union of the plan's cadence and the brief's triggers (ask #76). Fields are `ExtractionField` (a `VariableSpec` plus `label`, `hint`, `sensitive`, `show_in`); values go into the one variable store flows and tools share (`tools.context.session_variables`), a field's `show_in` writes it to a details row or a notebook section, and `still_needed: checklist` keeps `need_<field>` items in the envelope checklist (a notebook target is ask #73/#234, next plan). The `extraction` event carries field names and whether each is set; values only on the `full` storage tier and never for a `sensitive` field. Since V6-21: a sensitive field is masked (`••••`) on the panel and in `describe_panel` and left out of the session summary below `full` (S6-11); text values are cleaned and cut at 500 characters (S6-13); a flow node's own `extract` values are fenced like live ones (S6-12). A flow's `extract` wins for the names it lists.

**Rules (D-V6-25).** `AgentConfig.rules` (≤ 50) pairs a condition with up to ten actions (`checklist.set_item`, `checklist.check`, `status.set`, `details.set`, `note.push`, `var.set`, `escalate`, `instruct` — a one-turn system note, admin text — and `disposition.set`, added by V6-13). Conditions use a small grammar parsed in contracts (`rules_expr`: `var.x is [not] set|empty`, comparisons, `matches /re/`, `tool.<name>.ok|failed`, `not`, `and`, `or`, parentheses; no `eval`, no attribute access, no calls; bounded depth, checks and literal length). Rules run after each extraction, binding and tool batch; `once` is per session; each firing is a `rule_fired` event without values. A prompt agent's variables and disposition reach the session summary (ask #72).

**Pattern safety (S6-4, V6-28).** V6-21 widened the regex-safety scanner (`rules_expr.nested_repeat`, shared with guardrails) to refuse alternation inside a repeated group and adjacent overlapping unbounded repeats (`(a|a)+b` stalled the worker loop). Because that could make a **stored** rule unloadable, V6-28 moved the pattern check out of the contract's field validator: `Rule` checks the grammar only, `rule_issues` reports a refused pattern as an error at `rules[i].when` (a save is still a 422), and the worker skips such a rule with its existing warning. D-V6-31 gained the sentence; the RUNBOOK upgrade note says how to find and rewrite one (§9.8). Guardrail patterns go through the same scanner at save; since V6-29 (S6-28) the worker also skips a stored guardrail regex the scanner flags (a warning and a `guardrail_rule_unreadable` event naming the stage and rule, never the pattern), so a pre-V6-21 pattern cannot stall a call, and the upgrade note says to scan guardrails too.

**The console (V6-15).** "Extraction" (titled "Capture details") and "Rules" editor sections: a fields table, triggers, a condition builder with plain-words operators and a validated text fallback (a condition with `or`, `not` or parentheses is text-only from then on, ask #138), actions bound to the panel's blocks; `extraction` and `rule_fired` rows in the session timeline. The "test" button opens the test chat rather than forcing `extract_now` (ask #134).

## 11. Datasets: lookup tables (V6-16, V6-19)

A **dataset** ("lookup table" in the console) is a read-only table a workspace uploads (D-V6-27): CSV (sniffed separator, UTF-8 else Windows-1252) or JSON, at most 5 MiB, 50,000 rows and 64 columns, with up to 8 declared key columns typed `string|phone|email|number` and normalised for matching. A `phone` key matches on its last ten digits after dropping leading zeros, so numbers that differ only in country code collide (ask #108, a known limit). Migration `v6_002_datasets` adds `datasets`, `dataset_rows` and the per-key index `dataset_keys (row_id, column_name, dataset_id, value)` and widens the `tools.kind` check to include `dataset` (ask #103 records where the shape differs from the ledger). The bytes sit in the storage backend under `datasets/<workspace>/<id>/source.<ext>` (S6-18); the `dataset_import` job reports progress on its jobs row.

**Routes.** `POST /v1/datasets` (multipart; builder + `agents:write`), `GET`, `DELETE` (409 naming the tools that use it), rows preview, CSV export (a cell that starts like a formula is neutralised; nothing is ever evaluated), `POST /v1/datasets/{id}/lookup` (the console test), and `POST /internal/v1/datasets/{id}/lookup` (service token plus a live session id; only that session's workspace; an ended session is refused, S6-16). Quotas: 100 datasets and 1,000,000 rows per workspace, checked before the file is read; 10 uploads and 60 console lookups a minute per workspace (S6-14). Create, delete and a failed import write audit rows without cell values (S6-19).

**The `dataset` tool kind.** `DatasetToolDefinition {dataset_id (32 hex characters since S6-15), key_columns, return_columns, match: exact|prefix, max_rows ≤ 20}` plus V6-07's `requires_vars`, `bindings` and `pinned_arguments` (a pinned key column, often `{{ ctx.caller_phone }}`, is hidden from the model). The worker calls the internal route (api-local, so no outbound guard) and fences the rows as `dataset:<name>`; it records HTTP 200 or 404 so a flow step reads "no record" as `empty`. Logging from a call goes through a kit (`sheet_crm_log`), never into a dataset. Replacing a table in place is next-plan (ask #110).

## 12. The flow `tool` node (V6-17, V6-19)

A flow step that calls an attached tool with no model turn (D-V6-28): `{kind: "tool", tool, mcp_tool?, arguments, bindings, timeout_s ≤ 30 (10 by default), on: {ok, error?, empty?}}`. Arguments are rendered with V6-07's single pass (literals, `{{ var.* }}`, `{{ ctx.* }}`; a text that is exactly one `{{ var.x }}` keeps its type). The step runs through the same execution path as a model call (blocking, the fence, the guardrails, the duplicate policy), applies its bindings, sets `tool.<name>.ok|failed` for the rules engine, and takes the edge named for the outcome: `empty` is a success with no result or no bound value, or an HTTP 404/410 (ask #116); `empty` falls back to `ok`'s edge. The result text never reaches the model; later steps read bound variables, fenced. An unhandled `error` records `flow_error`, speaks a fixed apology and ends the call (the api warns when a step has no error path). A tool with `confirm_readback` cannot be a step; `on.ok` is required; every edge leaving a step is named by an outcome; a loop of steps only is refused; at most 10 steps per transition (asks #114, #115). The console's flow editor has the "Tool step" node, its tool picker and outcome edges (V6-19).

## 13. Tool kits (V6-18, V6-19)

A **kit** is a use case in one step (D-V6-26): tools, panel blocks, an instruction snippet, extraction fields, rules, optional flow steps and a test case, in variants by source (`http`, `mcp_preset`, `composio_action`, `dataset`, `none`). The catalogue is `api/src/lkap_api/templates/kits/*.json`, validated at import (every variant renders; snippets carry no link, key name, marker or placeholder; what a kit names starts with its prefix). Eight kits: `record_lookup`, `case_ticket`, `structured_intake`, `verify_identity`, `payment_esign_link`, `notify_escalate`, `sheet_crm_log` and `booking` (the Cal.com tool templates re-exposed; `/v1/tool-templates` stays).

`GET /v1/tool-kits` lists them rendered with each kit's default prefix; `POST /v1/tool-kits/{id}/instantiate` (builder + `agents:write`; a `composio_action` variant needs admin + `providers:write` before any vendor call, S5-40) takes a variant, a block prefix, settings, a key, app actions, a dataset, a flow anchor and `dry_run`. It creates the tool rows through `POST /v1/tools`'s checks (a kit's HTTP tools pass the host checks at instantiate time), appends the blocks and the snippet between `<!-- kit:<id>:<prefix> -->` markers, adds variables and rules, writes one agent version and one `tool_kit.instantiate` audit row (ids and counts only), and is idempotent by kit and prefix; a refused kit rolls back the tools it created. `structured_intake` and `notify_escalate` turn live extraction on (ask #147, ratified; the dry run says so). `verify_identity`'s code tools exist only with `tools.sms` set and call the business's own verification service, so the model never sees a code (ask #141; a platform code built-in is next-plan). MCP: `kit_list`, `kit_add`; recipes `add-kit`, `record-lookup-from-a-spreadsheet`. The Composio action slugs of `case_ticket` and `sheet_crm_log` are unverified until a live check (ask #143).

The console's Tools tab has a kits gallery and an Add-kit dialog that lists every tool, block, instruction and rule change from the dry run before Add (V6-19); it enables Add only on a fully valid preview (ask #191) and has no picker for app actions (ask #192).

## 16. Connections: agent names and their workers (V6-27)

**Agent names are unique per LiveKit server.** LiveKit hands a job to any worker registered under the dispatched name, so two connections on one server with the same `agent_name` split each other's calls. The api refuses that on create, on a change of URL or agent name, and in Test (409 `agent_name_in_use`), across all workspaces; the URL comparison ignores scheme, case, default ports and a trailing slash. There is no LiveKit API that lists registered agent names (ask #176), so a clash with an app outside LKAP stays invisible; Test adds a non-blocking warning when another connection's live workers share the server and name (`ConnectionTestResult.warnings`, `FleetStatus.shared_agent_name_workers`). No database constraint was added (ask #179).

**One connection, its own workers.** A worker serves exactly one connection (its `LKAP_CONNECTION_ID`, `LIVEKIT_*` and agent name). The console says so on the create form, shows a no-worker empty state and the worker count on the connection page and in the agent editor's connection picker (`FleetStatus.ready_workers`). **Call start fails fast:** `connect` and `text-sessions` answer 409 `no_worker_running` on an external or supervised connection when no worker of it has been heard from in 90 s — never in the first two minutes after the api starts, and not while another connection's live workers answer to the same server and name. A builder sees the connection's name and the Connections page; a public caller sees a plain "can't take calls right now" line with the same code (ask #181). `LKAP_CALL_START_WORKER_CHECK` is `block` by default, `warn` logs only and `off` skips it; the one false block is a worker started without `LKAP_CONNECTION_ID` on a non-default connection. Keeping `block` was Fable's recommendation and the user confirmed it (U-V6-4, ask #177); the real fix is workers reporting their own server and name (ask #178, a migration, next plan). Outbound phone calls do not check yet (ask #180). The connection page's one-click **Copy worker settings** puts the redacted worker environment on the clipboard; since V6-29 (S6-27) the api's own `OTEL_EXPORTER_OTLP_HEADERS` is a `<…>` placeholder there, in the `env`/`compose`/`lk` templates and in the deploy bundle, while the supervisor's real environment keeps it.

## 21. Reasoning models (V6-31)

**The problem (2026-09-29).** With the demo agents on `openai/gpt-6-luna` through OpenRouter, every turn failed with a 404 ("No endpoints found that can handle the requested parameters"). `openrouter-llm` sends `provider.require_parameters=true` by default (so a request with tools never lands on an endpoint that ignores them), and the api fills the registry's `temperature` default (0.7) into every resolved reference, so removing the stored field changed nothing; no Luna endpoint accepts `temperature`. `parallel_tool_calls` was suspected too, but livekit-agents 1.8.3 never sends it and neither does LKAP (pinned by a test). And a reasoning model is slow on a call: 8.2 s from end of speech to first audio for Luna at its default `medium` effort, against 3.6 s for GPT-4.1 mini on the same LiveKit Cloud stack.

**The capability view grows.** `ModelCapabilities` (the D-V4-24 view the api resolves declared → "Test model" → the cached live catalog → the registry, and hands the worker in `ResolvedProvider.capabilities` for `llm` and `workflow_llm`) gains `reasoning`, `reasoning_efforts` and `request_parameters`. OpenRouter is the one vendor list that publishes them per model (`supported_parameters`, and a `reasoning` record with `supported_efforts`), so its catalog adapter now keeps that record. The registry records the OpenAI GPT-5 ids on LiveKit Inference as reasoning models (livekit-agents treats them so itself) and the plain GPT-4 ids as not; Gemini on Inference and every OpenRouter suggestion stay unknown, so the live catalog decides. Google's direct entry thinks through `thinking_config`, not `reasoning_effort`, and gets no setting (an ask).

**What the worker does.** `lkap_agent.providers.reasoning` applies one rule from the contracts (`reasoning_effort_to_send`, `accepts_parameter`): an optional parameter (`temperature`, `top_p`, `parallel_tool_calls`, …; never `tools`) the model does not accept is left out, logged at DEBUG, so `require_parameters` stays on; with **Reasoning effort** empty, a reasoning model that lists its efforts gets the lowest one (`none` for Luna, `minimal` for Gemini 3.5 Flash), which is what a voice call wants; a stored effort the model does not offer becomes the next one above it. OpenRouter streams apply the same filter to each request's keyword arguments. With nothing known about the model (catalog never cached for that key, or cached before this change for the efforts) the request is exactly as before.

**What the builder sees.** The api warns, never errors: a stored option the model refuses ("left out of each request"), an ignored or replaced effort, and a reasoning model at `medium` or more on a voice pipeline ("adds several seconds to each reply"); a model that always reasons with no effort setting gets a tip. The model picker marks **Reasoning** models and **Fast for voice** ones (a small model, by a dated curated list, that does not reason or can reason at `none`/`minimal`); the LLM options show **Reasoning effort** only for a model that reasons, with Automatic (the lowest) first, and hide Temperature when the model sets its own.

**Compatibility (D-V6-31).** An exception to "no stored agent changes behaviour": an agent on a model whose view says it reasons and lists its efforts now sends the lowest effort (faster replies), and one on a model that refuses a stored option no longer fails. Every other agent sends the same request as before (pinned by a byte-for-byte test). A stored `provider: {"require_parameters": false}` workaround stays valid and is not migrated.
