# LKAP v2 — Phased Delivery Plan

Status: **decided** (Fable 5.1, 2026-09-19). Owners: **Opus 5** for hard/critical, **Sonnet 5** for the rest. Fable reviews at the end of each wave and owns the final review package.

Naming: v2 packages are **`V2-nn`**. Do not confuse with REVIEW-FINAL's fix packages (WP-A..D, done) or UI_UX_SPEC's UI packages (WP-0..WP-12; WP-0 landed, WP-1..12 resume under §4 below).

Definitions used by every package:
- **Python gate** (run inside the package dir): `uv run ruff check . && uv run ruff format --check . && uv run mypy src/ --strict && uv run pytest -q -m "not live"`.
- **Web gate** (in `web/`): `pnpm lint && pnpm typecheck && pnpm test && pnpm build`.
- **Contracts gate**: `cd contracts && uv run python -m lkap_contracts.export && cd .. && scripts/export_contracts.sh && git diff --exit-code contracts/generated web/src/contracts` (the export diff test must pass).
- **Live gate**: the named `uv run pytest -m live …` commands from `../RUNBOOK.md` §5 plus the v2 stages in §6 of this document, run against `wss://your-project.livekit.cloud` with exactly one worker per connection and never touching `other-project-agent`.
- **Exclusive ownership**: a package may create/edit only the paths it lists; shared files (`providers.py`, `api_models.py`, `registry.ts`, `main.py` router wiring, alembic versions) are owned by exactly one package per wave. Anyone else needing a change files it as a one-line ask in `docs/v2/_asks.md` for the owner.

### R-V2-30 — `add_member` re-adds; joining from another workspace goes through an invite (F-4, R2-19)
- Decision: the invite path is already consent-based: `POST /v1/auth/accept-invite` for an existing account requires that account's own password (`routers/auth.py`). So `add_member` narrows to what it is for: re-adding an account that was previously a member of **this** workspace (evidence: a `member.join`, `member.add` or `member.remove` audit row for this workspace and user). ### R-V2-34 — concurrency caps are reserved under a lock, and SQLite runs one api process (R2-15, ask V2-21-3)
- Decision: the count-then-insert in the three session starters, `routers/connect.py`, `routers/text_sessions.py` and `POST /v1/calls` (`telephony/calls.py::prepare_outbound_call`), becomes one helper in `lkap_api/limits.py`: `reserve_session_slot(db, agent, limits)`, an async context manager that (1) takes a per-process `asyncio.Lock` keyed by `agent.id`, (2) on Postgres locks the agent row (`select(Agent).with_for_update()`; SQLAlchemy silently drops `FOR UPDATE` on SQLite), (3) counts and raises `AgentBusyError` / `CallsBusyError`, and (4) stays held until the caller's `db.commit()` returns, so the row is visible to the next reader. The route holds the lock around its commit (`connect.py`, `text_sessions.py`, `routers/calls.py`; `prepare_outbound_call` does not commit, so the lock lives in the route). The workspace outbound cap uses the same helper keyed by `workspace_id` with the workspace row locked. Consequence written into RUNBOOK: on SQLite the guarantee rests on the in-process lock, so **SQLite deployments run exactly one api process** (the default today); Postgres is required for `api ×2`.
- Owner: **V2-22**. Acceptance: the V2-21 burst (`scratchpad/loadtest/race.py`, 50 simultaneous connects, `max_concurrent_sessions=5`) admits exactly 5, as an api test using `asyncio.gather` over the ASGI transport; the same for 20 concurrent `POST /v1/calls` against `max_concurrent_outbound=3`; a Postgres case in the existing `test-postgres` CI job runs two concurrent connects at the cap through two sessions and admits one.
