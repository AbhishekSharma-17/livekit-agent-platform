# Knowledge and memory for LKAP: assessment, optimisation plan, pluggable stores

Status: research and plan, no implementation. Written 2026-09-24 by the architect (Fable) from a read-only pass over `api/src/lkap_api/kb/**`, `routers/knowledge.py`, `agent/src/lkap_agent/platform_agent.py`, `tools/builtin/search_knowledge.py`, `config_client.py`, `contracts/.../agent_config.py::KnowledgeConfig`, `deploy/docker-compose.prod.yml`, the installed `livekit-agents==1.8.2` and `fastembed==0.8.0`, plus a read-only latency probe on `api/data` (three tiny seed KBs). Vendor facts are cited with URLs and access dates in §9; anything marked *unverified* was not confirmed against a primary source today.

---

## 0. Executive summary

LKAP's knowledge base is a correct but minimal RAG v0: naive 800-character windows, one local embedding model (`bge-small-en-v1.5`, 384-d), vector-only cosine top-k in LanceDB, no reranking, no score floor, and retrieval sitting on the **critical path of every voice turn** inside `on_user_turn_completed`. On the seed data the retrieval itself is cheap (query embed ~4 ms, kNN 3–8 ms per KB, SQLite join <1 ms, so roughly 20–40 ms warm end to end including the worker→api hop, estimated), which means the problem today is **quality and robustness, not raw latency**, and the plan must keep it that way: every quality step we add (hybrid, rerank, query rewriting, remote stores) costs 30–300 ms on time-to-first-audio unless it is moved off the critical path first.

Five findings drive the plan:

1. **Two LanceDB writer processes exist in prod today.** `docker-compose.prod.yml` runs `api` and the `arq` `jobs` worker as separate containers on the same `api-data:/data` volume; ingest upserts run in `jobs`, document/KB deletes run in `api`, and the only serialisation is an in-process `asyncio.Lock`. LanceDB's own position is that concurrent writers are supported through optimistic concurrency but "too many concurrent writers can lead to failing writes as there is a limited number of times a writer retries a commit" [V-89][V-90]; the compose file itself says concurrent KB writes are "NOT verified safe". Scaling `api` past one replica multiplies the deleters, and nothing ever runs `optimize()`, so the tables also fragment.
2. **Auto-inject silently throws away LiveKit's preemptive generation on every turn that has a hit.** Preemptive generation is **on by default** in livekit-agents 1.8.2 (`_PREEMPTIVE_GENERATION_DEFAULTS = {"enabled": True, ...}` in `voice/turn.py`; LKAP's `build_turn_handling` does not override it) and LiveKit's docs state: "If the chat context or tools change in the `on_user_turn_completed` node, the speculative response is discarded and regenerated" [LK-audio]. `_inject_knowledge` appends a message, so with `auto_inject=True` (the default) every turn with a hit pays for two LLM calls and gets none of the head start. The zero-code stop-gap is to disable preemptive generation whenever auto-inject is on (P0-0); the real fix is pre-fetching on interim transcripts *and* landing the injection before the SDK takes its preemptive snapshot, which needs a spike (P0-2), or moving retrieval to the tool path only.
3. **Every turn retrieves, nothing is filtered.** "Yes", "okay", "hold on" all trigger an embed + search and inject `top_k=4` chunks regardless of score (a real match scored 0.738 in LIVE-RESULTS; bge-small returns 0.3–0.5 for noise). The injected note lives only in the per-turn context copy, so follow-ups ("and the deductible?") re-search with a context-free query.
4. **The chunker cuts mid-sentence and stores no locators.** `KbChunk.meta` holds only `filename`; no page, heading or offset, so `kb_citations` can only name a file. `text/html` imports are ingested as raw markup.
5. **The embedder is a process-global env switch.** Changing `LKAP_EMBEDDER` breaks every existing KB (dimension mismatch against its LanceDB table); `KnowledgeBase.embedder_id` is recorded but never used to pick an implementation, and the model name is a hard-coded constant.

Top recommendations (details in §2, §5, §7):

- **P0 (this quarter, no new vendors):** gate retrieval (min score, skip short/backchannel turns, dedupe across turns), fix the chunker (sentence/heading-aware with page and heading metadata), parallelise the per-KB fan-out, add a local hybrid path (BM25 via SQLite FTS5 / Postgres `tsvector` fused with RRF), pre-fetch on the interim transcript (`user_input_transcribed`, `is_final=False`) so the hook only awaits an already-running task, and add a local cross-encoder rerank (`fastembed` `TextCrossEncoder`, measured today at ~110 ms for 20 passages and ~55 ms for 10 on a busy dev laptop CPU) *only* on the tool path and on pre-fetched results.
- **Default store follows the SQL database.** Keep LanceDB when `LKAP_DATABASE_URL` is SQLite (dev, single host, zero vendor keys, D6 still holds); use **pgvector** when it is Postgres (prod). That removes the second writer, gives `tsvector` BM25 for free, works with `api ×N`, and needs only a `pgvector/pgvector:pg16` image swap in the compose file. pgvectorscale is optional and only worth it above ~1M vectors.
- **Two plug points, not one:** a `VectorStore` (LKAP chunks and embeds, the store holds vectors + text) and an `ExternalRetriever` (the vendor owns ingestion and returns hits). Ship **Qdrant**, **Pinecone** and **Weaviate** as bring-your-own `VectorStore` connectors (Turbopuffer optional, with a warm-up); ship **Vertex AI Search**, **Bedrock Knowledge Bases**, **Azure AI Search** and **Ragie** as `ExternalRetriever` connectors, and let Drive/Notion/Confluence/SharePoint sync come from Ragie or Unstructured rather than building connectors.
- **Graph RAG: not by default.** For a voice agent over policy documents it is overkill; offer it later as an `ExternalRetriever` (LightRAG on the same Postgres, or Neo4j GraphRAG) for tenants whose questions are genuinely multi-hop.
- **Memory: Mem0 OSS on the existing Postgres (pgvector) as the default, Zep Cloud as the managed option**, keyed by an HMAC of `sip.phoneNumber` (or the web identity) per workspace, read once before the greeting, written once at session end by the existing summary job, per-agent opt-in with retention and an erasure route.

### 1.3 Latency budget of a voice turn and where retrieval sits

LiveKit's cascaded pipeline runs: end-of-turn detection → `on_user_turn_completed` (our hook, traced as its own span; the SDK logs `on_user_turn_completed_delay`) → LLM → TTS. Everything inside the hook delays the first LLM token. The hook receives a *temporary copy* of the chat context: the SDK comment reads "the user can edit it for the current generation, but changes will not be kept inside the Agent.chat_ctx", and LiveKit's RAG guidance is to add the retrieved text as an `assistant` message in exactly this hook [LK-external-data]. So the injected knowledge is seen by this turn's LLM call only; it does not accumulate, but it is also not available to the next turn.

`preemptive_generation` (on by default: `{"enabled": True, "preemptive_tts": False, "max_speech_duration": 10.0, "max_retries": 3}`) starts the LLM on the STT transcript *before* end-of-turn is confirmed and reuses that reply only if the hook left the transcript, chat context, tools and `tool_choice` equivalent (`agent_activity.py`: "preemptive generation invalidated after `on_user_turn_completed`…"). LiveKit's own documentation: "If the chat context or tools change in the `on_user_turn_completed` node, the speculative response is discarded and regenerated" [LK-audio]. `_inject_knowledge` changes the context whenever there is a hit, so **auto-inject and preemptive generation are mutually exclusive per turn today, and the discarded call is still billed.** Interim transcripts are available: `AgentSession` emits `user_input_transcribed` with `is_final: bool` [LK-events], which is the hook point for pre-fetching.

Budget: LiveKit measures its own optimised stack at ~354 ms time-to-first-sentence and says "Past a few hundred milliseconds, the conversation stops feeling natural" [LK-gemma]; the LLM's first token typically takes 100–600 ms of that depending on provider. Retrieval therefore has to stay well under ~50 ms on the critical path, or be finished before the turn ends. LiveKit's guidance for anything that takes "a few hundred milliseconds" or more is explicit user feedback: a verbal update via `generate_reply`, pre-synthesised filler audio, or background "thinking" audio [LK-external-data].

### 1.4 Multi-tenant isolation

- Admin routes scope every KB by `workspace_id` (404 across workspaces); the `agent_knowledge_bases`/`config.knowledge.kb_ids` attach is validated on save.
- LanceDB isolates by table name (`kb_{id}`), not by workspace; SQL rows carry `kb_id` only (no `workspace_id` on `kb_chunks`).
- `POST /internal/v1/kb/search` trusts the caller-supplied `kb_ids` (service token; the worker passes the resolved config's ids). That is by design, but any future store or memory layer must keep the same rule: **the api resolves scope, never the store**.

### 1.5 Scaling limits

- **The "single writer" assumption is already false in prod**: `api` (deletes) and `jobs` (upserts) share `api-data:/data`; the `asyncio.Lock` is per process. Lance commits use optimistic concurrency with rename-if-not-exists and a bounded retry count, so contention surfaces as failed writes rather than corruption [V-89][V-90][V-91]; `api ×N` adds N deleters. SQLite dev mode is safe only because `LKAP_JOBS_BACKEND=inline` keeps ingest in the api process.
- No ANN index: brute force is fast to ~100k vectors × 384-d and then degrades; LanceDB needs an explicit `create_index` (IVF_PQ / IVF_HNSW_*) and, in OSS, manual `optimize()` for compaction, pruning and adding new rows to the index ("Rows appended after an initial index build remain outside the index until refreshed manually (OSS)") [V-48][V-92]; delete-then-add upserts leave deletion markers and small fragments; the Python docstring's rule of thumb is to optimize after ~100k modified rows or 20 modification operations [V-93].
- Sequential per-KB fan-out.
- Global embedder: no per-KB model, no re-embedding path, no dimension check before query.
- Backups: the LanceDB directory is tarred with `LKAP_DATA_DIR` (RUNBOOK); there is no consistency point between SQL rows and Lance files, so a restore can leave orphan vectors or chunks without vectors.

### 1.6 File types and web import

- Supported: Markdown, plain text, PDF (text layer only), JSON-as-text via URL import. Declared in the OpenAPI description as `.md/.txt/.pdf`.
- Not supported: DOCX, PPTX, XLSX, HTML→text (a `text/html` URL is accepted by `import_media_type_allowed` and ingested as raw tags), scanned PDFs (no OCR), tables (pypdf flattens them), images.
- URL import is one page, no crawling, no sitemap, no re-sync/refresh, no dedupe by URL.

### 1.7 Concrete weaknesses (ranked by user impact)

1. Retrieval on every turn with no score floor and no short-utterance gate → irrelevant chunks injected into most turns, wasted tokens, and preemptive generation disabled.
2. Context-free queries: follow-ups are searched verbatim; no rewriting from the conversation; the injected note is not carried across turns.
3. Char-window chunking without structure or locators → cut sentences, weak citations, tables destroyed.
4. Vector-only: exact identifiers ("H0-44721", "AUTO-11111", form names, dollar amounts) are precisely what bge-small is worst at; BM25 would catch them.
5. No reranking; `top_k` cosine order goes straight to the prompt.
6. Two-writer LanceDB in prod; no index; no compaction; no scale-out path.
7. Global embedder switch breaks existing KBs; hard-coded model names (violates the "never hardcode model names" rule).
8. Sequential per-KB queries; 3 s timeout.
9. `text/html` imported raw; no DOCX/PPTX; no OCR; no crawling or re-sync.
10. Both auto-inject and `search_knowledge` on by default → the model can trigger a second search for a turn that already had one.
11. No evaluation harness: nothing measures recall@k or answer faithfulness per KB.
12. Ingest progress is binary (`pending` → `ready`), and a 25 MB file can occupy the single `arq` worker for minutes.

## 2. Optimisation plan for voice

Principle: **first take retrieval off the critical path, then spend the reclaimed budget on quality.** Each item lists the latency it costs *on the turn* (not at ingest) and the expected effect.

### P0 — no new vendors, no schema migration beyond `KbChunk.meta`, ≈1–2 weeks

| # | Change | Where | Turn latency | Expected impact |
|---|---|---|---|---|

Reverted by P0-2 once injection lands before the snapshot. |
| P0-1 | **Retrieval gate**: skip auto-inject when the utterance is < N tokens or matches a backchannel list ("yes", "okay", "thanks", digits only); add `min_score` (starting point 0.55 for bge-small cosine, per-embedder, **to be calibrated by P0-9**; today's only data points are one 0.738 hit and an estimate for noise) and drop hits below it; dedupe chunk ids already injected in the last M turns. | `platform_agent._inject_knowledge`, `KnowledgeConfig` | −20–40 ms on ~half the turns | Fewer irrelevant chunks, fewer tokens, restores preemptive generation on turns without hits. |

### P2 — platform features, ≈1–2 months

- Pluggable stores and external retrievers (§5), the "knowledge connection" UX, and pgvector as the Postgres default.
- Web crawling and sync (sitemap crawl with Firecrawl or Crawl4AI; scheduled re-sync; content-hash dedupe).
- Graph RAG as an opt-in external retriever (§4).
- Agent memory (§6).
- Multilingual: `bge-m3` or `multilingual-e5` per KB; language detection at ingest.
- Speculative retrieval from the agent's *own* upcoming sentence (retrieve while TTS plays), and answer caching for FAQ-style KBs.

### What the plan does **not** recommend

- An LLM-based query rewrite on the critical path (200–600 ms).
- Reranking un-prefetched results on the critical path with a hosted API.
- Replacing fastembed as the default: the zero-vendor-key rule (D6) still matters for the free-tier story; bge-small is adequate once hybrid + rerank exist.
- Graph RAG by default (§4).

### 3.2 Default for single-host, and bring-your-own connectors

**Recommendation: the default follows the SQL database.**

- `LKAP_DATABASE_URL` is SQLite (dev, laptop, single container): keep **LanceDB** as the local store, but (a) create an index above ~50k rows, (b) run `optimize()` after ingest jobs, (c) keep ingest in-process (`inline`), which is already the dev default. D6 (no vendor key) still holds.
- `LKAP_DATABASE_URL` is Postgres (prod compose): use **pgvector** in the *same* database. Reasons: it removes the second writer and the shared volume, transactions cover chunk rows and vectors together (no orphan vectors after a restore), `tsvector` gives BM25 with one GIN index, `api ×N` and `jobs` all work, backups are `pg_dump`, and the Python path is the existing `asyncpg`/SQLAlchemy stack. Cost: change `postgres:16` to `pgvector/pgvector:pg16` in `deploy/docker-compose.prod.yml` and one migration. HNSW index per KB via a partial index or a single table with `(kb_id, embedding)` and `WHERE kb_id = $1` plus iterative index scans (pgvector ≥ 0.8) for filtered recall. Index dimension caps are 2,000 for `vector` and 4,000 for `halfvec` [V-1], so `text-embedding-3-large` (3,072-d) must use `halfvec` or Matryoshka truncation via the `dimensions` parameter; `text-embedding-3-small` (1,536) and every fastembed model fit as-is. pgvectorscale (StreamingDiskANN) is a later option above ~1M vectors; it needs its own extension image, so it is not part of the default.
- Why not LanceDB Cloud or a hosted vector DB as the default: it would reintroduce a vendor key into the free path, and the corpora LKAP serves (per-agent policy docs, playbooks) are small.

**Bring-your-own connectors (in priority order):**

1. **Qdrant** — Apache-2.0, free-forever cloud node plus self-host, native sparse+dense RRF fusion, payload-index multitenancy, `AsyncQdrantClient` with every method async. The best fit for teams who already self-host [V-8][V-9][V-10][V-11].
2. **Pinecone** — the most common "we already have it"; serverless namespaces map 1:1 to KBs, integrated BM25/sparse hybrid, `PineconeAsyncio`, and hosted rerankers on the same key [V-15][V-16][V-18][V-22].
3. **Weaviate** — BSD-3, native per-tenant shards, hybrid with score fusion by default, `WeaviateAsyncClient`, free sandbox [V-23][V-24][V-26].

Fourth, optional: **Turbopuffer** (namespaces, native BM25 hybrid, cheapest at scale, `AsyncTurbopuffer`) with the caveat that a cold namespace answers in ~874 ms p50 versus 14 ms warm, so the adapter must issue a warm-up query at session start [V-58][V-59]. Milvus/Zilliz is held back by its async client's "not for production" note [V-37]; Chroma's hybrid exists only in Chroma Cloud [V-41]; Elasticsearch/OpenSearch, MongoDB Atlas and Redis can follow behind the same Protocol when a tenant asks; Supabase is the pgvector adapter with a different DSN.

### 4.1 When graph RAG is worth it for a voice agent

The benchmark evidence is consistent: graph RAG helps on **multi-hop** and **global/summarisation** questions and does not help, or hurts, on **single-hop factoid** questions. GraphRAG-Bench (ICLR '26) reports HippoRAG2 53.4 % vs vanilla RAG 42.9 % on complex reasoning but states that "basic RAG is comparable to or outperforms GraphRAG in simple fact retrieval" (medical set: vanilla RAG 64.7 % vs MS-GraphRAG 38.6 %) and that "GraphRAG frequently underperforms vanilla RAG on many real-world tasks" [G-56]; the MSU/Meta unified evaluation finds 2–3 point gains on MultiHop-RAG/HotpotQA, a loss on Natural Questions, and "substantially higher construction costs and retrieval latency" [G-58]. The original GraphRAG paper's gains are on global sensemaking over ~1M-token corpora [G-16].

For LKAP's workload (an agent answering a caller from a few hundred pages of policy lines, playbooks and FAQs, with a sub-second turn budget) that means: **not by default.** The discriminators that justify offering it to a tenant are (a) questions that traverse entities ("which riders on the policy issued by agent X in 2023 cover water damage and were amended after the flood?"), (b) temporal facts ("what was the deductible *before* the renewal?"), (c) corpus-wide "themes" questions, or (d) a tenant that already runs a graph store. Indexing cost is LLM-bound in every option (per chunk or per episode), and every option except raw graph queries has at least one LLM call somewhere near the query path that must be removed or pre-computed before it can sit in a voice turn.

**Recommendation:** keep graph RAG out of the core and offer it later as an `ExternalRetriever` (§5) with two reference adapters: **LightRAG** on the same Postgres/pgvector (self-hosted, MIT, `naive` mode or a cached keyword step for the voice path) for tenants who want it without a new database, and **Neo4j** (`neo4j-graphrag` `HybridCypherRetriever`, run through `asyncio.to_thread` or replaced by our own async Cypher) for tenants who already run Neo4j. Graphiti belongs to the memory story (§6), not the document story. Microsoft GraphRAG is in maintenance mode and LLM-bound at query time; skip it.

**`VectorStore` v2** (extends today's Protocol; LanceDB stays the reference implementation):

```python
class StoreCapabilities(BaseModel):
    hybrid: bool          # native lexical + dense fusion
    filters: bool         # metadata filters at query time
    stores_text: bool     # can return chunk text without the SQL join
    namespaces: bool      # per-KB isolation is a first-class object

class VectorStore(Protocol):
    capabilities: StoreCapabilities
    async def ensure_namespace(self, kb_id: str, *, dimension: int) -> None: ...
    async def upsert(self, kb_id: str, records: list[VectorRecord]) -> None: ...   # VectorRecord gains text + meta
    async def query(self, kb_id: str, *, vector: list[float] | None, text: str | None,
                    k: int, filters: dict[str, Any] | None = None) -> list[VectorHit]: ...
    async def delete_document(self, kb_id: str, document_id: str) -> None: ...
    async def delete_kb(self, kb_id: str) -> None: ...
    async def health(self) -> StoreHealth: ...
```

`KnowledgeService.search()` composes: embed (cached) → `store.query(vector, text)` when `capabilities.hybrid` else `gather(store.query(vector), lexical.query(text))` + RRF → optional `Reranker.rerank(query, hits)` → `min_score` → join text for stores without `stores_text` → `KbHit` (gains `meta`: page, heading_path, url).

**`ExternalRetriever`**: `async def search(query, *, k, filters) -> list[KbHit]` plus `describe() -> RetrieverInfo` (source names, last sync, doc count) for the console. No ingest through LKAP; the KB row records `kind="external"` and the connection id.

### 5.2 Data model and config

- `knowledge_connections` (new table): `id, workspace_id, name, kind (lancedb|pgvector|qdrant|pinecone|turbopuffer|vertex_ai_search|bedrock_kb|azure_ai_search|ragie|vectara|lightrag|neo4j)`, `settings` JSON (non-secret: url, index/namespace prefix, region, project), `credential_id → credentials` (vault ciphertext, same encoding as today), `status (unverified|ok|error), last_checked_at, last_error, capabilities` JSON.
- `knowledge_bases` gains `connection_id` (nullable = platform default), `dimension`, `embedder_model`, `chunking` JSON, `kind (managed|external)`, `external_ref` (e.g. the Vertex data store id).
- `KnowledgeConfig` v2: `kb_ids`, `auto_inject`, `top_k`, **`min_score`**, **`prefetch: bool`**, **`rerank: "none"|"local"|"connection:<id>"`**, **`max_inject_tokens`**, **`skip_short_turns: bool`**, `query_mode: "last_turn"|"conversation"`.
- Embedder resolution becomes per KB (`knowledge_bases.embedder_model` + the connection's credential), with `LKAP_EMBEDDER` only as the default for new KBs.

### 5.3 Console UX: "knowledge connection"

- Settings → **Knowledge connections** (next to Storage and LiveKit connections): a table and a **Dialog** (no drawers, per the UI rule) with: Kind (radio cards grouped *Vector stores* / *Managed search* / *Graph*), non-secret fields rendered from a per-kind schema (like `providers.json` today), a credential picker that reuses the vault "add credential" modal (API key / service-account JSON / connection string), and **Test connection** (lists collections/indexes, checks the dimension, reports `capabilities`). Secrets are write-only; the response carries a fingerprint.
- KB create dialog: "Where is this knowledge stored?" → *Platform default* (LanceDB/pgvector, no choice needed) or a connection; for *Managed search* kinds the dialog asks for the external data-store/index id and skips upload.
- KB detail: retrieval settings preview (hybrid on/off, reranker, min score), a test search that shows **vector / lexical / fused / reranked** scores side by side, and the eval-set runner (P0-9).
- Agent Knowledge tab: `min_score`, `prefetch`, `rerank` selectors with a latency hint ("adds ~40 ms on the tool path").

### 5.4 Rollout order

1. P0 items on the existing LanceDB + SQL (no schema change except `meta`, `dimension`, FTS index).
2. `VectorStore` v2 + `PgVectorStore` + default-by-database; migrate prod with a one-off re-index job (`kb_reindex`).
3. `knowledge_connections` + Qdrant/Pinecone/Turbopuffer adapters + console dialog.
4. `ExternalRetriever` + Ragie, Vertex, Bedrock, Azure adapters.
5. LightRAG / Neo4j adapters; memory (§6).

### 6.1 Design for LKAP

- **Identity**: `subject_id = hex(HMAC-SHA256(workspace_memory_key, E.164(sip.phoneNumber) | web participant identity))`; the raw number never reaches the memory store. The ICO's pseudonymisation guidance is explicit that a keyed hash (not a bare hash) is the technique to use, that the key must be held separately with strict access control, and that the result is still personal data for whoever holds the key, so erasure must delete the vendor-side record too [M-67]. The key lives in the vault per workspace; rotating or deleting it orphans the memories cleanly. Hex output satisfies every vendor's id constraints (Supermemory's tag regex, Zep/Mem0 free-form ids).
- **When**: read once at session start (in the worker, before the greeting, where 50–300 ms is invisible) and inject a compact "What we know about this caller" block into the system prompt; write once at session end from the existing summary job (transcript → `remember`), never per turn on the voice path. Both Mem0's voice guide and LangMem's docs say the same: extraction on the hot path "adds perceptible latency"; do it after the call [M-43][M-45]. The vendor LiveKit examples (Mem0, Zep) that call `add`/`search` inside `on_user_turn_completed` are not the pattern to copy: they put a vector search plus, for Mem0, an LLM extraction on the critical path, and would also invalidate preemptive generation (§1.3).
- **Scope**: per agent by default (`memory.scope: agent|workspace`), opt-in (`memory.enabled=false`), `retention_days`, a caller-facing consent line where the tenant requires it, and an erasure route `DELETE /v1/memory/subjects/{subject_id}` that fans out to the backend (`user.delete`, `delete_all(user_id)`, container-tag delete). Note Supermemory's delete is admin-only, which complicates automated erasure.
- **Backends**: `MemoryStore` Protocol with `recall(subject_id, query, k)`, `remember(subject_id, messages | facts)`, `forget(subject_id)`. **Default: Mem0 OSS (`AsyncMemory`) on the existing Postgres/pgvector**, using the agent's configured LLM for extraction (any OpenAI-compatible base URL or LiteLLM) and `infer=False` where a tenant wants verbatim-only memory; graph memory is not available in OSS and is not needed here. **Managed option: Zep Cloud** (Graphiti temporal graph, `user_id`/thread model, `AsyncZep`, real erasure API, SOC 2/HIPAA on higher tiers) via a knowledge connection of kind `zep`. **Not recommended**: Letta (it wants to be the LLM and the agent loop, which conflicts with LiveKit's; its Python client is deprecated), LangMem (LangGraph-store-bound, last release 2025-10), Supermemory (admin-only erasure; otherwise a plausible third managed option).
- **Console**: caller memories visible on the session detail with a "forget" action; memory reads/writes logged to `session_events`; a workspace-level "purge all memories" action.

## 8. Open questions for the user

1. **Prod topology**: is `api ×N` planned soon? If yes, the pgvector default moves to P0; if the platform stays single-host for a while, P0 can ship on LanceDB and pgvector lands with the connections work.
2. **Free-tier stance**: must the *prod* default remain vendor-key-free (fastembed + pgvector), or is a hosted embedder (e.g. `text-embedding-3-small`, Voyage) acceptable as the prod default? This decides whether re-embedding jobs are P1 or P2.
3. **Corpus shape**: what do real tenants upload? Policy PDFs with tables (→ Docling in P1), scanned documents (→ OCR), or mostly Markdown/FAQ? Expected size per KB (hundreds of pages vs. tens of thousands)?
4. **Languages**: English only for now, or multilingual (→ `bge-m3`/`multilingual-e5` and multilingual rerankers)?
5. **Which "bring your own" store do you hear most from prospects**: Qdrant, Pinecone, or something else (Azure AI Search / Vertex)? The order in §3.2 is a guess.
6. **Memory**: is cross-session caller memory a product requirement now, and which regulatory posture applies (HIPAA/GDPR: consent, retention, erasure)? Should memory be per agent or per workspace?
7. **Preemptive generation**: do you want it enabled by default? It shapes P0-2 (pre-fetch must inject before the SDK snapshot).
8. **Budget for hosted rerank**: acceptable per-search cost (Cohere/Jina/Voyage) on the tool path, or local only?
9. **Graph RAG**: any tenant asking for relationship-style questions today? If none, §4 stays P2.
