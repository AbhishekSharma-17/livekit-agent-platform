## 1. Part 1 — decisions

### D-W3-1 — Session events from packs and tools: a `record_event` callback on the pack session context

**Decision.** `PackSessionContext` (packs/base.py:169–186) gains one Protocol **method**, `def record_event(self, event_type: str, payload: dict[str, Any]) -> None: ...` (declared like `UiChannel.patch`, not as an attribute: under `mypy --strict` a non-ClassVar attribute on a Protocol is a *settable* member, and a fake implementing it as a method would fail with "expected settable variable, got read-only attribute"). Its shape matches what `PlatformAgent` (platform_agent.py:169) and `BackgroundToolRunner` (background.py:65) already accept as a `Callable`. The worker's `SessionContext` dataclass keeps a `Callable`-typed field named `record_event` (a callable attribute satisfies a Protocol method) bound to `SessionObserver.record` in `_assemble` (main.py:538–558). Packs and built-in tools call `ctx.record_event(type, payload)`; delivery stays buffered/best-effort in the observer, so a pack can never slow or break a call by recording.

**Emission rules (write these into CONTRACTS §7 next to the event list).**
- Platform-owned types are emitted only by the worker: `session_started`, `agent_state`, `user_turn`, `agent_turn`, `tool_call_started/ended`, `workflow_run`, `metrics`, `error`, `info`, `session_ended`. A pack must not emit them.
- Packs and tools may emit `escalation` (`{reason: str, urgency: "low"|"normal"|"high"}`) and `info` (`{message: str}`). Any other type is stored as-is by the api (`SessionEventIn.type` is a plain `str`, internal.py:158–166) and rendered generically by the console; packs should prefix custom types with their pack id (`insurance_claim.route_changed`) so they never collide with platform types.
- `escalate_to_human` (tools/builtin/escalate_to_human.py:22–51) emits `escalation{reason, urgency}` right after `set_status("Escalated", "warning")`.
- The insurance pack emits `escalation` on the **route transition into `emergency_escalation`**, in `render_and_patch` (packs/insurance_claim/tools.py:104–125), which already knows `intake.previous_route` and is the single choke point for both the tool-triggered run and the passive debounced run. Payload: `{"reason": "claim routed to emergency_escalation", "urgency": "high", "route": <route>}`. Not on the urgent-reply branch of `submit_workflow_run`: the passive run never speaks but still escalates, and a repeated run must not re-emit.

**Why a callback and not a richer API.** The observer is the only writer to the api's event endpoint and already owns buffering, redaction and shutdown ordering; exposing a `Callable` keeps packs free of any `lkap_agent` import (dependency direction `agent → packs → contracts` holds), needs no contracts model change (no schema regen, no TS regen), and matches the two existing call sites so there is one idiom, not two.

**Contracts implications.** `packs/base.py` is "CONTRACTS §8 verbatim": §8's `PackSessionContext` listing gains the one line. `SessionContext` (platform_agent.py:136–154, `@dataclass(slots=True)`) gets the field with a no-op default so every existing constructor call keeps compiling (`tests/live/test_e2e_insurance.py:104`, `test_main.py`). Both fake contexts must gain the attribute or `mypy --strict` fails wherever a fake is passed as `PackSessionContext`: `agent/tests/fakes/fake_ctx.py` and `packs/tests/insurance_claim/fake_ctx.py` (they are divergent copies — see F-18).

**Does it block the MVP?** No. The console already shows the escalation as `workflow_run` + the urgent `done` activity + the danger stamp, and the user's manual test does not depend on the event. It is in the fix plan anyway because it is ~40 lines, it is the last unimplemented CONTRACTS §7 type, LIVE_TEST_PLAN Stage 9's pass line names it, and without it a second pack has no way to put anything of its own on the session timeline.

**Implementation.** WP-B (§4) owns the code; WP-A wires `record_event=record_event` into `SessionContext(...)` in `_assemble`; WP-D writes the CONTRACTS §7/§8 lines and appends this decision to `DECISIONS-W2.md` as **D-W3-1** so it sits inside the document that "wins everywhere".

### D-W3-2 — Start-call freeze: confirmed as implemented (freeze is a no-op until a connect has been attempted)

**Decision.** Confirm the refinement in `web/src/lib/livekit.ts:268–276`: `freeze()` sets `frozen = true` only when `last !== null || inflight !== null`. This amends D-W2-2(a), whose text ("keep the exported `freeze()`, harmless, still called on unmount") assumed the cleanup could never run before the first fetch — React StrictMode in `next dev` runs the session effect's cleanup before re-running it on the same memoised source, so the unrefined freeze killed every first call in dev.

**Rationale.** The purpose of freezing is to prevent a *second* `POST /connect` on the same source; a source that has never fetched has nothing to replay and nothing to protect. The refinement preserves D-W2-2(a)'s guarantee (one source, at most one row) in every path: first success → `frozen` (line 260); unmount after success → `freeze()` no-op; unmount during the in-flight first fetch → freezes, and the second `start()` receives the same in-flight promise (line 230), still one row.

**One nuance to record.** Freezing while the first fetch is in flight and that fetch then *rejects* leaves the source dead (`last === null`, `frozen === true` → `session_closed` on any later call). This is acceptable only because `SessionExperience` (session-experience.tsx:43–53) remounts a fresh `LiveSession`, and therefore a fresh source, on every Start/Try-again (the `attempt` key). If anyone ever reuses a source across attempts, this nuance becomes a bug. The vitest at `web/tests/livekit-connect.test.ts` ("freeze() before any connect is a no-op") covers the StrictMode case; WP-D adds one sentence to DECISIONS-W2 D-W2-2(a) and records the decision as **D-W3-2**.

## 2. Executive verdict

**MVP-grade for a supervised local test on LiveKit credentials; not for exposure to anyone but the operator.** The core loop the docs promise is real and was proven live: dispatch → resolve → cascaded Inference session → typed and (scripted) audio turns → tools → panel patches → hangup → one stored session row with transcript, usage and events, plus the insurance pack end to end on `google/gemini-3.5-flash` including camera pinning and the urgent escalation path. The code quality is high for an MVP: contracts-first, secrets handled correctly end to end (vault, service-token-only decrypt path, redacted logs, `server-only` admin fetch, IDs-only dispatch metadata), offline suites that exercise the real `AgentSession` with fakes rather than mocking the platform away, and tripwire tests on the two SDK-private seams.

What I would tell the user before they start:
1. **Everything you paste into the console is protected only by the fact that the web app runs on your laptop.** `/api/console/*` has no authentication of its own (by D14 design); anyone who can open `http://localhost:3000` is an admin, and test mode rides on that. Do not port-forward or tunnel the web app.
2. **One real handoff blocker is fixed in §4 before you test providers/avatars:** today a bad avatar key or a failing `session.start()` crashes the job silently (no spoken line, row marked `ended` instead of `failed`). Until WP-A lands, a "provider works / avatar works" verdict from a silent call is unreliable.
3. **Nothing ends an idle call.** `user_away_timeout_s` only flips a state flag; a forgotten `/s/…` tab streams STT and bills Inference until you close it (the 6 h sweep marks the row failed but does not end the room). WP-A adds an idle hangup; until then keep calls short and close tabs.
4. **Unverified live paths:** a real human mic+camera call in a browser, realtime models (Gemini Live/OpenAI Realtime), avatars (bey/tavus), image generation, vendor-key STT/LLM/TTS, MCP servers, and the Docker builds. The factory constructs every registry provider offline, and the console lets you select and credential all of them, but none has run against a vendor.
5. **The no-code HTTP-tool flow has a trap** (F-05): an HTTP tool with an empty `allowed_hosts` passes the console's dry run and fails every live call. WP-C fixes both ends; until then always fill `allowed_hosts`.

## 6. How to build your second use case today

What the code actually supports, with the gaps named. Three paths, cheapest first.

### Path A — no code: a new agent from the console (generic pack)

1. `/console` → **New agent** → name, pack **generic** → Create. You land in the editor with a runnable cascaded Inference pipeline (`deepgram/nova-3` → `google/gemma-4-31b-it` → `inworld/inworld-tts-2`) that needs only the LiveKit keys.
2. **Providers**: switch any slot to a vendor (Deepgram, OpenAI, Google, Cartesia, ElevenLabs) or the whole pipeline to **Realtime** (Gemini Live / GPT Realtime); pick a model from the combobox or type one; **+ New** next to Credential opens the paste dialog (values are encrypted, only a fingerprint comes back). Add an **Avatar** (bey/tavus) or **Image generation** (Google/OpenAI) the same way. The worker constructs exactly what you saved, per job, no restart. Gap: none of the vendor/realtime/avatar/image paths has run live yet (F-34); there is no "Test credential" button (F-16).
3. **Instructions & voice**: system prompt, greeting (`say` = TTS reads it verbatim; realtime models without TTS auto-switch to `generate`), language, timezone, interruptions, away timeout.
4. **Tools**: toggle the built-ins (`end_call`, `search_knowledge`, `describe_current_frame`, `pin_frame`, `push_note`, `set_status`, `escalate_to_human`, `current_time`; `http_request` is a separate switch and only works with a worker `LKAP_HTTP_TOOL_ALLOWED_HOSTS`). **HTTP tool**: name, description, JSON-Schema `parameters`, method, URL and body templates with `{{ arg }}`, headers with `{{ secret.NAME }}` bound to an `http-tool-secret` credential (free-form NAME=value bag), `result_path` JSON pointer, **`allowed_hosts` (required in practice — F-05)**, Dry run. **MCP server**: streamable-HTTP URL, headers/secret, optional `allowed_tools`. Gap: tools are attached only when you **Save & validate** (WP-C adds the hint); stdio MCP is not supported.
5. **Knowledge**: create a KB at `/console/knowledge`, upload `.md/.txt/.pdf` (fastembed, local, no key; first upload downloads ~130 MB), wait for `ready`, attach it here; auto-inject per turn + `search_knowledge` tool; `top_k`.
6. **Panel**: keep `generic` (renders status/progress/notes/checklist/assets/activity plus a raw view of `custom`), toggle camera / screen share / chat / per-turn frame injection. A camera agent on gemma gets the amber "cannot see images" hint — pick `google/gemini-3.5-flash`.
7. **Save & validate** → fix any red errors → **Test call** (draft, via the console proxy) or **Published** → share `/s/<slug>`.
