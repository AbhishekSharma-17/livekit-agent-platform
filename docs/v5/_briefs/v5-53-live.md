## Vendor facts (checked for V5-53 on 2026-09-26)

"Verified" = read on that date from the named Composio documentation page and coded to. "Unverified" = not stated on any page read; the code's assumption is given and the live run confirms or corrects it.

| Fact | Status | What the code does |
|---|---|---|
| Several connected accounts per toolkit per `user_id`; each may have an `alias`, a human-readable label **unique per user and toolkit within a project**; an empty string clears it; no length or character rule is documented | **verified** (`docs.composio.dev/docs/managing-multiple-connected-accounts`; API reference, "Update connected account") | The alias is `label_slug(label)` (`[a-z0-9_]`, at most 40 characters), with `_2`, `_3`… when a sibling already has it. |
| The alias is set on `POST /connected_accounts/link` as a top-level `alias` field, and on `POST /connected_accounts` **inside `connection`** | **verified** (API reference, "Create a link", "Create connected account") | `start_link(alias=…)`, `create_with_key(alias=…)`. A link refused because of the alias (409/400: an account LKAP does not track holds it) is asked for again without one and the alias is set after sign-in; a key connect is retried the same way on 409. |

| Execution picks the account with `connected_account_id` (or `alias`); without one, "the most recently connected active account" is used | **verified** (multiple-accounts page) | Every `provider` tool now carries its connection's `connected_account_id` (materialise, and re-pinned on activation and reconnect). ## What V5-53 does not do (by design or pending an ask)

- **Existing tools are not renamed** when an app gains its second account (R-V5-13 item 3): the first account's tools keep `<app>_<action>`; their descriptions gain `(<label>) ` on the next `refresh-schema?apply=true` (the response says `description_prefixed`). They are, however, pinned to their account the moment the second account becomes active, so they never run on the wrong one.
- **The account line does not reach the model yet.** `provisioning.SessionPlan.account_line` composes "Gmail accounts: Work (default; account "work"), Personal (account "personal") — say which one to use when it matters." for every app with several chosen accounts, but neither the MCP tool row nor `ResolvedAgentConfig` has a field for it and `compose_instructions` has no hook (worker and `routers/internal.py` are outside V5-53). A multi-account tool-finder session is provisioned correctly; until the ask lands the model learns the accounts only from Composio's own tools (step 7 records whether that is enough).
- Two accounts may not share a label within one app (409); the aliases still differ when two labels slug alike ("Work" / "Work!" → `work`, `work_2`).
- A pending account (sign-in never finished) cannot be made the default; the first account that finishes signing in is the default.
